1 What observability solves

A distributed integration can be healthy at every individual resource blade and still be slow or wrong as a business transaction. Observability exists to answer four questions: what happened, where, in what causal order, and to which business transaction?

architect boundary

Monitoring is the act of watching known signals. Observability is the broader ability to infer internal system behavior from emitted telemetry, including questions you did not prebuild a dashboard for.

2 Metrics, logs, traces, and events are different evidence

Metrics

Numeric time series. Fast, compact, ideal for alerting and trends: latency, failures, CPU, queue depth, throttling.

Logs

Detailed records. Rich context for investigation: error details, workflow events, gateway logs, resource logs.

Traces

Related spans that reconstruct one distributed operation and show parent/child causality and duration.

QuestionBest first signal
Is the system unhealthy right now?Metrics and alerts
Which hop consumed the latency?Distributed trace
Why did this one hop fail?Logs, exceptions, dependency details
Who changed the resource or configuration?Azure Activity Log / control-plane events
Which prescription or order was affected?Business correlation / tracked property
gotcha

Do not turn a high-cardinality business identifier such as PrescriptionId or OrderId into a metric dimension. Metrics work best with bounded dimensions. Put high-cardinality searchable identifiers in logs/traces.

3 Azure Monitor data platform

Azure Monitor is the umbrella service. In the current data platform, Log Analytics workspaces hold log and trace data queried with KQL. Azure Monitor workspaces are the metrics workspace used for Prometheus and the newer OpenTelemetry metrics path, queried with PromQL.

Application Insights is the application-performance and distributed-tracing experience on top of Azure Monitor. Current Application Insights resources are workspace-based and require a linked Log Analytics workspace. If you create one without selecting a workspace, Azure can create a managed workspace for it.

current behavior

Classic Application Insights resources are retired and no longer ingest new data. Use workspace-based Application Insights.

4 Application Insights and OpenTelemetry

For new Application Insights projects, Microsoft recommends the Azure Monitor OpenTelemetry Distro. It packages supported OpenTelemetry instrumentation with Azure-specific capabilities such as Application Insights standard metrics, Live Metrics, resource detection, sampling compatibility, offline retry, and Microsoft Entra authentication options.

Microsoft-supported rich path

Use the Azure Monitor OpenTelemetry Distro when Application Insights is your primary observability experience.

Vendor-neutral path

Azure Monitor also supports native OTLP ingestion patterns for teams standardizing on OpenTelemetry pipelines and collectors.

The Application Insights connection string identifies ingestion endpoints and the resource. Treat configuration as sensitive operational data, but remember the instrumentation key inside it is an identifier, not a secret. Microsoft Entra authenticated ingestion is available for stronger control.

The lowercase Application Insights tables and the App* Log Analytics tables represent the same workspace-based application telemetry through different query scopes. Do not assume a query copied from one scope works unchanged in the other.

5 Trace identity vs business correlation

W3C Trace Context uses a traceparent header to carry a trace ID, parent span ID, and flags across HTTP boundaries. Application Insights maps distributed operation identity into fields such as OperationId, item Id, and ParentId.

A business correlation ID is different. It might be a prescription transaction ID, order ID, claim ID, workflow business key, or MessageId. It should survive retries, replays, redelivery, dead-letter/resubmit, and sometimes even a completely new technical trace.

trace ID != business ID != message ID != workflow run ID
design rule

Preserve W3C trace context where the platform/SDK supports it, and separately stamp one stable business correlation key into message metadata, tracked properties, custom dimensions, and application logs.

6 APIM telemetry: gateway request plus backend dependency

APIM can send frontend request/response telemetry, backend dependency telemetry, exceptions, and explicit policy traces to Application Insights. Current documentation also lists correlated child dependency tracking for supported policies such as forward-request, send-request, send-service-bus-message, validate-jwt, and several data/AI policies.

performance gotcha

Do not blindly set APIM Application Insights logging to 100 percent and log bodies/headers in a high-throughput gateway. Microsoft documents material throughput impact in high-rate tests and recommends sampling plus restrained payload logging. Application Insights is not your audit ledger.

security

For APIM to Application Insights, Microsoft recommends a connection string with APIM managed identity credentials where possible. Portal setup still has limitations, so IaC/REST may be needed for the managed-identity configuration.

validate-jwt detail

When APIM shows a validate-jwt dependency, the external call is the OpenID Connect metadata/JWKS retrieval used to obtain issuer and signing-key configuration. Local signature/claim validation itself is not a remote dependency.

metric cardinality has hard limits

For APIM custom metrics, each dimension is limited to 100 unique values and each metric namespace to 1,000 active time series. A transaction ID, patient ID, MessageId, or request ID therefore belongs in logs/traces, not metric dimensions.

7 Asynchronous boundaries add queue time

A queue breaks the simple HTTP timing model. End-to-end latency becomes:

producer work + send + broker residence + consumer work + downstream dependencies

Current Azure Service Bus client libraries support distributed tracing integration. Azure Functions also has current OpenTelemetry guidance demonstrating trace propagation across HTTP and Service Bus chains. But do not assume every connector, custom client, or older SDK preserves trace context automatically.

measure this

Record or derive queue wait from message enqueue time to consumer start. This is often the missing number when the Function executes in 300 ms but the user waits 20 seconds.

async gotcha

Retries and redelivery can create multiple technical attempts for one business transaction. Your observability model must be able to show attempt number, MessageId, delivery count when available, DLQ reason, and the stable business key.

Async serviceWhat to observeArchitectural caution
Service BusSend/receive spans where instrumented, enqueue-to-consumer wait, delivery attempts, DLQ, processing duration.Do not assume every connector or custom client propagates trace context. Keep the business correlation ID in message metadata or payload.
Event GridPublish/delivery failures, delivered vs dropped/dead-lettered events, destination processing duration, failure logs.Event delivery telemetry proves broker behavior, not automatically one continuous application trace through every subscription target.
Event HubsIngress/egress, throttling/errors, consumer lag, checkpoint/consumer health, partition-level bottlenecks.High-volume streams usually need aggregate metrics plus selective traces rather than one expensive full trace per event. Runtime audit and application-metrics logs are tier-dependent.
how Service Bus trace context crosses

With the current Azure.Messaging.ServiceBus client, the library writes a Diagnostic-Id into ServiceBusMessage.ApplicationProperties during send/schedule operations and uses it to correlate the message activity with send, receive, process, and settlement spans. That is an SDK behavior - do not assume every connector or custom producer preserves the same property. Keep the stable business ID explicit on the message as well.

how to measure queue wait

Service Bus stamps the broker arrival time as EnqueuedTime/EnqueuedTimeUtc. At consumer start, calculate queueWaitMs = nowUtc - message.EnqueuedTime and emit it as a metric/property. The broker timestamp is useful because it is not based on the producer clock.

queueWaitMs = (DateTimeOffset.UtcNow - message.EnqueuedTime).TotalMilliseconds

Once emitted, trend p50/p95/p99 queue wait separately from handler duration. A fast Function behind an 18-second queue is still an 18-second customer experience.

8 Logic Apps telemetry

Logic Apps modelObservability path
StandardApplication Insights enhanced telemetry is available. Trigger/action events include connector/action context, retries, exceptions, workflow/run identity, and can use OpenTelemetry-formatted export.
ConsumptionUse Azure Monitor diagnostic settings / Log Analytics tracking data. Tracked properties and custom tracking IDs are important for business searchability.

For Standard workflows in Application Insights, current documentation shows operation_Id as the workflow run ID for trigger/action telemetry, with operation_ParentId linking caller/child relationships. The telemetry also exposes clientTrackingId when you set one.

design rule

If the business key exists in the incoming Service Bus message or HTTP body, surface it early as a tracked/custom property. Do not make operators scroll thousands of workflow runs hoping to recognize the right one.

9 Functions telemetry

Azure Functions integrates with Application Insights and now also has an OpenTelemetry telemetry mode and language-specific guidance. The important architecture distinction is between:

  • host/runtime telemetry - trigger execution, host behavior, scale/runtime logs;
  • application telemetry - spans, dependencies, exceptions, custom logs, business context produced by your code;
  • dependency/service telemetry - Service Bus, Storage, SQL, partner APIs, and other Azure resources.
host.json gotcha

Overly aggressive log-level filtering or sampling can remove telemetry you later expect to query. Treat monitoring configuration as production configuration and test it in an environment that has realistic traffic.

For a Service Bus-triggered Function, capture message identity and business correlation alongside the trace. If processing succeeds but telemetry export fails, business processing must not depend on the telemetry call succeeding.

10 Diagnostic settings and resource logs

Diagnostic settings are configured per Azure resource and select which supported resource-log categories and platform metrics are sent to destinations such as Log Analytics, Event Hubs, Storage, or partner integrations.

Resource-specific tables

Prefer resource-specific Log Analytics tables where the service supports them. They are easier to query and evolve than putting unrelated services into one giant AzureDiagnostics schema.

Policy at scale

Use Azure Policy/initiatives to deploy diagnostic settings consistently across subscriptions and resource groups instead of relying on portal clicks.

delivery semantics

Azure resource logs are not a transactional audit channel and are not documented as completely lossless. If the business or regulatory requirement requires a legally durable record of every transaction, design that audit record explicitly.

2026 cost change

Exporting some platform-log categories through diagnostic settings to Storage, Event Hubs, or partner destinations can incur export charges. Microsoft documents billing activation changes effective June 15, 2026. Log Analytics ingestion has its own pricing model.

storage retention

A diagnostic setting can route logs to Storage, but that does not make them immutable. Add a Storage lifecycle policy for retention, and add an immutability policy separately when tamper resistance is a requirement. The old diagnostic-settings storage-retention feature is deprecated and its retention behavior was disabled on September 30, 2025.

11 KQL: follow a transaction, not a table

In a workspace query, start with the identity you know and normalize the fields you need. A technical trace query is useful when one OperationId survived the path:

union AppRequests, AppDependencies
| where OperationId == "<trace-operation-id>"
| project TimeGenerated, Type, AppRoleName,
          OperationId, ParentId, Id, Name, Success
| order by TimeGenerated asc

For an end-to-end integration, standardize one opaque businessCorrelationId in APIM trace metadata, Logic Apps tracked/client correlation properties, Service Bus message properties, and Function telemetry. Then query the business journey even when an async hop creates a new technical trace:

let businessId = "RX-2026-004182";
union
(
  AppRequests
  | extend c = todynamic(tostring(Properties["correlation"]))
  | extend BusinessId = coalesce(
        tostring(Properties["businessCorrelationId"]),
        tostring(c.clientTrackingId),
        tostring(Properties["clientTrackingId"]))
  | project TimeGenerated, Signal="request", AppRoleName,
            OperationId, ParentId, BusinessId,
            Detail=Name, Success, DurationMs
),
(
  AppDependencies
  | extend BusinessId = tostring(Properties["businessCorrelationId"])
  | project TimeGenerated, Signal="dependency", AppRoleName,
            OperationId, ParentId, BusinessId,
            Detail=Name, Success, DurationMs
),
(
  AppTraces
  | extend c = todynamic(tostring(Properties["correlation"]))
  | extend BusinessId = coalesce(
        tostring(Properties["businessCorrelationId"]),
        tostring(c.clientTrackingId),
        tostring(Properties["clientTrackingId"]))
  | project TimeGenerated, Signal="trace", AppRoleName,
            OperationId, ParentId, BusinessId,
            Detail=Message, Success=bool(null), DurationMs=real(null)
)
| where BusinessId == businessId
| order by TimeGenerated asc
important

The exact property path depends on how each component emits telemetry. The architecture decision is the stable field name and propagation contract; the KQL is the normalization layer.

If the consumer emits queueWaitMs as a custom property, trend broker residence separately:

AppTraces
| where isnotempty(Properties["queueWaitMs"])
| extend queueWaitMs = todouble(Properties["queueWaitMs"])
| summarize p50=percentile(queueWaitMs, 50),
            p95=percentile(queueWaitMs, 95),
            p99=percentile(queueWaitMs, 99)
  by bin(TimeGenerated, 5m)
query strategy

First narrow by time, environment, role, and correlation key. Then expand. Starting with union * across months of production telemetry is both expensive and slow.

12 Alerts, SLIs, and availability

Azure Monitor supports metric alerts, log-search alerts, simple log alerts, and activity-log alerts. Metric alerts are usually the best first choice for fast, low-cost thresholding when the signal already exists as a metric. Use KQL alerts when the condition requires richer joins/filtering or business logic.

alert design

Page on symptoms that require human action. Use dashboards for context. Do not page separately on ten downstream causes for the same customer-visible outage.

Application Insights availability monitoring currently uses Standard tests for public HTTP/HTTPS endpoints. URL ping tests retire on September 30, 2026 and should be migrated before that date.

dynamic thresholds

Dynamic thresholds can learn normal metric/log behavior and reduce hard-coded threshold maintenance, but they need historical data and are not ideal for every slowly degrading condition. Know what you are asking the model to detect.

SLI, SLO, error budget, burn rate

TermMeaning
SLIThe measured reliability/performance signal, such as successful requests or p95 latency.
SLOThe target you set for that SLI over a compliance period, for example 99.9% successful transactions.
Error budgetThe allowed unreliability before the SLO is missed. At 99.9%, the budget is 0.1%.
Burn rateHow quickly current failures are consuming that error budget. Fast burn catches sudden regressions; slow burn catches sustained degradation.
URL ping retirement - September 30, 2026

Existing URL ping tests are removed on the retirement date. Standard tests are the current replacement for public endpoints, but enabling them incurs charges and alert rules are not migrated automatically. Migration therefore means: recreate/validate the test, review cost, repoint or recreate alerts, then retire the old test.

private endpoints

Standard availability tests require network reachability and cannot directly test an endpoint that is reachable only through your private network. For nonpublic APIs, run a health probe from inside the network and emit a metric/log signal that Azure Monitor can alert on. TrackAvailability() custom tests remain documented for existing implementations, but Microsoft now labels that guidance as archived classic API guidance rather than the preferred new design.

alert processing rules

Use Azure Monitor alert processing rules to add/suppress action groups by scope, filter, and schedule. They are the native way to suppress notifications during planned maintenance without disabling the underlying alert rule and losing the alert event itself.

dashboard trap

A beautiful dashboard is not evidence that correlation works. Test the incident path: start with one business ID, find its trace, identify a slow dependency, locate the message attempt, then reach the exact exception or workflow action.

14 Sampling, retention, and cost

  • Prefer trace-consistent sampling at the instrumentation layer. Application Insights' OpenTelemetry sampler is designed to avoid randomly breaking distributed traces.
  • Ingestion sampling exists but Microsoft does not recommend it as the primary choice for OpenTelemetry workloads.
  • Daily cap is a last-resort cost safety valve. Hitting it creates a telemetry blind spot.
  • DCR/workspace transformations can filter or reshape incoming logs before storage, but transformations have their own cost rules and should not be treated as free processing.
  • Retention is table-specific. Log Analytics commonly starts with 30-day defaults, Analytics tables can be configured for longer interactive retention, and long-term retention can extend much further.
  • Table plans are table-specific. Do not assume all Application Insights tables can simply be switched to Basic/Auxiliary.
never sample audit truth

Observability telemetry can be sampled. A required business/audit record cannot. If every prescription-signing event must be retained, write that durable record to the system designed to own audit truth, then observe that system separately.

Healthcare rule: decide whether the telemetry may contain PHI before thinking about cost

PHI boundary

A prescription body, patient name, MRN, DOB, medication details, or another patient identifier copied into telemetry makes that telemetry PHI-bearing data. Treat the monitoring path as part of the sensitive-data surface: access, retention, export, incident response, and purge decisions now matter.

  • Default to no request/response body logging at APIM and application layers. Enable it only for a narrowly justified diagnostic case.
  • Mask or exclude sensitive headers/query parameters where APIM diagnostics support data masking.
  • Never use patient identifiers as metric dimensions. High-cardinality identifiers are bad metric design and expand sensitive-data exposure.
  • Use an opaque business transaction ID. RX-2026-004182 is useful because it can correlate the journey without encoding an MRN or patient identity.
  • Use DCR/workspace transformations on supported tables to remove or obfuscate sensitive fields before they are stored. Prefer preventing collection at the source; transformations are a second control, not permission to log everything.

15 Private monitoring paths: AMPLS

Azure Monitor Private Link Scope (AMPLS) lets you route Azure Monitor ingestion/query through private endpoints. This is a monitoring-network architecture problem: private endpoint, DNS, access mode, and which monitor resources are associated with the AMPLS must all agree.

common break

Locking down Application Insights but forgetting the linked Log Analytics workspace can break private query experiences. Microsoft specifically calls out the need to secure both for workspace-based Application Insights.

Some Azure portal and Resource Manager-based experiences have Private Link limitations. Test the actual operator workflow from the network where your team will investigate incidents.

16 Failure checklist for architects

  • No telemetry at all: wrong connection string, ingestion blocked, sampling/cap, role/identity issue, DNS/private-link issue, runtime telemetry disabled.
  • Trace stops at APIM: backend not instrumented, context not propagated, unsupported connector/policy path, sampling mismatch.
  • Trace stops at Service Bus: client/consumer instrumentation missing, older SDK, custom sender stripped context, async hop starts a new trace without a link.
  • Cannot find a business transaction: no stable business ID was stamped into message/workflow/application telemetry.
  • Function is fast but transaction is slow: measure queue residence, retries, throttling, downstream dependencies, and cold/start/scale behavior.
  • Logic App run is hard to locate: capture client tracking ID / tracked properties and query telemetry instead of relying only on run-history scrolling.
  • Unexpected bill: body/header logging, high-cardinality custom events, 100% APIM logging, unsampled App Insights, verbose resource logs, broad diagnostic exports.
  • Alerts are noisy: alerting on causes instead of customer symptoms, thresholds too tight, no evaluation window, no suppression/grouping strategy.
  • Private monitoring broke: AMPLS association, PNA settings, private DNS, linked Log Analytics workspace, portal/query path.
health of observability

Also monitor telemetry ingestion gaps, sampling/cap events, agent/exporter failures, private DNS/AMPLS reachability, and whether critical dashboards/alerts still receive fresh data. An observability platform can fail silently while the application remains healthy.

17 Interview model

say this

I design observability in layers. Platform metrics tell me health and capacity. Application Insights/OpenTelemetry gives me distributed request and dependency traces. Diagnostic settings centralize resource logs. I propagate W3C trace context where supported, but I also carry a stable business correlation ID through HTTP, messages, workflows, and logs because retries can create new technical attempts. For async paths I measure queue residence separately from consumer processing. I alert on user-facing symptoms and use KQL plus traces for root cause. Finally, I control cost with sampling, selected log categories, retention, and transformations rather than logging everything.

interview drill
  1. APIM shows 80 ms and Function shows 300 ms, but the business transaction took 12 seconds. Where do you look next?
  2. Why can one business transaction have more than one trace ID?
  3. Why is a Service Bus MessageId not automatically your business correlation key?
  4. When would you alert on a metric instead of a KQL query?
  5. Why is 100% APIM body logging a bad default?
  6. What is the difference between a Log Analytics workspace and an Azure Monitor workspace?
  7. How would you find the exact Logic App run for one prescription ID?
  8. Why is Application Insights not an audit system?
  9. What breaks when you put monitoring behind Private Link?
  10. How would you prove whether latency is queue wait or Function execution?
