End-to-End Observability - Feynman Way

derive the model from one slow business transaction
A prescription request crossed six services. The user saw success 14 seconds later. Every individual resource looks green. Where did the 14 seconds go?
Feynman loop: start with the mystery, invent only the evidence you need to solve it, predict what the evidence should look like, then break the model with retries, queues, sampling, and missing context.

1 Start with the mystery

If one process owned the whole request, you could put a stopwatch around it. But distributed systems split the work. One service waits on another. A message may sit in a queue. A retry may happen after the original HTTP request is already gone.

prediction

If every Azure resource says "Healthy," can the business transaction still be slow? Yes. Resource health and transaction behavior answer different questions.

2 Why logs alone fail

Imagine five log files:

APIM       10:00:00 request received
Logic App  10:00:00 workflow started
ServiceBus 10:00:01 message accepted
Function   10:00:12 function started
Partner    10:00:13 request completed

The timestamps suggest a story. But production has thousands of concurrent transactions. Which Function line belongs to which APIM request?

Detail without identity is just noise with timestamps.

So the first thing we need is not a bigger log. We need a thread that lets us stitch related work together.

3 Give the technical operation an identity

This is the idea behind distributed tracing. Each component creates spans for local work, and parent/child relationships preserve causality. But an asynchronous broker is a boundary: the consumer can continue the causal trace only when trace context is actually propagated.

Across HTTP, W3C Trace Context standardizes this with traceparent. With the Azure Service Bus SDK, Diagnostic-Id is carried in message application properties. Connectors and custom producers still need verification, so keep a separate business correlation ID.

4 A span is a stopwatch with context

A span is not just a log line. It has a start, duration, status, name, attributes, and a causal relationship to other spans.

Once you can see spans, you stop asking "is APIM slow?" and start asking "which child operation dominates the parent duration?" That is a much more useful question.

5 The queue breaks the simple timeline

This is the observability lesson from Service Bus: queue time is not function time. If you only monitor Function duration, you can miss the real bottleneck completely.

prediction

A Service Bus queue depth grows from 10 to 50,000 while Function duration stays flat at 250 ms. Is the Function healthy? Locally maybe. End-to-end, the system is falling behind.

6 Trace ID is not business ID

Now break the model. A message fails. Service Bus redelivers it. The Function retries a downstream API. Operations resubmit the DLQ item tomorrow.

The technical trace can legitimately change across attempts. The business transaction did not. So you need both.

Trace ID answers: what caused this attempt? Business ID answers: what real-world transaction is this about?

7 Derive metrics, logs, and traces

Now we can derive why three telemetry shapes exist:

Metric

"Failures are 8% right now." Cheap, fast, alertable. But not enough detail to explain one failure.

Trace

"This one request spent 9 seconds waiting for the partner." Causal and temporal.

Log

"Partner returned validation code RX104 because field X was missing." Local detail.

derive it

If you use logs to answer every health question, you pay query/ingestion cost for problems metrics solve better. If you use only metrics, you know something is wrong but not which transaction or dependency caused it.

8 Now map the model to Azure

Azure Monitor is not one database. It is the umbrella observability platform. Application Insights gives application-centric tracing/performance experiences. Log Analytics gives KQL over logs and traces. Diagnostic settings route resource telemetry. Azure Monitor workspaces serve the Prometheus/OpenTelemetry metrics path.

9 Find where the time went

For an integration transaction, write the latency equation before opening a portal:

total = gateway + workflow + broker wait + consumer + downstream + retry delays

Then gather one measurement for each term. This prevents random troubleshooting.

If this term is high...Look for...
GatewayAPIM policy work, auth calls, backend connect time, gateway capacity.
WorkflowConnector retries, action duration, concurrency, external calls.
Broker waitQueue depth, consumer scale, sessions, throttling, poison-message head-of-line effects.
FunctionCPU, downstream calls, lock handling, cold/start/scale, code path.
PartnerDependency span duration, HTTP status, timeout/retry policy.

10 Derive alerting from human attention

You do not want a person staring at dashboards. So some signals must wake someone up.

rule

Page on a symptom that is important enough for a human to act on: sustained failure rate, SLO burn, queue backlog age, DLQ growth, availability loss, severe throttling.

Then attach the context needed to investigate. A page that says "Function exception count = 17" without environment, operation, correlation, and impact creates work rather than removing it.

prediction

If queue depth grows every night because a planned batch runs, should a static threshold page the team every night? Probably not. The alert needs a better signal, window, schedule, or dynamic baseline.

11 Observability has a cost

Suppose your gateway processes millions of requests. Before asking what telemetry costs, ask what the telemetry contains. In healthcare, copying a prescription body, patient identifier, or sensitive header into monitoring data creates a PHI-bearing observability path.

Sampling is not deleting random evidence after the fact. Good trace sampling keeps a coherent subset of whole traces so you can still reconstruct them. A daily cap is an emergency brake, not a design strategy.

audit boundary

Never solve audit retention by disabling sampling on your observability platform. Audit truth and observability telemetry have different semantics, retention, and cost requirements.

first principle

Do not log a patient payload just because a logger can accept it. Keep body logging off by default, mask sensitive headers/query parameters, and use an opaque transaction ID for correlation. Cost optimization comes after the privacy boundary is correct.

12 Observability can fail too

This is the part people forget. Your monitoring path is another distributed system.

Telemetry missing

Bad connection string, SDK not initialized, sampling, quota/cap, exporter failure, ingestion blocked.

Trace broken

Context stripped at gateway, connector, message sender, or custom client.

Query broken

Wrong scope/table names, retention expired, private query path blocked, schema changed.

Alert broken

Wrong threshold, no data, action group failure, rule disabled, signal too delayed.

So monitor the monitoring path. Know what "no telemetry" means before an incident.

13 Break the model

prediction exercises
  1. An APIM request is sampled out but the backend records an exception. What happens to your end-to-end picture, and why does trace-consistent sampling matter?
  2. A Service Bus message is redelivered three times. Should all attempts have the same business correlation ID? Should they necessarily have the same trace ID?
  3. The Function finishes in 200 ms, but the message was enqueued 9 minutes earlier. Which metric or timestamp proves the bottleneck?
  4. A Logic App has 500,000 runs. You know the OrderId but not the run ID. What should have been stamped into telemetry?
  5. You put Application Insights behind Private Link and portal queries stop working. What other resource and DNS/access path do you inspect?
  6. Your APIM throughput drops after enabling detailed telemetry. What settings do you review first?
  7. One team wants every request body in Application Insights for seven years. What architecture boundary are they crossing?
  8. A dashboard is green, but customers are getting errors. Which part of your signal/alert design is suspect?
  9. Your trace ends at Event Grid. What assumption about automatic context propagation should you question?
  10. A partner API retry creates three dependency spans. Is that a telemetry bug or useful evidence?
prediction

Your API is private-only. A Standard availability test cannot reach it. Where should the health probe run, and what signal should it emit so Azure Monitor can alert?

prediction

Your SLO is 99.9%. Errors spike briefly but recover. What matters more than the raw error count: how much error budget was consumed, and how fast was it burning?

14 Blank-page explanation

say this without notes

Observability lets me reconstruct one business transaction across distributed components. I use metrics for health and alerting, traces for causality and latency, and logs for local detail. I propagate W3C trace context where supported, but I also carry a stable business correlation ID because queues, retries, and resubmissions can create new technical attempts. In Azure, Application Insights/OpenTelemetry gives application tracing, Log Analytics gives KQL, diagnostic settings collect resource logs, and Azure Monitor ties the platform together. For async flows I always separate queue wait from processing time. I control telemetry volume with sampling and selected categories, and I keep audit truth outside sampled observability data.
