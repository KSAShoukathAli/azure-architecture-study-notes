Azure Integration Services: 35 interview questions, answered

For architect and senior engineer rounds. Read the question, answer it out loud first, then open it and compare.

Each answer starts with the short version you'd say in the first 20 seconds. The detail below it is what you use when they push on follow-ups. Scenario questions have an orange edge.

Core services

They start here to check you know the building blocks and when each one fits.

Q1When would you choose Logic Apps Standard over Consumption? What changes in hosting, networking, and cost?

Short answer. Standard for enterprise work: private networking, many workflows in one app, predictable cost at volume, and local development. Consumption for small, spiky, low-volume flows where pay-per-action is cheapest.

ConsumptionStandard
HostingMulti-tenant, shared by MicrosoftSingle-tenant, runs on the Functions runtime in a Workflow Standard plan (or ASE v3)
WorkflowsOne workflow per resourceMany workflows per Logic App
BillingPer trigger and action executionPlan compute, plus managed connector calls
NetworkingPublic endpoints onlyOutbound VNet integration, inbound private endpoints
Workflow typesStateful onlyStateful and stateless
ConnectorsManaged (shared) connectorsBuilt-in connectors run in-process (Service Bus, Blob, SQL, Event Hubs) plus managed
Dev and deployMostly portalVS Code, run locally, deploy as a zip like app code

The built-in connectors matter more than people expect. In Standard, the Service Bus trigger runs inside your app. It uses your VNet, your identity, and scales with your plan. A managed connector call goes out through Microsoft's shared connector infrastructure instead.

Cost flips with volume. A flow that runs 50 times a day is almost free on Consumption. The same flow at 2 million actions a day is far cheaper on a fixed Standard plan.

What they're probing: whether you know the cost model and the networking story, not just "Standard is newer." Bonus point: ISE was retired in 2024, and Standard is its replacement for isolated workloads.

Q2Compare Service Bus, Event Grid, and Event Hubs. Give a use case for each.

Short answer. Service Bus for business messages you cannot lose. Event Grid for reacting when something happened. Event Hubs for high-volume streams you want to read and replay.

  • Service Bus. A broker. Consumers pull, lock a message, and complete it. You get dead-lettering, sessions, transactions, and duplicate detection. Use it for "submit this prescription" or "create this order."
  • Event Grid. A router. It pushes lightweight notifications to subscribers, with filtering and retries (up to 24 hours by default), and can dead-letter to Blob. Use it for "a file landed, go process it."
  • Event Hubs. A partitioned log. Events are retained, and each consumer group tracks its own position, so you can replay. It speaks the Kafka protocol too. Use it for telemetry, clickstream, or audit streams feeding analytics.

The cleanest way to say it: a message carries intent, and the sender expects it to be processed. An event is a fact, and the sender doesn't care who reacts.

What they're probing: the message vs event distinction. Many candidates list features. Fewer explain why you'd pick one.

Q3Service Bus queues vs topics with subscriptions. How do filters and actions work?

Short answer. A queue has one logical consumer. A topic is publish-subscribe: each subscription gets its own copy and behaves like its own queue. Filters decide which copies each subscription receives.

  • Correlation filter. Exact match on properties. Cheapest and fastest. Use it when you can.
  • SQL filter. Expressions like region = 'NC' AND priority > 3. More flexible, more CPU on the broker.
  • Actions. A SQL action can change properties on that subscription's copy, for example SET routedBy = 'nc-rule'.

Filters read message properties, never the body. So the publisher must put routing fields into application properties. If you came from BizTalk, this is the same idea as promoted properties on the MessageBox.

Topics need Standard or Premium tier. Basic has queues only.

What they're probing: that you know filters work on properties, and that adding a new consumer means adding a subscription, not changing the publisher.

Q4What are Service Bus sessions, and when do you need them?

Short answer. Sessions give you ordered, exclusive processing for a group of related messages that share a SessionId. You get order per key while still processing many keys in parallel.

A receiver locks one session and gets all its messages in FIFO order. Other receivers work on other sessions at the same time. So all updates for patient 123 apply in order, while patient 456 is handled by another worker.

Sessions also have session state. You can store a small blob of progress on the session itself, which helps with aggregation or convoy patterns, like "collect all 5 parts, then release."

  • You must enable sessions when you create the queue or subscription. You can't switch it on later.
  • Every message must then carry a SessionId.
  • One hot key limits throughput for that key. One stuck message blocks that session until it's settled or dead-lettered.

In Logic Apps Standard, the Service Bus built-in trigger supports sessions, which is how you build the sequential convoy pattern.

What they're probing: that ordering is per key, not global, and that you know the cost of a stuck session.

Q5What is the dead-letter queue? What sends messages there, and how do you reprocess them?

Short answer. The DLQ is a sub-queue for messages that couldn't be delivered or processed. It never empties itself. Someone has to watch it, fix the cause, and resubmit.

Messages land in the DLQ when:

  • Delivery count passes MaxDeliveryCount (default 10). This is your poison message.
  • The message TTL expires and dead-lettering on expiration is turned on. If it's off, expired messages just disappear.
  • Your code explicitly dead-letters it with a reason, for example a validation failure.
  • A subscription filter throws an error, or a forward fails, when those options are enabled.

Each dead-lettered message carries DeadLetterReason and DeadLetterErrorDescription. Group by those first. Fix the root cause. Then resubmit to the main queue with Service Bus Explorer in the portal, or a small replay Function. Your consumer must be idempotent before you replay anything.

Never build an automatic loop that pushes DLQ messages straight back. A true poison message will just cycle forever.

What they're probing: whether you've actually run this in production. Mention alerting on the dead-lettered message count metric.

Q6Logic Apps vs Azure Functions. How do you decide which one owns a piece of logic?

Short answer. Logic Apps orchestrate and connect. Functions compute. Most good designs use both: the workflow owns the flow, and Functions own the heavy logic.

Pick Logic Apps when the work is mostly "call A, check the result, call B, handle errors." You get connectors, retry policies, run history your support team can read, and B2B/EDI support.

Pick Functions when the work is real code: parsing HL7, complex transforms, custom libraries, high-throughput processing, or anything you want to unit test properly.

A simple test: if you'd need 40 actions full of string expressions to do something, it belongs in code. Logic Apps Standard makes the line softer. It can run inline JavaScript, C# scripts, and local .NET functions from inside the workflow.

What they're probing: judgment. Say where you draw the line and why, with a real example.

Q7What are the APIM policy scopes, and how does inheritance work?

Short answer. Global, workspace, product, API, operation. The most specific scope's policy runs, and the <base /> tag decides where the parent scope's policy runs inside it.

Each policy has four sections: inbound, backend, outbound, and on-error.

<inbound>
  <base />
  <rate-limit-by-key calls="100" renewal-period="60"
      counter-key="@(context.Subscription.Id)" />
</inbound>

Put your policy after <base /> and the parent runs first. Put it before and yours runs first. Delete <base /> and the parent policy is skipped at that scope.

That last one is a real security bug. If validate-jwt lives at global scope and someone removes <base /> on one operation, that operation is now open.

What they're probing: whether you understand <base /> and policy order, not just the list of scopes.

Q8Explain Durable Functions. When would you use them instead of a Logic App?

Short answer. Durable Functions are code-first stateful workflows. Use them when the orchestration is complex, owned by developers, and should be tested as code.

  • Client function starts an orchestration.
  • Orchestrator defines the steps. Its state is saved to storage and rebuilt by replaying history.
  • Activity functions do the actual work.
  • Entities hold small bits of durable state.

Common patterns: chaining, fan-out/fan-in, async HTTP APIs with a built-in status endpoint, monitors, and waiting for a human approval with a timeout.

The catch is replay. The orchestrator re-runs from the start many times, so it must be deterministic. No DateTime.Now, no random numbers, no direct I/O. Use context.CurrentUtcDateTime and push all I/O into activities.

Choose Durable over Logic Apps for dynamic fan-out across thousands of items, heavy branching logic, or when you want full unit tests. Choose Logic Apps when it's connector-heavy and your operations team needs to read run history.

What they're probing: replay and the determinism rules. That's the part people get burned by.

Design and patterns

This is where architect rounds are won. They want trade-offs, not feature lists.

Q9How do you guarantee idempotency in an integration flow?

Short answer. Assume every message arrives at least twice. Give each business operation a stable key, and make the second delivery harmless.

  • Stable key. Use a business ID, like prescription ID plus version. Set it as the Service Bus MessageId.
  • Duplicate detection. Service Bus (Standard and Premium) drops messages with the same MessageId inside a time window. This only catches the sender retrying. It doesn't help if your consumer processes a message and then crashes before completing it.
  • Idempotent receiver. Record processed keys in a table with a unique constraint. Insert the key in the same transaction as the side effect when you can.
  • Safe operations. Prefer upserts and "set status to Shipped" over "add 1 to count."
  • Downstream APIs. Send an Idempotency-Key header when the API supports it.

Watch the check-then-act race. Two workers can both check "not processed" at the same time. The unique constraint is what actually saves you.

What they're probing: that you understand at-least-once delivery and know duplicate detection alone isn't enough.

Q10How do you handle message ordering when consumers scale out?

Short answer. You can't have global order and full parallelism at the same time. Pick an ordering key and keep order per key. Better still, design so order doesn't matter.

  • Service Bus sessions. Set SessionId to the order or patient ID. Order per key, parallel across keys.
  • Event Hubs partition key. Events with the same key go to the same partition and stay in order there.
  • Resequencer. If the source can't guarantee order, carry a sequence number and buffer until the gap fills.
  • Version-aware consumers. Carry a version or timestamp. The consumer ignores anything older than what it already has. This is often the simplest and most robust answer.

One trap: setting Logic Apps trigger concurrency to 1 does give you order, but it serializes everything. Throughput collapses.

What they're probing: whether you know the trade-off and can name more than one way out.

Q11Explain claim-check, competing consumers, and publish-subscribe. Where have you used them?

Short answer. Claim-check keeps big payloads out of the broker. Competing consumers scale out processing. Publish-subscribe lets you add consumers without touching the sender.

  • Claim-check. Store the payload in Blob, send only a reference. This avoids message size limits and keeps sensitive data like PHI out of the broker and its logs.
  • Competing consumers. Many workers read one queue. Peek-lock makes sure each message is processed by one worker at a time. Scale workers on queue depth.
  • Publish-subscribe. One topic, many subscriptions. A new audit or reporting consumer is just a new subscription.

Have one real story ready for each. For example, one prescription event fanned out to pharmacy routing, audit, and a state PDMP feed, each on its own subscription.

What they're probing: real use, not textbook definitions.

Q12How do you design retries without creating duplicates downstream?

Short answer. Retry only transient failures. Back off with jitter. Cap the attempts. And make the call idempotent, because a timeout doesn't tell you whether the first call worked.

Retries hide in many layers: the SDK, the Logic Apps action retry policy (exponential, 4 retries by default), the APIM retry policy, and Service Bus redelivery. Stack three of them and one failure can turn into 64 calls. Pick one layer to own retries and turn the others down.

  • Retry: timeouts, 408, 429 (honor Retry-After), 500, 502, 503, 504.
  • Don't retry: 400, 401, 403, 404, 422. Fail fast and send to an error path.
  • Circuit breaker: if a dependency is clearly down, stop hammering it. APIM backends support a circuit breaker rule.

The subtle part is the timeout. The backend may have committed the change and failed to answer. That's exactly why the retry must carry the same idempotency key.

What they're probing: retry storms and the timeout ambiguity. Say both.

Q13Synchronous vs asynchronous integration. How do you decide, and how does the caller get the result for async calls?

Short answer. Go synchronous when the caller needs the answer to continue and the work is fast. Otherwise accept the request, queue it, and return 202 with a status URL.

Sync is simpler, but it couples the caller to your slowest dependency. Gateways and load balancers also have hard timeouts, often a couple of minutes, so long work over sync HTTP will eventually fail in a confusing way.

For async, you have three ways to hand back the result: polling a status URL (shown above), a callback webhook the caller registers, or an event the caller subscribes to. Durable Functions give you the polling pattern out of the box.

What they're probing: whether you know the 202 pattern by name and can explain timeouts.

Q14How do you version APIs in APIM without breaking existing consumers?

Short answer. Versions for breaking changes, revisions for non-breaking ones. Keep old versions running until traffic shows nobody uses them.

  • Versions live in a version set. The scheme is path (/v2/orders), header (Api-Version: 2), or query string (?api-version=2). Path is the most visible and easiest to route and cache.
  • Revisions let you change an API safely. You test the new revision on its own URL (;rev=3), then make it current with a change log entry. Consumers see no URL change.

What counts as non-breaking: adding optional fields or new operations. Renaming, removing, or changing a field's type is breaking.

Retiring a version is a process. Announce it, send a deprecation or sunset header, watch calls per version in APIM analytics, and contact the teams still calling it. Only then turn it off.

What they're probing: versions vs revisions, and a sane deprecation process.

Security and networking

Architect panels go deep here, especially on DNS and private endpoints. Rehearse these out loud.

Q15How do you make sure a backend only accepts traffic from APIM?

Short answer. Lock the network first, then check identity. Never rely on the subscription key or a shared secret header alone.

  1. Network. Put APIM in a VNet. Give the backend a private endpoint, or access restrictions that only allow APIM's subnet. Turn off public access on the backend.
  2. Identity. APIM calls the backend with its managed identity using the authentication-managed-identity policy. The backend validates the token: right audience, and the caller is APIM's identity.
  3. Optional mTLS. APIM presents a client certificate with authentication-certificate, and the backend checks it.

Why not a secret header? It's static, it leaks into logs and config, and rotating it means touching both sides at once. A managed identity token expires on its own and has no secret to manage.

What they're probing: defense in depth. Two independent controls, network and identity.

Q16Walk through validate-jwt in APIM. What do you check and why?

Short answer. Is the token real (signature), meant for this API (audience), from someone we trust (issuer), still valid (expiry), and allowed to do this (roles or scopes)?

<validate-jwt header-name="Authorization" require-scheme="Bearer"
    failed-validation-httpcode="401">
  <openid-config url="https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration" />
  <audiences><audience>api://prescription-api</audience></audiences>
  <issuers><issuer>https://login.microsoftonline.com/{tenant-id}/v2.0</issuer></issuers>
  <required-claims>
    <claim name="roles" match="any"><value>Prescriptions.Write</value></claim>
  </required-claims>
</validate-jwt>
  • openid-config pulls the signing keys. Key rotation is handled for you.
  • Audience stops a token issued for another API from being replayed against yours.
  • Issuer must match the token version. v1 tokens use https://sts.windows.net/{tenant-id}/. v2 tokens use https://login.microsoftonline.com/{tenant-id}/v2.0. The app registration's accessTokenAcceptedVersion decides which you get. A mismatch here is the most common 401 in real projects.
  • roles vs scp. App-to-app calls (client credentials) carry roles. Calls on behalf of a user carry scp. Check the one that matches your flow.

Also worth knowing: validate-azure-ad-token is a simpler Entra-specific policy. For multi-tenant APIs, check the tid claim against an allow-list.

What they're probing: the v1/v2 issuer trap and roles vs scp. Those separate people who've done it from people who've read about it.

Q17Managed identity vs service principal vs Key Vault secrets. When do you use each?

Short answer. Managed identity for anything in Azure calling Azure. Federated credentials for pipelines and workloads outside Azure. Key Vault only for secrets you can't get rid of.

  • System-assigned managed identity lives and dies with the resource. Simple, one per resource.
  • User-assigned managed identity is created separately. You can grant its RBAC before the app exists, share it across instances, and it survives redeploys.
  • Service principal with a secret or cert is the older way, for systems outside Azure. For GitHub Actions and similar, use workload identity federation (OIDC) instead. No secret to store or rotate.
  • Key Vault is for things only a secret can unlock: a partner's API key, SFTP credentials, a certificate. Read it with a managed identity, often through Key Vault references in app settings.

Grant the narrowest role. Use Azure Service Bus Data Sender or Data Receiver, not Owner. Then disable local (SAS key) auth on the namespace so the keys can't be used at all.

What they're probing: "no secrets" as a design goal, and least-privilege data-plane roles.

Q18How do private endpoints and VNet integration work for Logic Apps Standard and Service Bus? What breaks with DNS?

Short answer. A private endpoint gives a service a private IP inside your VNet. It only works if DNS turns the service's normal name into that private IP. Most private endpoint problems are DNS problems.

How it fits together. Public DNS already points the service name at a privatelink name. If your VNet is linked to a private DNS zone for that privatelink name, the lookup returns the private IP. If not, it returns the public IP, and with public access off, the call fails.

  • Create the private endpoint and attach a DNS zone group, so the A record is created for you.
  • Link the private DNS zone to every VNet that must resolve it. In hub-spoke, keep the zones central in the hub and link spokes to them.
  • On-premises clients need a conditional forwarder to an Azure DNS Private Resolver inbound endpoint.
  • If your VNet uses custom DNS servers, they must forward to Azure DNS (168.63.129.16), or the private zone is never consulted.

Logic Apps Standard specifics. Two separate directions:

  • Outbound (the app calling private things): VNet integration into a subnet delegated to Microsoft.Web/serverFarms.
  • Inbound (callers reaching Request triggers privately): a private endpoint on the Logic App.

The classic failure: the Logic App's own storage account. If you lock it down, it needs private endpoints for blob, queue, table, and file, each with its DNS zone. Miss one and the runtime can't start, and the error message won't say "DNS."

Debug checklist. Run nslookup sb-orders.servicebus.windows.net from inside the VNet (Kudu console works). A 10.x answer is good. A public IP means the zone isn't linked or DNS isn't forwarding.

What they're probing: that you can explain the CNAME-to-privatelink chain and troubleshoot it, not just "we used private endpoints."

Q19APIM Internal vs External VNet mode. What does Application Gateway add?

Short answer. External: the gateway has a public IP and can reach backends in the VNet. Internal: the gateway has only a private IP. For public traffic, put Application Gateway with WAF in front of it.

Application Gateway gives you three things APIM alone doesn't: a WAF, one controlled public entry point, and path rules. You can expose only /external/* to the internet and keep internal APIs reachable only from the VNet and on-premises.

Things that trip people up with Internal mode:

  • DNS. The gateway, developer portal, and management hostnames need private DNS records, or custom domains that resolve to the private IP.
  • NSG rules. APIM's management traffic must be allowed in (port 3443 from the ApiManagement service tag).
  • Health probe. Point Application Gateway's probe at APIM's /status-0123456789abcdef endpoint.

Tier matters. Classic VNet injection is Developer and Premium. The v2 tiers use a different model (outbound VNet integration, inbound private endpoints), so confirm the tier before you design.

What they're probing: why App Gateway is there, and whether you've dealt with the DNS and NSG details.

Operations and DevOps

They want to know you can run this thing, not just draw it.

Q20How do you deploy Logic Apps, APIM, and Service Bus through CI/CD across environments?

Short answer. Everything is code. Infrastructure through IaC, workflows and policies from source control, environment differences through parameters only. Build once, deploy the same artifact everywhere.

What they're probing: build once, promote many, and how you handle per-environment values without editing workflow files.

Q21How do you trace one request end to end across APIM, Logic Apps, Service Bus, and Functions?

Short answer. Create one correlation ID at the front door and carry it through every hop: HTTP header, message property, log field. Send all telemetry to one Application Insights and query by that ID.

  • APIM. Set the header if the caller didn't send one: <set-header name="x-correlation-id" exists-action="skip"> with @(context.RequestId.ToString()). Turn on the Application Insights diagnostic.
  • Logic Apps. The x-ms-client-tracking-id header becomes the run's tracking ID. Add tracked properties for business keys.
  • Service Bus. Put the ID in CorrelationId or an application property. The Azure SDKs also pass W3C trace context automatically.
  • Functions. Read the ID and add it to the logging scope so every log line carries it.
union requests, dependencies, traces, exceptions
| where timestamp > ago(1d)
| where customDimensions has "c0ffee-1234"
| order by timestamp asc

In healthcare, keep PHI out of tracked properties and custom dimensions. Log IDs, not names or member data.

What they're probing: a concrete mechanism at each hop. "We used App Insights" isn't an answer.

Scenarios

Talk through these like a design session. State assumptions, ask one or two questions, then commit to a design.

Q22A client has 200 BizTalk orchestrations, maps, and custom pipelines. How do you migrate them to Azure?

Short answer. Don't migrate 200 things one by one. Inventory everything, retire what's dead, group the rest by pattern, build the shared platform first, then move in waves with parallel runs.

  1. Inventory. Applications, ports, adapters, maps, pipelines, orchestrations, BRE policies, BAM, bindings, and real traffic volumes from the tracking database. Use an assessment tool to export it, then verify by hand.
  2. Retire. Anything with no traffic in 12 months is a candidate to switch off. In most estates a real chunk is dead.
  3. Classify. Simple routing, transform-and-send, long-running orchestration, B2B/EDI. Each class gets one target pattern, not 200 custom designs.
  4. Build the platform first. Landing zone, networking, CI/CD, logging, and a standard error-handling framework. Every wave reuses it.
  5. Migrate in waves. Start low-risk but representative. Run old and new in parallel, compare outputs, cut over per partner or per interface.
  6. Decommission BizTalk hosts as each wave clears.

For the "why now" context: BizTalk Server 2020 is the last release, and its support ends in 2030.

What they're probing: program thinking. Inventory, patterns, platform, waves, parallel run. With your BizTalk history, tell this as a story you lived.

Q23A partner sends 10x normal volume at month-end and your backend falls over. What do you change?

Short answer. Protect the backend first, then absorb the burst. Throttle at APIM, buffer in a queue, and let workers pull at the rate the backend can actually handle.

Right now: add rate-limit-by-key or quota-by-key per partner in APIM, returning 429 with Retry-After. Then call the partner and agree on a rate.

Structural fix:

  • Accept the request, validate it, put it on a queue, return 202. The caller is decoupled from the backend.
  • Cap worker concurrency to what the backend can take: Functions maxConcurrentCalls, Logic Apps trigger concurrency, or KEDA on AKS scaling on queue length with a max replica count.
  • If APIM itself saturates, add units or autoscale on the capacity metric. If Service Bus throttles, move to Premium messaging units.
  • Cache read-heavy calls with cache-lookup and cache-store.
  • Month-end is predictable. Pre-scale on a schedule and load test before it happens.

The key point: you often can't scale the backend. A legacy database has a ceiling. The queue lets you accept at burst speed and process at backend speed.

What they're probing: load leveling, and that you protect the weakest component instead of scaling everything.

Q24Orders have been piling up in a dead-letter queue for two days and nobody noticed. What do you do now, and how do you prevent it?

Short answer. Stop the bleeding, find the cause, replay safely, then make it impossible to miss again.

Now:

  1. Check if it's still happening. If every new message fails, fix or pause the consumer before anything else.
  2. Sample the DLQ and group by DeadLetterReason. Usually one or two causes explain most of it: a schema change, expired credentials, a downstream outage.
  3. Fix the root cause and deploy.
  4. Confirm the consumer is idempotent. Some of these may have partly processed.
  5. Replay in small batches and watch. Messages with genuinely bad data go to a repair queue for the business team, not back into the flow.
  6. Tell the business what's delayed and by how much. Two days of orders is a customer issue, not just a technical one.

Prevent:

  • Azure Monitor alert on the dead-lettered message count metric, split by entity name, firing when it's above zero. Route it to on-call, not a mailbox nobody reads.
  • A DLQ handler that logs, classifies, and notifies with the reason attached.
  • An alert on message age or active message count, so a stuck consumer shows up even when nothing dead-letters.
  • Turn on dead-lettering on expiration, so expired messages are kept rather than silently dropped.
  • A written replay runbook, and a synthetic heartbeat message that flows end to end every few minutes.

Finish with a blameless postmortem. The real failure was monitoring, not the message.

What they're probing: calm incident handling, business awareness, and whether your prevention is concrete.

Q25A new partner sends HL7 v2 or X12 over SFTP. Your internal systems expect FHIR JSON over REST. Design it end to end.

Short answer. Land the file untouched, validate and acknowledge fast, convert to a canonical model, map to FHIR, and deliver through a queue. Lock down PHI at every hop.

Ingest. Use SFTP on Blob storage with local users and SSH keys, plus an IP allow-list. Keep the raw file untouched in its own container for audit. BlobCreated fires Event Grid, which starts the workflow. The file stays in Blob, and messages carry references (claim-check).

Validate and acknowledge.

  • X12: Integration Account with the partner and agreement. X12 decode validates envelopes and produces the 999 and TA1 acks.
  • HL7 v2: parse in a Function with a proven library (NHapi in .NET), or the built-in HL7 support if your setup has it. Return an HL7 ACK.

Canonical, then FHIR. Split the batch into one message per transaction in a canonical model, onto a Service Bus topic. A Function maps to FHIR. For HL7 v2, the FHIR service in Azure Health Data Services has a $convert-data operation with Liquid templates you can customize. Validate the result against your FHIR profiles before you post it.

Errors, three kinds:

  • Syntax errors: reject the file and send a negative ack.
  • Business errors: quarantine the transaction and notify the partner or support team.
  • Transient errors: retry, then dead-letter.

Use the standard control numbers as idempotency keys: ISA13, GS06, and ST02 for X12, and MSH-10 for HL7. A resent file then can't create duplicates.

PHI. Private endpoints everywhere. Managed identity and RBAC. Encryption at rest, with customer-managed keys if policy requires. TLS 1.2 or later. Turn on secure inputs and outputs in Logic Apps so PHI doesn't land in run history. Keep PHI out of logs and tracked properties. Set retention and purge rules. And have a BAA in place with Microsoft.

Onboarding. Drive partner differences from config: IDs, formats, mapping version, contacts. Partner number 12 should be a config change, not new code.

What they're probing: healthcare depth (acks, control numbers, PHI in run history) on top of good integration design. This is home ground for you, so use real examples from your pharmacy work.

Reliability, routing, and platform choices

Added from the carousel review. These fill the gaps: failure handling, B2B, and choosing the right tier or plan.

Q26Explain the Saga pattern. How do you handle a transaction that spans several services?

Short answer. A saga replaces one big distributed transaction with a chain of local transactions. Each step has a compensating action. If a later step fails, you run the compensations in reverse to undo what already happened.

There are two styles:

  • Orchestration. One coordinator (a Durable Functions orchestrator or a Logic App) calls each step and decides what to undo. Easier to follow, test, and support. This is the usual answer.
  • Choreography. Each service reacts to events from the previous one, usually over Service Bus. No central brain, but the flow is hard to see once there are more than three or four steps.

In Durable Functions, the orchestrator wraps the steps in try/catch. The catch block calls compensating activities in reverse order. Its state survives restarts because it's replayed from history.

Three things people forget:

  • Compensations are business undo, not a rollback. You issue a refund; you don't delete the payment row.
  • Compensations can fail too, so they need retries and must be idempotent.
  • There's no isolation. Other systems can see the half-done state, so use explicit statuses like Pending until the saga finishes.

What they're probing: orchestration vs choreography, and whether you know compensation is a business action. Tie it back to BizTalk: this is what replaces atomic scopes and MSDTC.

Q27How do you handle errors inside a Logic App workflow?

Short answer. Retry policies for transient errors on each action. Scopes with run-after settings for try/catch/finally. And a Terminate action in the catch, so a handled failure still shows as Failed.

  • Retry policy. Per action: none, fixed, or exponential. The default is exponential with 4 retries. Turn it down where another layer already retries.
  • Run-after. Every action runs after the previous one's status: Succeeded, Failed, Skipped, or TimedOut. A Catch scope runs after Try is Failed or TimedOut. A Finally scope runs after Catch in any status.
  • Find what failed. Inside Catch, use result('Try') and filter for items where status is Failed. That gives you the action name and error for logging.
  • Terminate. End the Catch with Terminate set to Failed. Otherwise the run shows as Succeeded because the error was "handled," and your failed-runs alert never fires.
"Catch": {
  "type": "Scope",
  "runAfter": { "Try": [ "Failed", "TimedOut" ] },
  "actions": { ... }
}

For Service Bus triggers, decide what the catch does with the message: dead-letter it with a reason, or abandon it so it's retried. Don't just complete it and lose it.

What they're probing: the Terminate gotcha, and result() for getting the real error out of a scope.

Q28How do you implement content-based routing and message transformation?

Short answer. Route at the broker on message properties when you can, in the workflow when you must read the body. Transform with the lightest tool that fits: Liquid for JSON, XSLT for XML, a Function for anything complex.

Routing options:

WhereHowUse when
Service Bus subscriptionsSQL or correlation filters on propertiesMany consumers, routing on known fields. Most decoupled.
Logic AppsCondition or Switch on body contentRouting needs fields deep inside the payload
APIMset-backend-service on header, path, or claimEdge routing of API calls, like per-tenant backends

Broker filters can't read the body. If routing depends on a body field, have the publisher copy it into an application property. That keeps routing at the broker and the consumers ignorant of each other.

Transformation options:

What they're probing: that you pick the tool by payload type and complexity. For you, this is BizTalk maps and promoted properties in new clothes.

Q29What is an Integration Account, and when do you need one?

Short answer. It's the store for B2B and enterprise integration artifacts: schemas, maps, trading partners, agreements, and certificates. You need it for EDI trading partner work, and on Consumption for XML validation and maps.

What it holds:

  • Schemas (XSD) and maps (XSLT, Liquid)
  • Trading partners and their identities (like ISA qualifiers)
  • Agreements for X12, EDIFACT, and AS2: envelopes, validation rules, acknowledgment settings
  • Certificates for AS2 signing and encryption, and batch configurations

Consumption vs Standard. A Consumption Logic App must link to an Integration Account (in the same region) to use schemas, maps, or B2B actions. Logic Apps Standard can keep schemas and maps inside the project itself, so plain XML validation and transforms don't need one. For partners and agreements, you still use an Integration Account.

Tiers. Free is for dev only, with no SLA. Basic covers message handling. Standard covers full B2B. It bills per hour whether you use it or not, so don't create one "just in case."

What they're probing: when you actually need one. The Standard-without-an-Integration-Account point shows you're current.

Q31Event Grid: CloudEvents vs the native schema, and what is an Event Domain?

Short answer. Use CloudEvents 1.0 for new designs. It's the open CNCF standard and works across vendors. An Event Domain is one endpoint that manages thousands of topics, usually one per tenant, with separate access control on each.

Native Event Grid schemaCloudEvents 1.0
id, topic, subject, eventType, eventTime, data, dataVersionid, source, type, subject, time, specversion, data
Azure-specific. Older tooling assumes it.Vendor-neutral. SDKs in every major language.

You pick the input schema when you create the topic. Conversion between schemas only works in some directions, so decide up front.

Event Domains suit a multi-tenant platform. You publish to one endpoint and set the topic per event, like tenant-042. Each tenant subscribes only to their own topic, controlled with RBAC. One domain holds up to 100,000 topics.

Related details worth knowing:

  • Delivery is at-least-once with retries for up to 24 hours. Turn on dead-lettering to Blob, or failed events are dropped.
  • Filter by event type, subject prefix or suffix, and advanced filters on data fields.
  • Webhook endpoints must pass a validation handshake before they receive events.
  • Event Grid namespaces are the newer model. They add pull delivery and MQTT, using CloudEvents.

What they're probing: schema choice and multi-tenant design. Mentioning dead-letter-to-Blob shows you've run it.

Q32How do you implement a circuit breaker in an Azure integration solution?

Short answer. In .NET code, use Polly v8 through Microsoft.Extensions.Http.Resilience. At the gateway, use APIM's backend circuit breaker. For queue consumers, pause receiving while the breaker is open.

In code. The standard handler gives you rate limiting, timeouts, retry, and a circuit breaker in a sensible order:

builder.Services.AddHttpClient<PharmacyClient>()
    .AddStandardResilienceHandler(o =>
    {
        o.CircuitBreaker.FailureRatio = 0.5;
        o.CircuitBreaker.MinimumThroughput = 20;
        o.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(30);
    });

Older articles show CircuitBreakerPolicy. That's the Polly v7 API. Say v8 resilience pipelines in an interview.

At the gateway. APIM backends can carry a circuit breaker rule: trip after N failures (or specific status codes) in a time window, for a set duration, and honor Retry-After. It's configured on the backend resource through Bicep, Terraform, or the API, not in policy XML. Combine it with backend pools to fail over to a second backend.

For queue consumers, the key insight. If the downstream is down and the consumer keeps pulling, every message fails 10 times and dead-letters. You've turned an outage into a DLQ cleanup job. When the breaker opens, stop the processor. Messages wait safely in the queue. Resume when a probe succeeds.

What they're probing: the three states, current tooling, and the queue-consumer point. That last one is the senior answer.

Q33On-premises data gateway vs VNet integration vs Hybrid Connections vs ExpressRoute. How do you choose?

Short answer. They work at different layers. The gateway and Hybrid Connections are app-level tunnels to specific on-prem systems. VNet integration puts your app's traffic into your network. ExpressRoute or VPN is what connects that network to on-premises.

OptionWhat it isPick it when
On-premises data gatewayAgent on-prem that connects outbound to Azure. Used by managed connectors (SQL, File System, SAP, Oracle).Consumption Logic Apps, Power Platform, or no network link to on-prem yet. Run it as a cluster for HA.
VNet integrationThe app's outbound traffic goes through your VNet. Built-in connectors then reach private IPs directly.Enterprise platforms on Logic Apps Standard, Functions Premium or Flex, App Service. Needs a network link to on-prem.
Hybrid ConnectionsApp Service feature over Azure Relay. One TCP host and port per connection.A quick path from App Service or Functions to one or two on-prem endpoints, no VPN.
ExpressRoute (or site-to-site VPN)The network link itself: a private circuit (or encrypted tunnel) between on-prem and your VNets.Always the foundation for serious hybrid work. VPN is cheaper; ExpressRoute is private, faster, more predictable.

A typical enterprise answer: hub-spoke VNets, ExpressRoute into the hub, Logic Apps Standard and Functions with VNet integration in spokes, and DNS forwarding both ways. The gateway stays for the few managed connectors that need it, like SAP.

One more option to know: Logic Apps Standard has a hybrid deployment model that runs workflows on your own Kubernetes through Azure Arc. That's for when the data can't leave the site at all.

What they're probing: that you see these as layers, not four competing products. Say "VNet integration needs ExpressRoute or VPN to reach on-prem." Many candidates miss that.

Q34Azure Functions hosting plans: which one, and how do you handle cold start?

Short answer. Flex Consumption is the default choice for new serverless work: it scales to zero, supports VNet integration, and has always-ready instances for cold start. Premium for steady heavy load. Dedicated when you already pay for an App Service plan.

PlanScaleVNetCold startFits
ConsumptionTo zeroNoYesLight, bursty, non-critical work. Short timeouts (10 min max).
Flex ConsumptionTo zero, fast, per functionYesAvoidable with always-ready instancesMost new serverless integration work
Premium (Elastic)Min 1, elastic upYesReduced by pre-warmed instancesSteady volume, long runs, bigger instances
Dedicated (App Service)Manual or autoscaleYesNone with Always OnSpare capacity on an existing plan, predictable cost

Microsoft is steering new Linux serverless work to Flex Consumption. Check the current status of the Linux Consumption plan before you pick it.

Cold start: does it matter? For a Service Bus-triggered background worker, a few seconds usually doesn't. For a synchronous HTTP API behind APIM, it does.

  • Use always-ready instances (Flex), minimum instances (Premium), or Always On (Dedicated).
  • Keep startup light: lazy-load heavy clients, trim dependencies, and use ReadyToRun for .NET isolated.
  • Remember HTTP triggers are still capped at about 230 seconds by the front-end, whatever the plan's timeout is.

"Keep-warm pings" appear in older articles. They're a workaround, not a design. Mention them only to say why you don't need them anymore.

What they're probing: whether you know Flex Consumption exists, and whether you match the plan to the trigger type.

Q35Explain at-most-once, at-least-once, and exactly-once delivery. Where does Azure land?

Short answer. Azure messaging is at-least-once by default. Exactly-once isn't a platform guarantee. You get exactly-once processing by pairing at-least-once delivery with idempotent consumers.

SemanticsWhere you see itRisk
At-most-onceService Bus ReceiveAndDelete. Fire-and-forget telemetry.Loss on any crash
At-least-onceService Bus PeekLock, Event Grid, Event Hubs replay from the last checkpointDuplicates
Exactly-once processingAt-least-once plus an idempotent consumerOnly as good as your idempotency design

Details that show depth:

  • Lock duration. If processing takes longer than the lock, the message is redelivered while you're still working on it. Renew the lock, or keep processing short.
  • Event Hubs checkpoints. If you checkpoint every 100 events and crash at 99, those 99 come again.
  • Service Bus transactions. You can complete an incoming message and send an outgoing one atomically inside the same namespace. That's exactly-once across broker operations, but it doesn't cover your database.

The practical line to say: "I design every consumer assuming redelivery will happen."

What they're probing: that you don't claim exactly-once delivery, and that you know which knob (receive mode) controls the trade-off. Links straight to Q9.

Bonus scenarios to practice without notes: "A downstream system is down for 6 hours. What happens to in-flight messages?" and "Cut this platform's Azure bill by 30 percent."
