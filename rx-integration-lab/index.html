Rx Integration Lab: FHIR to NCPDP on Azure Integration Services

A read-through lab. You won't click anything. You'll walk one prescription through APIM, Logic Apps, Service Bus, Functions and Event Grid, and learn why each piece sits where it does.

The story in one breath.

An EHR sends a FHIR prescription. APIM checks who is calling. A Logic App accepts it and drops it on Service Bus so nothing gets lost. A second Logic App picks it up, transforms it to NCPDP NewRx with help from a Function, and sends it to the pharmacy through the Surescripts network. Event Grid then tells everyone who cares that it happened.

Payloads are simplified on purpose. The goal is the platform: reliability, security, transforms, events, deployment and troubleshooting. That's what integration architect interviews test.

1. The problem

A health system runs an EHR. Doctors write prescriptions there. The EHR speaks FHIR R4 (JSON, a MedicationRequest resource). Pharmacies, through the Surescripts network, speak NCPDP SCRIPT 2017071 (XML, a NewRx message).

Someone has to sit in the middle. That's you.

3. Follow one prescription

Read this section twice. If you can retell it without looking, you can answer most architecture questions.

  1. EHR gets a token

    The EHR is an app registration in Entra ID. It uses the client credentials flow: client ID plus a certificate or secret, scope api://rx-intake/.default. Entra returns a JWT with aud, iss and a roles claim of Prescriptions.Write.

    Why: machine-to-machine call, no user present, so client credentials is the right flow.

  2. APIM checks the caller

    validate-jwt checks signature, issuer, audience and role. rate-limit-by-key stops one noisy EHR from hurting others. APIM adds x-correlation-id if the caller didn't send one.

    Why: bad requests die at the edge. The backend never sees them.

  3. APIM calls the intake workflow with its own identity

    The EHR's token stops at APIM. APIM gets a new token with its managed identity and calls wf-rx-intake.

    Why: the backend trusts APIM, not every EHR. Each hop has its own identity, so you can revoke one without breaking others.

  4. Intake validates and publishes

    A stateless workflow does a JSON schema check, then sends to topic rx-inbound. It sets MessageId to an ID for this specific command, like NewRx:RX-123 (stable if the same command is retried), keeps rxId as a separate property, sets CorrelationId to the header value, and an application property messageType = 'NewRx'. Then it returns 202 Accepted.

    Why stateless: it's short, and once the message is in Service Bus, durability is Service Bus's job. Stateless is faster and cheaper on storage.

  5. Service Bus holds and routes

    Duplicate detection drops a repeat of the same MessageId within the window. That's why the ID includes the message type: a CancelRx for RX-123 must not look like a repeat of its NewRx. Subscription sub-newrx has a SQL filter messageType = 'NewRx'. A CancelRx would go to a different subscription and workflow.

    Why: this is BizTalk's MessageBox pub/sub. Publisher doesn't know who processes.

  6. Transform workflow receives with peek-lock

    The message is locked, not deleted. If the workflow crashes, the lock expires and Service Bus redelivers it.

    Why: "at least once" delivery. You never lose a prescription. The cost is you must handle duplicates.

  7. Liquid map: FHIR to canonical

    A Liquid template turns FHIR JSON into your canonical data model (CDM). The CDM is flat and stable.

    Why a CDM: if a second EHR sends HL7 v2 tomorrow, you write one new map into the CDM. The NCPDP side doesn't change.

  8. Function validates and enriches

    The workflow calls func-rx-validate. It checks the prescriber NPI check digit and maps RxNorm to NDC.

    Why: real code, unit-testable, versioned in Git with tests.

  9. XSLT map: canonical to NCPDP

    The CDM JSON is converted to XML, then an XSLT map produces the NewRx message.

    Why XSLT: the target is XML with a strict schema. XSLT is the natural tool, and you already know it from BizTalk.

  10. Send to Surescripts

    HTTP POST to Surescripts with a client certificate pulled from Key Vault. Surescripts returns Status (it accepted the message for delivery) or Error. Surescripts then routes the NewRx to the right pharmacy using the NCPDP ID in the message: a retail store, or a mail-order pharmacy like OptumRx or CenterWell.

    Why one endpoint: you integrate once with the network, not with every pharmacy.

  11. Settle the message

    Success: Complete, and the message is gone. Business error (bad NPI): Dead-letter with a reason. Temporary error (Surescripts 503): Abandon so it's retried.

    Why explicit: in BizTalk the engine did this. Here you decide. Classify by the specific error, not just 4xx vs 5xx: a 429 is a 4xx but should be retried.

  12. Announce it

    Publish Rx.Sent to Event Grid. wf-rx-notify updates the EHR. func-rx-audit writes an audit record. Neither is known to the transform workflow.

APIM is a gateway plus a policy engine. Think of it as the only door into your integration platform.

The inbound policy

<inbound>
  <base />
  <!-- 1. Who are you? -->
  <validate-jwt header-name="Authorization" failed-validation-httpcode="401">
    <openid-config url="https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration" />
    <audiences><audience>api://rx-intake</audience></audiences>
    <required-claims>
      <claim name="roles" match="any"><value>Prescriptions.Write</value></claim>
    </required-claims>
  </validate-jwt>

  <!-- 2. Not too fast -->
  <rate-limit-by-key calls="100" renewal-period="60"
      counter-key="@(context.Subscription.Id)" />

  <!-- 3. Traceability: keep the caller's id, or create one -->
  <set-header name="x-correlation-id" exists-action="skip">
    <value>@(context.RequestId.ToString())</value>
  </set-header>

  <!-- 4. Call the backend as APIM, not as the EHR -->
  <authentication-managed-identity resource="api://la-rx-intake" />
  <set-backend-service backend-id="la-rx-intake" />
</inbound>

Read it top to bottom: identity, protection, traceability, forwarding. That order is the talking point.

Issuer gotchaThe access token version is controlled by the API's app registration, through requestedAccessTokenVersion in the manifest (older manifest format: accessTokenAcceptedVersion). null or 1 gives v1 tokens, 2 gives v2. It doesn't matter which token endpoint the client calls. v1 tokens have sts.windows.net/{tenant}/. v2 tokens have login.microsoftonline.com/{tenant}/v2.0. A mismatch gives a 401 that looks like "everything is right." You hit exactly this in your APIM lab.
How does APIM reach a Logic App HTTP trigger?By default, a Logic App Standard HTTP trigger is protected by a SAS signature in its callback URL (sig=...). Two options: store that URL in a Key Vault-backed named value, or enable App Service authentication (Easy Auth) on the Logic App and call it with APIM's managed identity. The second is cleaner because there's no shared secret to rotate. That's the one shown above.

The APIM object model

API (with operations) sits in one or more products. A subscription gives a consumer a key for a product or API. Policies run in four sections: inbound (before the backend), backend (the forward call), outbound (shape the response) and on-error (anything that failed).

Subscription key vs OAuth: don't mix them up

MechanismAnswersUse it for
OAuth 2.0 / JWTWho is calling, and are they allowed?Authentication and authorization
APIM subscription keyWhich consumer or plan is this?Optional: per-consumer quotas, analytics, access plans

If an interviewer asks "why both?", a good answer is: OAuth is the security control. The subscription key is optional, for usage tracking and plans. If you don't need keys, use an open product and rate-limit on a token claim instead:

<rate-limit-by-key calls="100" renewal-period="60"
  counter-key="@(context.Request.Headers.GetValueOrDefault("Authorization","").AsJwt()?.Claims.GetValueOrDefault("azp", "unknown"))" />

azp is the calling app's ID in v2 tokens. In v1 tokens it's appid.

Other APIM terms to know

TermMeaning
Rate limit vs quotaRate limit caps bursts over a short window (100 per minute). Quota caps total volume over a long period (100,000 per month).
Version vs revisionA version is a breaking change that callers opt into (/v2). A revision is a non-breaking change you test, then make current.
validate-contentChecks the request body against the API's schema at the gateway
rewrite-uri, set-backend-serviceChange the backend path or target without the caller knowing
OpenAPI importThe API contract drives operations and schemas
DiagnosticsAPIM logs to App Insights and Log Analytics

HTTP status codes you should explain without thinking

CodeMeaning in this designRetry?
202 AcceptedIntake took the prescription. Processing happens latern/a
400 Bad RequestMalformed JSON or schema failureNo, fix the request
401 UnauthorizedNo token, or token invalid (signature, issuer, audience, expired)Only with a new token
403 ForbiddenToken valid, but missing the required roleNo, fix permissions
404 Not FoundWrong path or API versionNo
409 ConflictConflicts with current state, like a duplicateUsually no
422 UnprocessableValid shape, bad business data (bad NPI)No
429 Too Many RequestsRate limit hitYes, after Retry-After

Why 202 and not 201? Nothing is created yet from the caller's point of view. 202 says "accepted for processing." Also: POST is not idempotent by nature, which is why the caller's retries need duplicate protection. PUT and DELETE are meant to be idempotent.

Policy scopes

Policies stack: global, product, API, operation. <base /> pulls in the outer scope. Put validate-jwt at API level so every operation gets it. Put rate limits at product level so each partner has its own limit.

The one-liner: Logic Apps Standard runs on the Azure Functions runtime. That explains almost everything else, including why you deploy it like a Function app.

Stateful vs stateless

Here's the BizTalk link your friend was pointing at. Stateful checkpointing is your dehydration. It's automatic. What's not automatic is the handoff between two workflows. That's what Service Bus is for.

Built-in vs managed connectors

Built-in connectors (Service Bus, HTTP, Blob, Event Hubs, SQL and more) run inside the Logic App process. They're faster, have no per-call throttling from a shared service, and use your VNet. Managed connectors run in shared Microsoft infrastructure, create an API connection resource, and have throttling limits.

Rule of thumb: use built-in when one exists. The Service Bus trigger here is built-in.

splitOn matters. The trigger can receive a batch. splitOn starts one run per message, so one bad prescription can't fail the others. It's called debatching.

The Catch scope wiring

"Catch": {
  "type": "Scope",
  "runAfter": { "Try": [ "Failed", "TimedOut" ] },
  "actions": { ... }
}

Microsoft docs use Failed and TimedOut. The Standard designer often writes them in capitals. You may see both.

Inside Catch, result('Try') gives you the status and error of every action in Try. You use it to decide abandon vs dead-letter, and to write a useful dead-letter reason.

Retry policies

Every HTTP-type action has a retry policy. Default is exponential, a few attempts. For the Surescripts call you might set 3 retries with exponential backoff. That handles a brief blip inside the run. If it still fails, Catch abandons the message and Service Bus handles the longer retry. Two retry layers, each for a different time scale.

Concurrency and scaling

Throughput questions come up often. Four controls to know:

  • Trigger concurrency limits how many runs execute at once. Too high can overwhelm Surescripts or hit its limits. Too low and the subscription backlog grows.
  • For each concurrency controls parallel iterations inside a run. Set it to 1 when order inside a loop matters.
  • splitOn creates independent runs per message.
  • Plan scale-out: Standard scales at the Workflow Standard plan level, adding instances under load.

Sessions deliberately reduce parallelism per session to keep order. That's a trade-off, not a free feature.

6. Service Bus

Service Bus is an enterprise message broker. It holds messages until someone is ready and able to process them.

Queue or topic?

QueueTopic + subscriptions
PatternPoint to point, competing consumersPublish/subscribe
ReceiversEach message goes to one receiverEach subscription gets its own copy
RoutingNoneSQL or correlation filters per subscription
Hererx-inbound, because NewRx, CancelRx and RxChange go to different workflows

A subscription behaves like its own queue. Each one has its own dead-letter queue.

The life of a message under peek-lock

Settings that matter, and why

SettingValue hereWhy
Lock duration1 to 5 minutes (5 is the max)Set it longer than normal processing. If a run can legitimately take longer, renew the lock (the built-in Service Bus connector has a renew-lock action). If the lock is still lost, redelivery happens, and idempotency protects you
Max delivery count5After 5 failed attempts, stop retrying and dead-letter it (poison message)
Duplicate detectionOn, 10 minute windowEHR retries after a timeout won't create two prescriptions. Must be set at creation
MessageIdType + business ID, e.g. NewRx:RX-123Duplicate detection compares only this, for the whole topic. Stable across retries of the same command, different for a different command. A random GUID per send would defeat it
Dead-letter on expirationOnExpired prescriptions are kept for review, not silently deleted
SessionsOptional, SessionId = prescription groupOrders related messages within one session-enabled queue or subscription. It does not coordinate across subscriptions. If NewRx and CancelRx must be ordered, they must flow through the same session-aware subscription, or you need explicit state checks
Local auth (SAS)DisabledForces Entra RBAC. No keys to leak
Duplicate detection is not idempotencyIt only catches repeats with the same MessageId inside the window. A redelivery after lock expiry is the same message delivered again, not a new send, so duplicate detection doesn't stop it. Your workflow still needs to be idempotent: for example, check an "already sent" record keyed by rxId before calling Surescripts.
The hardest case: the partner's answer is lostSurescripts accepts the NewRx, but your HTTP call times out before the response arrives. Did it succeed? You don't know. Retrying blindly may send it twice. The architect answer: Service Bus gives at-least-once delivery, not exactly-once. Use a partner-supported message ID so the partner can reject duplicates (NCPDP messages carry a MessageID). Where that isn't enough, query status or reconcile before resending. Never claim "exactly once" across a network boundary.

Tiers in one line each

Basic: queues only. Standard: topics, pay per operation, 256 KB messages, public endpoint. Premium: dedicated capacity, private endpoints, up to 100 MB messages, geo-DR. For healthcare in production, expect Premium because of private networking.

Handling the dead-letter queue

A DLQ nobody watches is just a slower way to lose data. Three things make it real:

  • An alert on dead-lettered message count above zero.
  • Clear DeadLetterReason and description, written by your Catch scope, like InvalidPrescriberNpi.
  • A replay path: a small workflow that reads the DLQ, lets an operator fix or approve, and resends to the topic.

7. Azure Functions

Functions are for the parts that are really code. The line is simple: Logic Apps orchestrate, Functions compute.

Fundamentals in five points

  • Trigger: what starts the function. HTTP, Service Bus, Timer, Event Grid, Blob and more. Exactly one per function.
  • Bindings: declarative input and output connections, like writing to a queue without client code.
  • Isolated worker model: your .NET code runs in its own process, separate from the host. It's the model going forward for .NET.
  • Hosting: Flex Consumption (serverless, scale to zero, VNet support), Premium (pre-warmed, no cold start), or Dedicated (App Service plan). Cold start is the delay when a scaled-to-zero app wakes up.
  • Configuration: app settings, Key Vault references and managed identity, exactly like Logic Apps Standard.

A Function can also do what a Logic App does: a Service Bus-triggered Function could process prescriptions. You'd choose that for very high throughput or complex code. You'd choose Logic Apps for visible orchestration, connectors and run history.

What goes in the Function here

  • NPI validation. The 10th digit is a Luhn check digit, calculated with the prefix 80840.
  • RxNorm to NDC lookup against a reference table.
  • Anything with loops, string math or unit tests.
// .NET 8 isolated worker
public class ValidateRx
{
    [Function("ValidateRx")]
    public async Task<IActionResult> Run(
        [HttpTrigger(AuthorizationLevel.Anonymous, "post")] HttpRequest req)
    {
        var rx = await req.ReadFromJsonAsync<CdmRx>();
        if (!IsValidNpi(rx.PrescriberNpi))
            return new UnprocessableEntityObjectResult(new { code = "InvalidPrescriberNpi" });

        rx.Ndc = await _drugCodes.LookupNdcAsync(rx.RxNormCode);
        return new OkObjectResult(rx);
    }

    static bool IsValidNpi(string npi)
    {
        if (npi is not { Length: 10 } || !npi.All(char.IsDigit)) return false;
        var s = "80840" + npi[..9];
        int sum = 0; bool dbl = true;
        for (int i = s.Length - 1; i >= 0; i--)
        {
            int d = s[i] - '0';
            if (dbl) { d *= 2; if (d > 9) d -= 9; }
            sum += d; dbl = !dbl;
        }
        return (10 - sum % 10) % 10 == npi[9] - '0';
    }
}
Why AuthorizationLevel.Anonymous?Because Easy Auth (App Service authentication) sits in front and rejects any call without a valid Entra token for this Function's audience. The Logic App calls it with its managed identity. That's stronger than a function key, which is a shared secret.
Why return 422 for a bad NPI?It's a business error, and a specific code lets the Catch scope decide. But don't classify by first digit alone. 422 (bad data): dead-letter, retrying won't help. 408, 429, 500, 502, 503, 504: transient, retry. 401, 403: configuration or security problem, alert and don't retry endlessly.

8. Event Grid

Event Grid delivers events: small notices that something happened. In the classic model used here (Event Grid Basic), it pushes them to subscribers. The newer namespace topics (Event Grid Standard) support pull delivery as well as push.

Events vs messages: the question you will get

Event Grid (event)Service Bus (message)
Meaning"This happened" (a fact)"Do this" or "here is the data" (a job)
Publisher expectsNothing. Doesn't care who listensThat someone processes it
DeliveryPush to endpoints (namespace topics can also pull)Pull by receivers
SizeSmall, a pointer to dataCarries the payload
Ordering, sessions, transactionsNoYes
Failure handlingRetries with backoff, then dead-letter to BlobLock, redelivery, DLQ
HereRx.Sent, Rx.FailedThe prescription itself

Rule of thumb, not law: the prescription itself belongs on Service Bus, and "it was sent" is usually cleaner on Event Grid. Service Bus topics can carry events too, when subscribers need sessions, ordering or transactions.

Topic types

The first three are Event Grid Basic. The last is Event Grid Standard.

  • System topic: Azure services publish their own events, like Blob Created. Example: a Surescripts formulary and benefit file lands in Blob Storage, and wf-rx-formulary-load fires.
  • Custom topic: you publish your own business events. That's rx-events here.
  • Partner topic: a SaaS partner publishes events into your Azure subscription.
  • Namespace topic (Event Grid Standard): the newer model, with pull and push delivery and MQTT support.

An event on the wire (CloudEvents schema)

{
  "specversion": "1.0",
  "type": "Rx.Sent",
  "source": "/integration/rx-transform",
  "id": "5f1c...",
  "time": "2026-09-16T14:02:11Z",
  "subject": "prescriptions/RX-100245",
  "data": { "rxId": "RX-100245", "correlationId": "c0a8...", "pharmacyNcpdpId": "1234567" }
}

No patient data. The event says what happened and where to look. Subscribers fetch details if they're allowed to.

How the pieces connect

  • Publishing: the transform workflow sends an HTTP POST to the topic endpoint, authenticated with its managed identity. It needs the EventGrid Data Sender role.
  • Subscribing: each subscription has a filter (by event type or subject) and an endpoint: a Logic App, a Function, a Service Bus queue, or a webhook.
  • Webhook validation: Event Grid proves you own a webhook endpoint with a validation handshake first. Built-in Azure endpoints handle this for you. A custom webhook that ignores it never gets events.
  • Retries: by default, up to 30 attempts over 24 hours with backoff. Configure a Blob container for dead-lettered events, or failed events are dropped.
Common pattern worth naming: Event Grid into Service BusIf a subscriber must never miss an event and processes slowly, point the Event Grid subscription at a Service Bus queue. Event Grid gives the fan-out. Service Bus gives the durability and pace control.

9. Entra ID, OAuth 2.0 and Key Vault

The design goal: no secrets inside Azure. Every application-to-application call uses managed identity. Secrets exist only at the edges, with outside parties. (One caveat below: the Logic App's own host storage connection.)

OAuth 2.0 and JWT in 6 facts

  • Client credentials is for app-to-app with no user. The app sends its ID and a secret or certificate, and gets an access token.
  • The scope for this flow is {app-id-uri}/.default, meaning "all app roles granted to me."
  • App-only permissions show up in the roles claim. Delegated (user) permissions show up in scp.
  • aud is who the token is for. iss is who issued it. exp is when it dies. A JWT is signed, not encrypted.
  • The API validates the signature with Entra's public keys from the OpenID configuration document.
  • Certificates beat client secrets for the EHR: nothing to copy around, and harder to leak.

Managed identity

A managed identity is a service principal Azure creates and manages for a resource. No password exists that you could leak. System-assigned lives and dies with the resource. User-assigned is its own resource that you can attach to several apps. That helps when you recreate apps often, or want permissions granted before the app exists.

Who gets which role

IdentityRoleScope
Logic App MIAzure Service Bus Data Sender + ReceiverNamespace (or just the topic)
Logic App MIKey Vault Secrets UserKey Vault
Logic App MIEventGrid Data Senderrx-events topic
Logic App MIStorage Blob Data ContributorArchive container
Logic App MIApp role on the Function's app registrationFunction app
APIM MIApp role on the Logic App's app registration (Easy Auth)Logic App

Scope roles as narrowly as you can. "Contributor on the resource group" works in a lab and fails a security review.

Key Vault

What still needs Key Vault here: the client certificate and credentials for Surescripts. Two ways to consume it:

  • Key Vault reference in app settings: @Microsoft.KeyVault(SecretUri=https://kv-rx.vault.azure.net/secrets/SurescriptsPassword/). The workflow reads @appsetting('SurescriptsPassword') and never knows Key Vault exists.
  • APIM named value backed by Key Vault, for secrets used in policies.

Leave the version off the URI. Then rotation is automatic: the platform picks up the new version on its refresh cycle.

Use the RBAC permission model on the vault, not access policies. It's the current default and it fits the same role model as everything else.

10. Production networking

The lab keeps things public for simplicity. In production healthcare, expect everything private. The whole design comes down to one VNet, five subnets, and private DNS.

The subnets, and why each one exists

SubnetHoldsRules that matter
snet-appgwApplication Gateway with WAFDedicated to App Gateway only. Only public entry point for external callers
snet-apimAPIM in internal modeDedicated to APIM. Needs an NSG that allows APIM's management traffic (the ApiManagement service tag) and the Azure load balancer probe. Missing these rules is a classic deployment failure
snet-la-intLogic App outbound (VNet integration)Delegated to Microsoft.Web/serverFarms. Nothing else can live here. Size it for scale-out, since each instance takes an address; /26 is a common minimum
snet-func-intFunction outbound (VNet integration)Same delegation rule. Kept separate here for clarity and independent scaling
snet-peAll private endpointsNo delegation. Each private endpoint takes one private IP. Group them here so NSGs and routing stay simple
Optional: AzureBastionSubnet, snet-jumpboxAdmin accessYou need a way in to test private endpoints. Your APIM lab already has a jumpbox for exactly this

The key insight: inbound and outbound use different subnets

This confuses almost everyone at first, so it's worth saying clearly in an interview.

VNet integration is outbound only. It lets the Logic App send traffic into the VNet, from an address in snet-la-int. It does nothing for traffic coming to the Logic App.

A private endpoint is inbound only. It gives the Logic App a private IP in snet-pe so APIM can call it. It does nothing for traffic going out.

A fully private Logic App needs both. So does the Function. Service Bus, Key Vault and Storage only receive calls, so they only need private endpoints.

Why the Logic App needs four storage endpoints

Logic Apps Standard uses its storage account for blobs, queues, tables and file shares (state, run history, scheduling, content). Each of those storage services is a separate private endpoint with its own DNS zone. Lock the storage account down and forget one, and the runtime fails to start. That's a common and confusing outage.

Four phrases to say cleanly

TermDirectionPlain meaning
VNet integrationOutboundLets my app send traffic into the VNet
Private endpointInboundGives a PaaS resource a private IP inside my VNet
Private DNS zoneName resolutionMakes the normal hostname resolve to that private IP
Public access disabledClosing the doorOnce the private path works, remove the public one

How DNS makes it work

The Logic App still connects to sb-rx-prod.servicebus.windows.net. Nothing in its config changes. Inside the VNet, that name resolves through a CNAME to sb-rx-prod.privatelink.servicebus.windows.net, and the private DNS zone answers with the private endpoint's IP, like 10.42.4.5.

That's why the most common failure is DNS. The private endpoint exists, but the zone isn't linked to the VNet, so the name still resolves to the public IP. The call hits a disabled public endpoint and fails. Check with nslookup from inside the VNet: a 10.42.x.x answer is good, a public IP is your bug.

11. Real production topology

Section 10 showed one environment's subnets. In a real company, that layout is repeated per environment, and shared security sits in a central hub. This is what to draw when asked "how does this look in production?"

Environments: separate spokes, same code

  • One subscription per environment. Clean RBAC, cost tracking and Azure Policy boundaries. Few people get access to prod.
  • Same Terraform, different variables. Dev uses cheap tiers. QA mirrors prod closely enough to test performance and networking. Prod gets Premium Service Bus, zone redundancy and approvals.
  • Non-overlapping address ranges (10.41, 10.42, 10.43). Peering fails if ranges overlap, so plan them up front.
  • Spokes don't peer with each other. Dev can't reach prod, even by mistake.
  • Surescripts has its own environments. Dev and QA talk to the Surescripts certification environment. Only prod talks to Surescripts production. The SurescriptsEndpoint app setting is what switches it.

Many companies go further and use one hub for non-prod and a separate hub for prod. Same idea, stronger isolation.

WAF and firewall do different jobs

WAF (App Gateway or Front Door)Azure Firewall
DirectionInbound web trafficOutbound, and traffic between networks
UnderstandsHTTP: SQL injection, bad headers, OWASP rulesIPs, ports, domain names (FQDNs)
In this designIn front of APIM for the EHRsControls what Logic Apps can call out to

APIM and the WAF also overlap a little. The WAF blocks attack patterns. APIM handles identity, rate limits and API contracts. You want both.

The egress story

This is where an integration architect stands out, because partners care about it.

  1. A route table (UDR) on snet-la-int sends 0.0.0.0/0 to the firewall's private IP.
  2. The Logic App must route all outbound traffic through its VNet integration (the "route all" / outbound internet traffic setting). If it's off, internet calls skip the VNet and bypass the firewall completely.
  3. The firewall has an application rule allowlist: the Surescripts endpoints, plus PDMP registries or aggregators and ePA intermediaries if you support those transactions. Everything else is denied. A misbehaving workflow can't send patient data anywhere else.
  4. Traffic leaves from the firewall's static public IP. Surescripts and similar partners allowlist your source IP during onboarding, along with your client certificate. A fixed IP is what makes that possible.
Classic failure after go-liveEverything works in dev, then prod calls to Surescripts time out. Common causes: the prod firewall IP was never given to Surescripts for allowlisting, the FQDN rule is missing in the prod firewall, or "route all" is off so traffic leaves from a different IP.

What to say, in about 30 seconds

Each environment is a spoke in its own subscription, built from the same Terraform with different variables. They peer to a central hub that holds the WAF, Azure Firewall, Bastion and private DNS. EHR traffic comes in through the WAF to APIM. Logic App outbound traffic is forced through the firewall with a UDR, allowed only to Surescripts and the other partners we support, and leaves from a static IP that Surescripts has allowlisted. Dev and QA use the Surescripts certification environment. Only prod reaches production.

12. Observability

When someone says "prescription RX-100245 never reached the pharmacy," you want one query, not an afternoon.

The correlation ID thread

  1. APIM sets or keeps x-correlation-id.
  2. Intake copies it into the Service Bus message's CorrelationId.
  3. Transform reads it and writes it as a tracked property on key actions, along with rxId.
  4. The Function logs it. The Event Grid event carries it.

Same ID, every hop. That's the design choice that makes troubleshooting fast.

// App Insights: everything for one prescription, in order
union requests, dependencies, traces, exceptions
| where timestamp > ago(1d)
| where tostring(customDimensions) has "RX-100245"
| project timestamp, itemType, cloud_RoleName, name, resultCode, message
| order by timestamp asc

Where to look for what

QuestionLook here
Did the request reach us?APIM analytics, or App Insights requests for APIM
Which step of the workflow failed?Logic App run history (stateful), inputs and outputs of each action
Are messages piling up?Service Bus metrics: active messages, dead-lettered messages
Why was it dead-lettered?Service Bus Explorer, DLQ, DeadLetterReason
Did subscribers get the event?Event Grid metrics: delivered, failed, dead-lettered
Function exceptions?App Insights exceptions and failures blade

Alerts worth setting

  • DLQ message count above 0.
  • Active message count growing for 15 minutes (processor is stuck or down).
  • Workflow run failure rate above a threshold.
  • APIM 5xx rate and 401 spikes (a partner's certificate or secret expired).
  • Event Grid delivery failures.

18. Interview questions

Try answering each out loud before you open it.

When would you choose Logic Apps Standard over Consumption?

When I need VNet integration or private endpoints, built-in connectors for throughput, several related workflows deployed together, stateless workflows, or an application-style project with local development and zip deployment. Consumption also supports CI/CD, usually through ARM or Bicep. Consumption fits small, low-volume, internet-facing automations where pay-per-action is cheaper.

How do you guarantee a message isn't lost?

Accept fast and put it on Service Bus before replying. Process with peek-lock so a crash leads to redelivery, not loss. Use stateful workflows for multi-step work. Dead-letter poison messages instead of deleting them, and alert on the DLQ.

How do you prevent duplicate processing?

First, I say it honestly: Service Bus is at-least-once, so I design for duplicates rather than promise exactly-once. Duplicate detection with a stable per-command MessageId catches sender retries. A sensible lock duration plus lock renewal avoids redelivery during long runs. The processor is idempotent: it checks whether that command was already sent. And I send a stable message ID to the partner, with status checks or reconciliation when the outcome is unknown.

Explain peek-lock vs receive-and-delete.

Receive-and-delete removes the message as soon as it's handed over. If the receiver crashes, it's gone. Peek-lock hides the message for the lock duration. The receiver then completes, abandons or dead-letters it. If the lock expires, it becomes available again and the delivery count goes up.

Service Bus vs Event Grid vs Event Hubs?

Service Bus for commands and business messages that must be processed reliably, with ordering, sessions and DLQ. Event Grid for discrete notifications fanned out to many subscribers. Event Hubs for high-volume streams like telemetry, where consumers read from a partitioned log at their own pace.

How do you handle errors in a Logic App?

Retry policies on actions for short blips. A Try scope and a Catch scope with run-after set to Failed and TimedOut. In Catch, I read result('Try'), classify the error, abandon for transient ones and dead-letter with a clear reason for business ones, then publish a failure event and log the correlation ID.

How does APIM authenticate callers and backends?

Inbound, validate-jwt checks signature, issuer, audience and required roles on the caller's Entra token. Outbound, APIM uses its managed identity with authentication-managed-identity to get a fresh token for the backend. The caller's token isn't passed through.

What's the difference between roles and scp claims?

roles carries app roles, used in app-only flows like client credentials. scp carries delegated scopes when a user is involved. A daemon token has roles and no scp.

How do Logic Apps get secrets?

Preferably they don't need any, thanks to managed identity. When a partner needs a key or certificate, it lives in Key Vault, and the app setting uses a Key Vault reference without a version, so rotation is picked up automatically. The Logic App's identity has Key Vault Secrets User.

When do you use a Function instead of Logic App actions?

When logic needs loops, calculations, complex string handling, libraries, or unit tests. Logic Apps orchestrate, Functions compute. I call the Function with managed identity behind Easy Auth.

How do you deploy Logic Apps Standard with Azure DevOps?

Infra with Terraform in one pipeline. Workflows as a project folder in Git, zipped in build, deployed with the Azure Functions task using app type workflowapp, through environments with approvals. The service connection uses workload identity federation. Environment differences live in app settings and parameters.json, so the same zip goes everywhere.

A partner says messages are missing. How do you investigate?

Get an ID or time window. Search App Insights by correlation ID. Walk the path: APIM request, intake run, topic and subscription counts, DLQ, transform run history, the partner call result. Most often it's a filter mismatch, a dead-lettered message, or a failed partner call that was handled but not alerted on.

Why use a canonical data model?

It decouples sources from targets. Each new source needs one map into the canonical model, and each target one map out. Without it, every source-target pair needs its own map, and changes ripple everywhere.

What does splitOn do?

It debatches a trigger's array output into one run per item. Each message is processed and settled on its own, so one bad item doesn't fail the batch, and run history is clearer.

How do you guarantee order for related messages?

Service Bus sessions. Set SessionId to the grouping key, like the prescription group, and use a session-aware receiver. Messages in a session are processed in order by one receiver at a time. Important: ordering holds only inside one session-enabled queue or subscription. In my design NewRx and CancelRx go to different subscriptions, so if strict order matters I route both through one session-aware subscription, or the CancelRx workflow checks the prescription's state first. Sessions lower parallelism, so use them only where order really matters.

How do you secure the platform network-wise in production?

APIM in internal VNet mode, or behind Application Gateway with WAF for external callers. Logic App with VNet integration for outbound and a private endpoint for inbound. Service Bus Premium, Key Vault and storage with private endpoints and private DNS zones. Public access disabled wherever possible.

19. The 60-second pitch

If they say "walk me through an integration you'd design," this is the shape.

An EHR sends FHIR prescriptions that pharmacies need as NCPDP NewRx. APIM is the front door: it validates the Entra token and app role, rate-limits per partner, and stamps a correlation ID. A stateless Logic App validates the payload, puts it on a Service Bus topic with a stable per-command MessageId, and returns 202.

A stateful Logic App picks it up with peek-lock. It maps FHIR to a canonical model with Liquid, calls a Function to validate the NPI and map RxNorm to NDC, then uses XSLT to build the NewRx and sends it to Surescripts with a certificate from Key Vault. Success completes the message. Business errors are dead-lettered with a reason, transient ones are abandoned for retry.

Then it publishes an event to Event Grid so notification and audit can react without coupling. Every hop uses managed identity. The correlation ID runs end to end into App Insights. Terraform builds the platform, and Azure DevOps deploys the same package to each environment with approvals.

That's roughly 60 seconds out loud. Every sentence maps to a section above, so any follow-up question has somewhere to go.
