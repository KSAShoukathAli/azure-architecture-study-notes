BizTalk to Azure Mapping - Feynman Way

stop asking "what replaces BizTalk?" - ask what the system was doing
You have a BizTalk application that has worked for years. The business does not care about receive ports, MessageBox, or orchestrations. It cares that the right message arrives, is understood, reaches the right process, survives failure, and gets delivered once safely enough for the business.
Feynman loop: remove the product names, describe the job in plain language, rebuild the minimum architecture that satisfies the job, predict failure behavior, then add Azure services only when the simple model breaks.

1 Start with one integration machine

That is the first simplification. BizTalk is not magic. It is a machine doing several jobs.

prediction

If we move to Azure, must all those jobs stay inside one product? No. But splitting them without a reason is just as bad as keeping everything together without a reason.

2 Name the jobs, not the features

1. Accept
2. Understand
3. Route
4. Remember
5. Deliver
Accept
Where does the message enter? HTTP? file? queue? timer?
Understand
Decode, parse, validate, transform, enrich.
Route
Who should receive it and why?
Remember
Does a long-running process need durable state or correlation?
Deliver and recover
Call the destination, survive transient failure, and give operations a safe recovery path.

Now BizTalk words become implementation details. Receive locations helped with Accept. Pipelines helped with Understand. MessageBox helped with Route and persistence. Orchestrations helped with Remember. Send ports helped with Deliver.

3 Why Azure splits the machine

4 Derive Logic Apps Standard

Suppose one integration flow needs:

  • a Service Bus trigger,
  • XML validation,
  • a transformation,
  • a few decisions,
  • a call to SQL and an HTTP API,
  • retry and run history.

Do we need six Azure services? No. Those jobs can live coherently inside one Logic Apps Standard application.

Start cohesive. Split when scale, ownership, durability, protocol, security, or lifecycle demands it.
break it

Now two independent consumers must receive the same event, even if the workflow app is down. That breaks the simple design. We have discovered a reason for an independent broker such as Service Bus.

5 Derive the receive location

A BizTalk receive location feels like a large concept because it combines endpoint, adapter, schedule, and pipeline. Strip those apart. The endpoint itself might simply become a workflow trigger. Only add APIM or Service Bus when the entry boundary needs their specific behavior.

6 Derive the pipeline

A pipeline sounds BizTalk-specific. But ask what it actually did:

raw bytes
   -> decode
   -> parse
   -> validate
   -> split / assemble
   -> enrich
   -> transform
   -> business message

Those are ordinary data-processing steps. Azure can express them as built-in workflow actions, XML/Flat File operations, maps, connectors, or small local functions.

prediction

If a custom pipeline component only reformats one field, should it automatically become a separately deployed Function App? No. That creates an unnecessary network, deployment, security, and monitoring boundary.

7 Derive MessageBox

MessageBox was an implementation center. It is not a target-architecture requirement.

8 Derive orchestration

An orchestration is not a drawing of boxes. It solves a harder problem:

A process may wait, branch, call systems, remember state, receive later messages, survive restarts, and still know what comes next.

That maps naturally to a durable stateful workflow when the process really needs persistence. If the flow is short-lived and can restart from the beginning, a stateless workflow might be enough.

break it

The orchestration has atomic transaction assumptions around two legacy systems. Can you just draw the same shapes in Logic Apps? No. Distributed cloud services do not recreate an MSDTC-style boundary by drawing the same workflow. You need idempotency, compensation, or a redesigned consistency model.

9 Derive correlation

BizTalk hid a lot of correlation plumbing behind promoted properties and subscriptions. In Azure, make the business key explicit and decide who owns the conversation.

  • If one durable workflow owns the wait, keep the state there.
  • If ordered broker messages belong together, Service Bus sessions may help.
  • If many processes need the key, store it explicitly in a state store.
  • If the goal is only routing, use routing/filtering rather than pretending it is process correlation.

10 Where does suspended work go?

BizTalk trained operators to look for suspended instances. Azure makes you ask a more precise question:

Workflow failed?
Run history, scopes, retry, resubmit.
Broker gave up?
Dead-letter queue, delivery count, lock/settlement.
Side effect partly happened?
Idempotency, compensation, reconciliation.
The failure is no longer "in BizTalk." It lives at a specific boundary.
prediction

If an operator resubmits a failed workflow after the downstream database already committed, what happens? Without idempotency, recovery can create a duplicate business effect.

11 Derive rules and B2B

Rules
If business decisions change independently of workflow code, a rules engine gives those decisions a separate model. Logic Apps Standard now has a Rules Engine that can reuse supported BizTalk rules.
B2B
If partners exchange AS2, X12, EDIFACT, or RosettaNet, you need partner/agreement/certificate semantics, not just a generic XML workflow.

The important idea is that enterprise-integration artifacts survive because the business contract survives. But the storage and runtime model can change.

healthcare

If the BizTalk estate uses BTAHL7, do not hide it under a generic XML label. HL7 v2.x encode/decode is now a native Standard capability. If the source sends HL7 over raw TCP/MLLP, the transport requirement changes the hosting decision: current MLLP operations are preview and require Logic Apps Standard Hybrid, where custom TCP ports can be opened.

12 One end-to-end migration

Notice what disappeared: we did not create Service Bus just to honor the memory of MessageBox. We added it only in the version where asynchronous decoupling is a real requirement.

13 Cut over without a big bang

You do not need one weekend where the entire BizTalk estate disappears. Move by business flow. During coexistence, bridge the two worlds only where needed: HTTP contracts, the BizTalk Logic Apps adapter/on-premises gateway, or a broker boundary. If BizTalk uses the SB-Messaging adapter as that broker bridge, the September 30, 2026 SBMP retirement must be handled first.

prediction

A BizTalk host used to throttle when the downstream system slowed. You migrate the flow to a Logic App that can start many runs at once. What happens on the first burst? The downstream can be overwhelmed unless you make backpressure explicit with concurrency limits, buffering, and dependency-aware retry behavior.

ordered delivery

A BizTalk send port with ordered delivery is not the same problem as an orchestration convoy. If endpoint delivery must stay serialized after a broker boundary, a Service Bus session plus a session-aware sequential consumer can preserve ordering for that key.

14 What the Migration Agent can and cannot know

The agent can accelerate inventory, planning, conversion, and validation, but it runs through GitHub Copilot. That adds a governance decision to the migration program: treat source projects and binding configuration as sensitive, remove secrets, and use your organization's approved Copilot and data-handling controls. Architecture ownership still stays with the team.

15 Break the model

scenario 1

A BizTalk send port has a filter on promoted properties. Do you create Service Bus? Not automatically. If routing is local to one workflow app, a condition may be enough. Use broker filters when routing needs an independent pub-sub boundary.

scenario 2

A pipeline component calls a database to enrich every message. Where does it go? Start with workflow-local implementation if it belongs only to that integration. Split it into a service only if independent lifecycle, scale, reuse, ownership, or security makes that boundary valuable.

scenario 3

A sequential convoy depends on messages with the same business ID arriving in order. Is a Service Bus session the replacement? Maybe part of the design, not a mechanical replacement. Sessions give ordered broker affinity for one SessionId. You still need to design the process state, timeout, missing-message, duplicate, and recovery semantics.

scenario 4

An operator wants one place containing every failed message, just like BizTalk suspended instances. Can you promise that? No. Failures can live in workflow runs, broker DLQs, downstream systems, or compensation/reconciliation stores. Build an operational view across those domains.

scenario 5

The Migration Agent generated a workflow that deploys successfully. Is migration complete? No. Deployment proves syntax and packaging. Migration requires semantic equivalence, nonfunctional testing, operational readiness, cutover, and rollback evidence.

16 Explain it from a blank page

BizTalk is one platform that combines endpoint adapters, message processing, pub-sub routing, durable orchestration, transformation, B2B, rules, and tracking. Azure Logic Apps Standard is Microsoft's primary successor application boundary, but Azure does not provide one service that equals BizTalk. I migrate by end-to-end flow. I identify what each BizTalk artifact was actually doing, keep related workflow behavior inside Logic Apps Standard where possible, and add APIM, Service Bus, Functions, integration accounts, rules, or tracking only when the requirements justify a separate boundary. MessageBox, correlation, convoys, suspended instances, and host topology are redesign areas rather than one-to-one mappings. The proof of migration is not that the new workflow looks similar; it is that contracts, routing, reliability, security, operations, and business outcomes remain correct under normal and failure conditions.
