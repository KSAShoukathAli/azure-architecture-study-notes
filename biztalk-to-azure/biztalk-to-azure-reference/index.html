architect lookup - preserve behavior, redesign implementation

1 Migration mindset

The migration unit is an end-to-end integration flow, not a BizTalk artifact.

A BizTalk application can make several responsibilities look like one platform concern: endpoint hosting, transport adapters, message parsing, transformation, pub-sub routing, orchestration persistence, business rules, tracking, and operations. Azure spreads these responsibilities across application/runtime boundaries.

anti-pattern

Artifact-by-artifact replacement: receive port becomes service A, MessageBox becomes service B, orchestration becomes service C, pipeline becomes service D - even when the new flow does not require those boundaries. This recreates complexity instead of modernizing it.

better question

For each BizTalk flow ask: What business behavior must remain? What durability, ordering, routing, transformation, protocol, security, and recovery guarantees are actually required?

3 What BizTalk bundled together

The MessageBox is especially important: it is not merely a queue. It stores messages, properties, subscriptions, orchestration state, tracking data, and host queues. That is why there is no single Azure service that honestly equals "MessageBox."

4 Choose the Azure boundary first

Add...When you need...Do not add it merely because...
API ManagementAPI security, lifecycle, mediation, products, policies, consumer boundary, SOAP/API facade.BizTalk had an HTTP receive location.
Service BusIndependent durable queue/topic, temporal decoupling, fan-out, competing consumers, broker ownership.BizTalk had MessageBox.
Azure FunctionsCode shared by multiple apps or needing independent scaling, versioning, ownership, endpoint, or security boundary.BizTalk used a helper assembly.
Integration Account / Rules / BPTB2B agreements, partners, certificates, business rules, or business process tracking.Every integration should have enterprise artifacts.
hosting is a separate decision

For BizTalk modernization, Standard can run on a Workflow Service Plan for managed Azure hosting, on App Service Environment v3 when isolated Azure hosting is justified, or in the Hybrid deployment model for local processing on customer-managed Azure Arc-enabled Kubernetes. Hybrid is partially connected rather than air-gapped and currently has feature differences, including no Azure Business Process Tracking and no managed identity authentication for connector operations.

5 Receive ports, receive locations, and adapters

BizTalk receive ports are logical objects; receive locations bind actual endpoints, adapters, schedules, and receive pipelines. In Standard workflows the usual target is a trigger or built-in/managed connector. For API governance or mediation, put APIM in front. For independently durable asynchronous intake, use a broker such as Service Bus.

adapter assessment

For every adapter, verify connector availability, authentication model, message size, throughput, trigger semantics, network reachability, and hosting support. A connector with the same protocol name is not automatically behaviorally equivalent.

6 Pipelines: decompose the stages

Do not translate a pipeline into a single replacement component. List what each pipeline stage actually does: decoding, parsing, disassembly, validation, enrichment, promotion, transformation, encryption, compression, or custom code. Then place each behavior in the workflow, built-in XML/Flat File actions, transformation actions, connectors, or workflow-scoped local functions.

gotcha

Property promotion is particularly BizTalk-specific because routing can depend on promoted context properties in MessageBox. In Azure, make routing data explicit in workflow data or broker message properties rather than trying to recreate a hidden central context.

8 MessageBox: do not search for one replacement

Use Service Bus topics/subscriptions when the target flow really needs independent publish-subscribe messaging. Use workflow conditions when routing belongs inside one application. Stateful Logic Apps owns workflow persistence. Monitoring/tracking moves to Azure monitoring and business-process capabilities. Rebuilding MessageBox as a mandatory broker layer for every flow is usually the wrong abstraction.

9 Orchestrations

Long-running BizTalk orchestrations usually map conceptually to stateful Standard workflows. Lightweight request/response or transformation flows can use stateless workflows when persistence is not required. Exception blocks, scopes, compensation, retries, and transaction assumptions require deliberate redesign rather than mechanical conversion.

reliability

Resubmission or retries can repeat side effects. Treat the target as at-least-once unless you have proven stronger semantics, and design idempotency around external writes.

10 Correlation and convoys

BizTalk correlation routes later messages to an existing orchestration instance using a correlation set. There is no universal one-to-one Azure equivalent. Choose based on what the correlation is really doing.

sequential convoy detail

The Logic Apps Standard built-in Service Bus connector currently includes session-aware queue/topic triggers specifically documented for sequential convoy patterns. That is useful when broker-level ordered affinity is the real requirement, but it still does not make Service Bus sessions a universal replacement for BizTalk correlation sets.

NeedPossible Azure design
One workflow waits for a later eventKeep the state in the durable workflow pattern that owns the process.
Ordered messages belonging to the same broker conversationService Bus sessions can group messages by SessionId; do not treat sessions as a generic BizTalk correlation-set replacement.
Pub-sub routing by propertiesService Bus topic/subscription filters or explicit workflow routing.
Cross-workflow/process lookupPersist an explicit business key in an appropriate state store and resolve deliberately.
Sequential/parallel convoyRedesign the conversation and ordering model. Convoys are not a shape to copy mechanically.

11 Send ports, send-port groups, and filters

A BizTalk send port combines destination, adapter, pipeline, retry behavior, and often subscription filters. In the target design these concerns may remain one workflow action or split only when required.

BizTalk concernAzure modernization path
Send adapter + endpointBuilt-in/managed connector, HTTP action, API, or custom connector.
Send pipelineTransform/encode/encrypt/compress steps before the send.
Send-port filterWorkflow conditions for local routing, or broker subscription filters for independent pub-sub.
Send-port groupExplicit fan-out branches, multiple actions, or topic subscribers depending on ownership and durability requirements.
Ordered deliveryIf ordering must survive a broker boundary, use Service Bus sessions plus a session-aware consumer that processes one session sequentially. This is related to, but not the same as, an orchestration convoy.
SOAP exposure/mediationConsider API Management when you need an independent SOAP/API facade and policy boundary.

12 Business Rules Engine

Microsoft's current Rules Engine for Logic Apps Standard supports declarative rules and can reuse supported exported BizTalk rules. The current documentation states that XML and .NET objects are native fact types and that BizTalk DB facts are not currently supported, so rule migration needs a fact-model review.

13 EDI and B2B

Logic Apps Enterprise Integration supports AS2, X12, EDIFACT, RosettaNet, schemas, maps, certificates, partners, and agreements. Standard logic apps can store schemas and maps directly in the application, while an integration account remains important for shared enterprise/B2B artifacts such as trading partners and agreements.

healthcare migration

For BizTalk Accelerator for HL7 workloads, current Logic Apps Standard guidance now matters directly. The HL7 built-in connector is generally available and supports v2.x encode/decode, validation through v2.6, individual processing, and batch decode/debatching. MLLP operations are public preview and require the Hybrid deployment model because MLLP is raw TCP and needs custom inbound ports. Two-way synchronous MLLP on the same connection/port is also preview. HL7 ACK parsing is supported for 2.4-2.6, while ACK generation is not currently provided by the HL7 connector.

connection to prior topic

The Observability chapter owns the detailed telemetry design. Here the migration point is simpler: BAM is not replaced by run history alone. Separate technical diagnostics from business-stage tracking.

15 Suspended messages and failure recovery

BizTalk gives operators a central suspended-instance concept. In Azure, failure ownership is distributed. A failed workflow run, a Service Bus dead-lettered message, and a downstream side effect are different recovery domains. Define replay/resubmit procedures per boundary and design idempotency before relying on manual resubmission.

16 Custom code: local function or Azure Function?

Use Logic Apps .NET local functions when...Use a separate Azure Functions resource when...
Code belongs to one Standard logic app.Code is shared by multiple applications or teams.
It validates, enriches, parses, formats, or calculates within the workflow.It is independently event-driven or API-hosted compute.
Workflow and code should deploy, scale, and operate together.Code needs independent scaling, versioning, deployment, ownership, or network/security boundary.
You are replacing pipeline/helper code that has no reason to become a service.The code is the primary compute workload and Logic Apps is only one consumer.
Custom BizTalk code does not automatically mean "create a Function App."
local-function limit

Current Microsoft guidance says Logic Apps local functions are not suitable for processes that might exceed 10 minutes or for BizTalk pipeline components that implement streaming. Those cases need a different implementation boundary.

security gotcha

Do not migrate credentials from binding files or SSO as plain application settings. Separate identity from secret material, and prefer managed identity where the target connector/service supports it.

18 Coexistence, cutover, and backpressure

BizTalk host throttling automatically slowed publishing or delivery when rates, memory, database pressure, or other resources crossed thresholds. Logic Apps does not recreate that host-level mechanism for you. Make load leveling explicit: trigger concurrency, Service Bus buffering when you need a broker boundary, consumer concurrency, retry/backoff, and downstream capacity limits.

coexistence bridges

During migration, old and new estates can exchange work through deliberate bridges. Microsoft documents the BizTalk Logic Apps adapter and on-premises data gateway for BizTalk-to-Logic Apps connectivity. HTTP/WCF-WebHttp is another contract boundary. Service Bus is useful when asynchronous decoupling is required, but BizTalk SB-Messaging users must address the September 30, 2026 SBMP retirement and current AMQP hotfix before relying on that bridge.

cutover rule

Parallel validation is not the same as two production owners. If both BizTalk and Azure execute side effects, you need explicit duplicate suppression and reconciliation. Safer migrations route one authoritative owner per flow, use shadow/read-only comparisons where possible, drain in-flight work, reconcile outputs, keep rollback criteria, and decommission only after evidence is complete.

ESB Toolkit itineraries

There is no direct Azure itinerary engine replacement. Decompose the itinerary into explicit routing, transformation, enrichment, and endpoint-selection decisions. Implement those decisions in workflows, routing metadata/policies, or a routing-slip style pattern rather than rebuilding the ESB Toolkit abstraction by name.

19 Azure Logic Apps Migration Agent

Current Microsoft documentation describes the Migration Agent as an AI-assisted Visual Studio Code extension built on GitHub Copilot and the Visual Studio Code Language Model API. A GitHub Copilot subscription is a prerequisite. Built-in parsers cover BizTalk projects, orchestrations, maps, schemas, pipelines, bindings, HIDX, business rules, and ASMX artifacts, but parser support is not proof that every construct can be converted automatically.

governance + preview

The Migration Agent remains a preview capability and its deployment/hosting automation is evolving. Verify the current release before relying on any specific automated deployment target. Treat BizTalk projects and binding files as sensitive configuration: review your organization's GitHub Copilot and AI data-governance requirements, remove secrets from source artifacts, and keep human review around generated architecture, code, and deployment configuration.

Use it to accelerate: inventory, dependency analysis, flow grouping, target mapping, baseline conversion, test execution, and repeatable planning. Do not delegate: architecture boundaries, security, semantics, reliability, performance, cost, cutover, or operational ownership.

21 Interview model

say this

I do not map BizTalk artifacts one-for-one. I first identify the end-to-end flow and the behavior BizTalk was providing: ingress, normalization, routing, orchestration, transformation, delivery, tracking, and recovery. For most migrations I start with Logic Apps Standard because it provides the core workflow and enterprise-integration application boundary. I add APIM for an independent API facade, Service Bus for independent brokered messaging, and Functions only when code needs its own scaling or lifecycle boundary. MessageBox, correlation, suspended messages, and host topology require redesign because they do not have single Azure equivalents. I validate semantic equivalence with representative messages and operational failure tests, then migrate in waves with coexistence and rollback.

interview drill
  1. Why is Service Bus not automatically the replacement for BizTalk MessageBox?
  2. When does a BizTalk receive location become APIM, and when does it just become a Logic Apps trigger?
  3. How would you migrate a custom receive pipeline component?
  4. What is the Azure equivalent of a BizTalk correlation set?
  5. How would you handle a sequential convoy?
  6. Where do suspended messages go after migration?
  7. When would you use Logic Apps local functions instead of Azure Functions?
  8. How do you migrate BizTalk BRE policies with database facts?
  9. How would you preserve B2B agreements and certificates?
  10. What evidence proves that a migrated map or orchestration is equivalent?
  11. How would you run BizTalk and Azure side-by-side during migration without duplicate business effects?
  12. What replaces BizTalk host throttling and how do you protect a slow downstream system?
  13. How would you migrate BTAHL7 when the source uses MLLP?
  14. What does the Migration Agent automate, what does GitHub Copilot change from a governance perspective, and what decisions still belong to the architect?
