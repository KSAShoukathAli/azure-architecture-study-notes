OAuth2, App Service & AKS Identity

field notes - the two OAuth2 flows, App Service's Kudu problem, and why AKS needs federation
The one-line version: a human logging in uses authorization code flow, a service calling another service uses client credentials flow. App Service (Web Apps, Function Apps, Logic Apps Standard) ships a separate companion site called Kudu for deployment and diagnostics, on its own hostname but tied to the same app's auth configuration. AKS pods federate their Kubernetes-native identity into a real Entra identity - it's pod identity vs resource identity that matters, not "AKS isn't Azure-native."

Who needs an identity?

  1. Human identity usually means a sign-in flow: Authorization Code + OIDC.
  2. Workload identity means a service proving who it is.
  3. If the workload is already an Azure resource, it can get a Managed Identity.
  4. If the workload is an AKS pod, it starts with a Kubernetes ServiceAccount and then federates into an Entra/Azure identity.

both paths converge on Entra ID and end with an access token - everything below hangs off this one fork.

— PART 1 —

1 The Two OAuth2 Flows

Three players show up across both flows: the user (a human, only in flow 1), the client (whichever app is asking for a token - this is OAuth jargon, it does not mean "the user"), and Entra ID (the authorization server). A fourth term, resource server, just means whatever API the client is ultimately calling.

Flow 1 - Authorization Code Flow, confidential web app (a human logs in)

This is the confidential-client case - a server-side web app with a backend that can hold a secret. It's the most common shape, but not the only one.

  1. The browser carries the user through redirects.
  2. The authorization code comes back through the browser.
  3. The backend performs the real token exchange with Entra.
  4. PKCE protects the code from being redeemed by the wrong party.
Boundary: in a SPA, the browser itself redeems the code. So “tokens never enter the browser” is not universally true.
why the extra hop, in this scenario

The code lands in the browser because Entra has no direct line to your backend - it only knows how to redirect the browser to a pre-registered callback URL. In this confidential-client case, redeeming that code for real tokens requires a client secret, and a secret can never live in browser JavaScript. So the code gets handed off to the backend, which holds the secret safely and does the actual exchange server-to-server.

public-client variant - SPAs, mobile, desktop

A single-page app has no backend to hold a secret, so it's a public client. It still uses authorization code flow, but with no client secret at all - the browser itself redeems the code, using PKCE alone as the protection, and receives the tokens directly. So "only the code crosses the browser, tokens never do" is true for the confidential-client diagram above, not for auth code flow in general.

PKCE - the second lock on the code

Even with a code sitting briefly in a URL, it shouldn't be redeemable by whoever intercepts it. PKCE (proof key for code exchange) fixes that: before redirecting to Entra, your app generates a random code_verifier, sends a hashed version (code_challenge) up front, then must present the original verifier when exchanging the code. Entra re-hashes it and checks the match.

Flow 2 - Client Credentials Flow (service calls service)

No user, no browser, no redirects. Picture APIM calling a backend microservice.

  1. Setup time: the backend app registration defines roles; an admin grants them to the client.
  2. Runtime: the caller proves its identity with a secret, certificate, or managed identity.
  3. The backend validates the token and reads the roles claim.

Since there's no resource owner granting permission live, the token carries app roles instead of user-delegated scopes - defined on the backend's app registration, then explicitly assigned to the client.

two phases, not one

Setup (once, by an admin): backend declares its roles in its manifest (e.g. backend.read) → admin goes to the client's enterprise application and grants it that role (often needs admin consent) → this is where the real access-control decisions get made.

Runtime (every call): client proves identity (secret or managed identity) → Entra looks up what it was already granted → stamps the roles claim into the token, no live approval needed → backend just reads the claim.

The setup phase is where misconfigurations live - a role granted too broadly sits there quietly. The runtime exchange is mechanical; it either works per spec or fails outright.

OAuth2 vs OIDC

OAuth2 alone only answers "can this app do X?" It was never designed to answer "who is this user?" OpenID Connect (OIDC) is a layer on top of the same authorization code flow that adds an ID token - a signed JWT carrying the user's name, email, and a unique ID. Your web app login almost always uses OAuth2 + OIDC together: the access token lets it call APIs, the ID token tells it who logged in.

OIDC never shows up in client credentials flow - there's no human to describe, so Entra only ever issues an access token there, never an ID token. Litmus test: is a human logging in whose identity matters? Yes → auth code flow + OIDC. Two services talking → client credentials, access token only.

2 App Service: the shared foundation

  1. These are different application models, but they live on the same App Service family.
  2. The shared platform gives you hosting, deployment, HTTPS endpoints, and operational tooling.
  3. Remember this as a shared foundation, not “all runtimes are identical.”

Web Apps, Function Apps, and Logic Apps Standard are three different things running on the exact same App Service foundation - just hosting different content: your website code, individual functions, or the Logic Apps workflow engine itself.

Kudu - the companion management site

Kudu is not your app's web server. Microsoft calls it a companion app that App Service creates alongside yours - a second, separate site reachable at yourapp.scm.azurewebsites.net. It handles deployment (zip deploy), file browsing, log streaming, and console access - the things you'd get for free with RDP into your own IIS box, recreated safely over HTTPS for a PaaS platform where you never get machine access. (Avoid calling it a "sidecar" - that word has a specific, different meaning in Kubernetes and the picture doesn't transfer cleanly.)
  1. The main site is for your application traffic.
  2. The SCM site is the companion management surface used for deployment and troubleshooting.
  3. Think “two endpoints, different trust zones,” not “Kudu is a sidecar inside my request path.”
why this matters

On classic self-hosted IIS, one machine gave you both traffic-serving and management access - physical access was the only boundary. On multi-tenant PaaS, Azure enforces that split logically instead: two endpoints, so different security policies could apply to each. Easy Auth is a real, supported way to secure a Standard Logic App's Request trigger with Entra ID, and plenty of real setups (APIM + Easy Auth) use it successfully. The caution is narrower than "it locks everything": Easy Auth, deployment tooling (Kudu/SCM), and the run-history/management API are separate configuration surfaces with their own auth and networking settings, so turning one on is not automatically transparent to the others - it needs deliberate configuration, and it's worth testing your deploy and monitoring path before committing to it, not assuming it will just keep working.

SAS vs managed identity on a Logic Apps Standard HTTP trigger

Concretely, APIM → Logic App: an EHR sends a request to APIM, which authenticates it, then forwards to a Logic App workflow that starts with an HTTP request trigger. The moment that trigger is created, Azure auto-generates a callback URL with a baked-in signature (a SAS - shared access signature) - not a stored password, a self-verifying signed URL. That URL, dropped into the APIM policy, is the credential APIM presents.

the real-world pattern

SAS on the one HTTP trigger entry point isn't a lesser choice in production - it's the native mechanism, just hardened with Key Vault-backed named values and rotation. Managed identity dominates for literally everything downstream of that entry point. A lab wiring it exactly this way mirrors real production architecture.

3 AKS: why pods federate INTO a managed identity

correction

AKS is a real Azure resource, and the cluster itself normally has its own managed identity. The distinction that matters isn't "AKS vs Azure" - it's cluster identity vs pod identity. The cluster's control plane already talks to Azure using managed identity, same as anything else. The gap is one level down: a pod starts life with a Kubernetes-native identity (its service account), and Kubernetes service accounts are not something Entra recognizes on their own.

  1. An AKS pod starts with a Kubernetes identity, not an Azure identity.
  2. OIDC federation lets Entra trust that Kubernetes-issued identity and map it to a managed identity or application identity.
  3. An Azure-native service like APIM can get a managed identity directly, so it does not need that bridge.
Kubernetes has its own native identity system (service accounts) that works identically on AKS, EKS, or on-prem, so Entra doesn't automatically trust it - a pod's identity and an Azure identity are two different things by default. OIDC workload identity federation is the bridge, and it lands on a real Entra identity: AKS exposes an OIDC issuer, and a federated credential is configured on a user-assigned managed identity (or an app registration), saying "trust tokens from this issuer for this service account." The pod presents its projected Kubernetes token, Entra checks it against that trust config, and exchanges it for a real access token from that same managed identity - no secret stored anywhere.

The key distinction is pod identity vs resource identity, not "AKS isn't Azure-native." APIM is a resource that already has an identity attached to it directly - there's no separate workload inside it with its own Kubernetes-native identity needing to be bridged. A pod does have that separate identity, so federation is the mechanism that links the two together. Once linked, both end up authenticating the exact same way: client credentials flow, presenting proof of identity to Entra, getting a token back.

APIM → AKS microservice

This is clean - AKS doesn't bundle a Kudu-equivalent companion site on the same hostname as your workload's traffic, so there's nothing to accidentally lock down together. APIM calls the microservice via client credentials flow (managed identity on APIM's side, bearer token validated in your code). Deployment and monitoring for AKS live entirely separately too - CI talks to the Kubernetes API server, logs go to Container Insights, none of it shares a hostname with the app's actual traffic.
