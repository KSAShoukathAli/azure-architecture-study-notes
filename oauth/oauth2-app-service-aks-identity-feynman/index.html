— PART 1 · THE ROOT QUESTION —

1 Who needs an identity?

start with the problem

An API receives a request. Before it allows anything useful, it needs to know who or what is calling and what that caller is allowed to do.

That gives us two different questions:

  • Authentication: who are you?
  • Authorization: what may you do?

Rebuild from basic facts

Fact 1
A human can interact with a sign-in screen.
Fact 2
A background service cannot stop and type a password.
Fact 3
Some Azure resources already have an identity Entra can recognize.
Fact 4
A Kubernetes pod begins with a Kubernetes identity, not automatically an Azure workload identity.
HUMAN
Think interactive authentication and delegated user context.
AZURE WORKLOAD
If the hosting resource supports it, Managed Identity can represent the workload.
AKS POD
The pod begins with a Kubernetes ServiceAccount identity; federation bridges trust into Entra.
Human? Think delegation.   Workload? Think its own identity.
boundary

This is a decision aid, not a complete OAuth catalog. Device Code, On-Behalf-Of, certificate credentials, federated credentials and other patterns exist. The point is to establish the first branch correctly before adding detail.

— PART 2 · OAUTH2 FROM FIRST PRINCIPLES —

2 Authorization Code Flow — a human is involved

the problem

A user wants to sign in to an application, and the application may also need permission to call an API on that user's behalf. We do not want the application collecting the user's Microsoft password.

Rebuild it without OAuth vocabulary

  1. The app sends the user to a trusted identity provider.
  2. The identity provider authenticates the user.
  3. Instead of throwing a powerful access token around in a redirect, it sends back a short-lived code.
  4. The proper client redeems that code at the token endpoint.
  5. The access token is then used against the API.

Case A — confidential server-side web app

1–3
The app does not collect the Microsoft password. The browser is redirected to Entra, where the user authenticates.
4–5
Entra redirects the browser back to the registered callback with a short-lived authorization code.
6–7
For this confidential server-side pattern, the server redeems the code at the token endpoint and receives tokens. Client authentication can use a secret or certificate; PKCE can also protect the code exchange.
important correction

Authorization Code Flow is not only a server-side flow. SPAs, mobile apps and desktop apps can also use it. The difference is whether the client can safely keep a credential.

Case B — SPA / public client

KEY DIFFERENCE
The SPA itself redeems the code, so tokens can exist in the browser. There is no client secret in browser JavaScript.
WHY PKCE?
The challenge/verifier pair binds the authorization-code exchange to the client that started it.
Confidential web appSPA / public client
Can safely hold app credential?Yes — server sideNo
Client secret / certificateMay authenticate client with secret or certificateNever place one in the browser

break it

What if I put a client secret in JavaScript? It is no longer a secret. Anyone who can inspect the client can obtain it.

What if somebody steals only the authorization code in a PKCE flow? They still need the matching verifier to redeem it.

Say it simply: Authorization Code Flow separates user interaction from token issuance. PKCE binds the code to the client that started the flow. Confidential clients can additionally prove their own identity with a server-held credential.

3 Client Credentials — no human is present

the problem

APIM, a daemon, Function, scheduler or backend service needs to call another API while nobody is sitting at a browser. So the workload must act as itself, not pretend to be a user.

Fundamental facts

There is no human approval screen at runtime.

The caller needs its own identity.

Entra must have some way to trust that caller.

The API must decide what that application identity is allowed to do.
1 · AUTHENTICATE WORKLOAD
The service proves its own identity using a credential mechanism such as Managed Identity, certificate, secret, or federation.
2 · GET TOKEN
Entra issues an access token containing the application identity and granted authorization claims.
3 · CALL API
The API validates the token and enforces its own authorization rules.
setup vs runtime

Setup: define what application permissions exist and grant the caller only what it needs.

Runtime: caller authenticates → Entra issues a token → API validates the token and enforces the granted application permission, commonly represented by app roles in the roles claim.

boundary

Managed Identity does not replace OAuth. It replaces the burden of storing a client secret or certificate for supported Azure workloads. Entra still issues an access token, and the target API still validates and authorizes that token.

OAuth2 vs OIDC — keep the jobs separate

OAuth 2.0: obtain authorization to access a resource. OIDC: adds an identity layer for user sign-in, including an ID token describing the authenticated user to the client.
Access token → for the API.    ID token → for the client application.
— PART 3 · APP SERVICE WITHOUT THE MYTHS —

4 App Service, Functions and Logic Apps Standard

the problem

You want Microsoft to run application code or workflows without giving you a VM to patch, IIS to maintain or an operating system to own. Azure therefore provides managed hosting layers.

The useful mnemonic

Your original picture — App Service underneath, Web App / Function App / Logic Apps Standard above — is useful for remembering the family resemblance. Just do not interpret it as “all three are literally the exact same runtime.”

MEMORY MODEL
These services share App Service platform capabilities, but each hosts a different runtime and programming model.
LOGIC APPS STANDARD
It uses the Functions extensibility model, which is why it inherits important App Service / Functions hosting characteristics.
Say it simply: Web Apps, Functions and Logic Apps Standard live in the App Service/Functions hosting ecosystem. They inherit many of the same platform capabilities, while the runtime sitting above the platform differs.

5 Kudu — why a second site exists

the problem

With your own Windows server you might RDP to the machine, inspect files, run commands and deploy software. App Service deliberately does not give you that kind of machine ownership. Yet operators and deployment tooling still need a management surface.

Rebuild the solution

I need my application endpoint.

I also need deployment / diagnostics / console capabilities.

Those are different jobs.

Therefore a managed PaaS can expose a separate companion management site.
MAIN SITE
This is the runtime surface your application or API clients normally call.
SCM SITE
Kudu is the companion management/deployment surface. Treat runtime, SCM, and Azure management APIs as separate paths when troubleshooting.
terminology correction

Do not memorize “Kudu is a sidecar.” Microsoft describes Kudu as a companion app created for an App Service app and exposed through the SCM endpoint. “Sidecar” has a more specific meaning in container/Kubernetes architecture and creates the wrong picture here.

break it

What if the main application endpoint is reachable but the SCM endpoint is blocked? Application traffic can still be conceptually separate from deployment/management access; however, deployment or troubleshooting methods that depend on SCM/Kudu can fail.

What if I protect the application with authentication? Do not assume every management path behaves identically. Treat runtime traffic, SCM access, Azure control-plane operations and workflow callback APIs as separate paths and verify the exact path involved.

— PART 4 · LOGIC APPS STANDARD AUTH —

6 APIM → Logic Apps Standard: two separate questions

the trap

It is easy to mix two directions together:

  • Inbound: how does APIM prove it may trigger the Logic App?
  • Outbound: how does the Logic App prove its identity when it calls Service Bus, Key Vault, Storage or another API?

They are different security problems.

INBOUND
APIM must satisfy the Request trigger's protection model — for example a SAS callback URL or Entra/Easy Auth configuration.
OUTBOUND
After the workflow starts, the Logic App can use its own Managed Identity to call supported downstream resources.

Inbound option 1 — SAS callback URL

A Request trigger can expose a generated callback URL containing a signature. Possession of that signed URL is the credential used to invoke the trigger. Treat it as a secret: store it securely, avoid logging it, and rotate when needed.

Inbound option 2 — Microsoft Entra / Easy Auth

For a Standard workflow that starts with the Request trigger, App Service / Azure Functions authentication (“Easy Auth”) can protect inbound calls. A caller such as APIM can use an Entra identity — including a managed identity when the configuration supports the intended audience — to obtain a bearer token and call the protected endpoint.

what not to memorize

Do not memorize the blanket statement “Easy Auth locks Kudu and therefore breaks listCallbackUrl, run history and deployment.” Kudu/SCM, Azure management APIs, workflow callback operations and runtime HTTP requests are distinct surfaces. Security and networking settings can interact, but diagnose the actual path instead of assuming one universal failure mechanism.

Outbound — Managed Identity is the natural default

Once the workflow is running, a Standard Logic App can use its system-assigned or user-assigned managed identity for supported connectors/actions to access Entra-protected Azure resources. That removes stored credentials from the workflow.

Inbound asks: who may trigger me?    Outbound asks: who am I when I call the next thing?
— PART 5 · AKS IDENTITY, CORRECTLY —

7 AKS has Azure identities — and pods have Kubernetes identities

the problem

A pod running your microservice needs to read Key Vault or send to Service Bus. Kubernetes can identify the workload with a ServiceAccount, but Microsoft Entra does not automatically treat every Kubernetes ServiceAccount as an Azure identity.

First remove a common misconception

AKS itself is absolutely an Azure resource. The AKS cluster uses Azure identities for cluster operations. The federation question appears specifically at the workload/pod layer, because the pod starts with a Kubernetes ServiceAccount identity.
1 · KUBERNETES KNOWS THE POD
The workload starts with a ServiceAccount identity and projected OIDC token.
2 · FEDERATION ESTABLISHES TRUST
Entra is configured to trust a specific issuer, ServiceAccount subject, and audience for a specific Entra identity.
3 · ENTRA ISSUES AZURE TOKEN
The workload exchanges its projected token for an Entra access token and then calls the protected resource.

Rebuild the mechanism

  1. The pod runs as a Kubernetes ServiceAccount.
  2. AKS exposes an OIDC issuer and provides a projected ServiceAccount token to the workload.
  3. A Federated Identity Credential tells Entra which issuer + subject + audience it should trust for a particular Entra identity.
  4. The Azure Identity library uses the projected token to obtain an Entra access token.
  5. The workload uses that access token against Key Vault, Service Bus, Storage or another protected API.
the corrected sentence to remember

APIM can have a Managed Identity directly because the APIM resource can be assigned an Azure identity. A pod starts with a Kubernetes ServiceAccount identity, so Workload Identity federation maps trust from that Kubernetes identity to an Entra identity.

another important boundary

Do not say “AKS uses federation instead of Managed Identity.” A federated Kubernetes workload can target a user-assigned managed identity or an Entra application. Meanwhile, the AKS cluster itself also uses Azure identities for cluster operations. The correct distinction is cluster identity vs workload identity.

Why federation exists

Plain English: Kubernetes already knows who the pod is. Azure already knows how to authorize Entra identities. Federation is the agreement that lets Azure trust a specific Kubernetes identity without giving the pod a long-lived secret.
break it

What if the ServiceAccount subject does not match the federated credential? Entra should not accept that workload identity.

What if the audience is wrong? The token exchange fails because the presented token does not match the trust configuration.

What if federation works but the Entra identity has no RBAC/data-plane permission on Key Vault or Service Bus? Authentication can succeed and authorization can still fail.

Interview-length explanations

authorization code

“When a human signs in, I normally think Authorization Code Flow. The user authenticates with Entra, the client receives a short-lived code, and that code is redeemed for tokens. PKCE protects the code exchange. A server-side confidential client can also authenticate itself with a secret or certificate, while a SPA cannot safely hold one.”

managed identity

“Managed Identity is how an Azure workload can authenticate to Entra without me storing an application credential. It doesn't remove tokens or authorization — Entra still issues an access token, and the target still enforces permissions.”

AKS workload identity

“The AKS cluster and the pod are different identity layers. The cluster can use Azure managed identities for Azure operations. A pod starts with a Kubernetes ServiceAccount; Workload Identity uses OIDC federation so Entra can trust that specific ServiceAccount and issue Azure access tokens without a long-lived secret.”

Kudu

“Kudu is the companion SCM site App Service creates for deployment and operational tooling. My app traffic goes to the main site; Kudu lives on the .scm.azurewebsites.net endpoint. I treat runtime, SCM and Azure management paths as separate surfaces when troubleshooting access.”
