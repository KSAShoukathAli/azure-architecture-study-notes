Reliability & Idempotency Patterns

architect reference notes
Architect rule: do not ask whether the platform guarantees exactly-once in isolation. Ask what happens if the sender, broker, consumer, database, or acknowledgement fails at every boundary.

1 The reliability model

Distributed reliability is mostly about ambiguous outcomes. The caller often knows only that it did not receive a successful acknowledgement. That does not prove the remote operation did not happen.

At-least-once delivery chooses possible duplicate processing over silent message loss.

3 Retry is for transient faults, not every fault

  • Prefer exponential backoff with jitter for shared cloud dependencies.
  • Keep retries finite and aligned to the caller's end-to-end time budget.
  • Do not retry unchanged 400-series validation/authentication failures merely because they failed.
  • Ask whether the operation is safe to repeat before enabling retries.
Logic Apps default

For most operations that support retry policies, the default is exponential with up to 4 retries. That means up to 5 total attempts: the original call plus 4 retries. Several operations use different defaults, so inspect the connector/action rather than assuming.

timeout budget

A retry policy is only safe when the whole downstream attempt budget fits inside the upstream budget. Current examples: APIM forward-request values above 240 seconds might not be honored; Logic Apps Standard built-in HTTP has a 225-second request timeout; an HTTP-triggered Function cannot return a response after about 230 seconds; Service Bus PeekLock starts with a 1-to-5-minute entity lock and can renew it. An outer timeout does not prove the inner operation stopped.

4 Retry storms and retry budgets

Microsoft's current transient-fault guidance explicitly warns against cascading retries. Be precise about retries vs attempts: if each layer makes 3 total attempts, two layers can create 3 x 3 = 9 dependency calls. But Logic Apps' common default of 4 retries means 5 total attempts; if the next layer makes 3 attempts, one incoming request can become up to 15 dependency calls. A retry budget limits aggregate retry pressure, not only retries per request.

5 Retry vs circuit breaker

Retry
"This failure may clear soon. Try again carefully."
Circuit breaker
"This dependency is unhealthy. Stop calling it for now."
Queue / delayed work
"The business action can wait. Decouple it from the caller."

A circuit breaker protects a dependency from repeated calls when failures are no longer transient. In queue-driven designs, broker retry and DLQ behavior can already provide failure isolation, so do not add a circuit breaker mechanically.

Queue-Based Load Leveling
Put a durable queue between bursty intake and a slower dependency. Consumers drain at a controlled rate instead of forwarding the burst directly.
Bulkhead
Isolate pools of concurrency, connections, queues, or compute so one failing dependency cannot exhaust resources needed by unrelated flows.
APIM

API Management backend entities support a circuit breaker that can stop forwarding to an unhealthy backend and return 503 while the circuit is open. It can honor Retry-After. Current limitations include no backend circuit breaker in the Consumption tier, one rule per backend, and approximate tripping because gateway instances do not synchronize breaker state.

6 Idempotency: same command, same business effect

Naturally idempotent: set status to Cancelled, upsert a known resource version, replace a value.

Artificially idempotent: charge card, create shipment, submit prescription, send partner order. These usually need an idempotency key plus durable state that records the outcome.

do not conflate

Correlation ID answers "which journey is this?" Idempotency key answers "is this the same logical operation I already applied?" They can be related, but they are not automatically the same identifier.

7 Designing an idempotency key

Good key propertyWhy
Stable across retriesThe retry must reproduce the same key.
Scoped to one business operationRX-4182:submit is safer than using an entire customer-level correlation ID.
Opaque and non-sensitiveDo not use MRN, patient name, or PHI as the dedupe key.
Uniqueness enforced durablyA database unique constraint or conditional write closes concurrent races.
Retention matches retry/replay horizonDeleting dedupe state too early allows an old replay to apply again.
healthcare protocol identifiers

NCPDP SCRIPT: MessageID is a unique transmission trace identifier and RelatesToMessageID links later messages to the conversation. Those are valuable dedupe/correlation inputs, but a transmission ID is not automatically the business idempotency key if a retry can create a new transmission. Keep the logical prescription operation in view too.

X12: ISA13, GS06, and ST02 are protocol control numbers. Logic Apps X12 receive agreements can explicitly disallow duplicate interchange, group, and transaction-set control numbers. This is protocol-level duplicate protection; downstream business effects still need the right idempotency boundary.

HTTP boundary

For non-idempotent POST operations, require a client-supplied Idempotency-Key (APIM can enforce that the header exists), persist the key with the operation result, and return the existing result/status resource when the same key arrives again. For long-running work, prefer 202 Accepted + Location/status endpoint so the client can query the original operation instead of guessing after a timeout.

8 Idempotent Consumer pattern

The strongest implementation writes the dedupe marker and the business state change in the same local transaction. A "check then act" query without a uniqueness guarantee is race-prone when two consumers process the duplicate concurrently.

9 Service Bus duplicate detection is sender-side protection

  • Supported in Standard and Premium, not Basic.
  • Tracks application-controlled MessageId.
  • Window: default 10 minutes, minimum 20 seconds, maximum 7 days.
  • Larger windows cost throughput because more IDs must be matched.
boundary

Broker duplicate detection protects repeated sends. It does not stop a successfully enqueued message from being delivered again after a consumer crash or lock loss. You still need an idempotent consumer.

10 PeekLock: side effect before Complete means redelivery is possible

PeekLock gives at-least-once delivery. Receive-and-delete gives at-most-once behavior and can lose work if the consumer crashes after receipt. For business-critical integration, PeekLock plus idempotent processing is usually the safer default.

Service Bus lock duration defaults to 1 minute and can be configured up to 5 minutes; longer processing requires lock renewal. Oversized prefetch can increase lock-expiry risk.

11 DLQ is a quarantine, not a retry loop

A poison message should stop consuming runtime capacity. Dead-letter it with enough context to diagnose the reason. Service Bus automatically moves a message after max delivery attempts; the default is 10. Messages in the DLQ remain until explicitly received and completed.

replay discipline

Do not bulk replay a DLQ into the same unchanged failure. Fix the cause, validate idempotency, then replay in controlled batches with correlation and audit.

12 Local transactions solve local atomicity - not distributed atomicity

Service Bus transactions are supported in Standard and Premium, not Basic. The normal transaction scope groups supported operations against a single messaging entity; the receive itself is not part of that scope. For an atomic handoff such as Complete on queue A + Send to queue B, use Service Bus cross-entity transactions, implemented through the send-via / transfer mechanism. SQL, Cosmos DB, and other external resources do not enlist automatically. Operations inside a Service Bus transaction are not automatically retried, and the transaction times out after 2 minutes.

13 Transactional Outbox and Inbox

Outbox solves the producer dual-write problem: commit business state and the event record in the same local database transaction, then relay later.

Inbox / processed-message table solves receiver duplicate execution: persist the consumed operation key alongside the business update.

Cosmos DB example

Microsoft's current Cosmos DB pattern uses a TransactionalBatch to write state + event in one logical partition, then the change feed relays events. The relay is still at-least-once, so downstream consumers remain idempotent.

SQL shape

For SQL-backed healthcare integrations, put the business row change and an Outbox row in the same SQL transaction. A relay later publishes pending outbox rows, using polling or a change stream/CDC-style mechanism where appropriate. Mark publication state durably. Assume the relay can publish more than once, so the broker message identity and downstream consumer remain idempotent.

15 Azure Functions: trigger retry is not one universal mechanism

current behavior

Functions has both trigger-extension behavior and runtime retry policies. Current runtime retry policies apply to Cosmos DB, Event Hubs, Kafka, and Timer triggers. Service Bus reliability is primarily driven by the Service Bus extension and broker settlement/DLQ semantics.

best effort max retries

Runtime retry counts are not a hard end-to-end execution limit. If a Functions instance fails between retry attempts, the in-memory retry count can be lost. For Event Hubs, a new instance can resume the batch with its retry count reset, so an invocation can occur more times than the configured maximum.

For Service Bus-triggered Functions, poison-message handling belongs to Service Bus. A handler exception before successful settlement can cause redelivery. This is why application idempotency and broker settlement behavior must be designed together.

Do not translate "the Function retried" into "the business effect happened once." Those are different guarantees.

16 Event Grid and Event Hubs reliability

Event Grid
Delivery is retried with exponential backoff for eligible failures. Some configuration errors are not retried. Without dead-lettering, undeliverable events can be dropped. Duplicate delivery is still possible.
Event Hubs
Designed for at-least-once event processing at scale. Checkpointing controls resume position. After crashes or checkpoint gaps, events can be processed again, so consumers must be idempotent.
Event Grid

Current delivery guidance says the endpoint gets about 30 seconds to respond. Retry timing is best effort and extends up to 24 hours. Configure dead-lettering when event loss is unacceptable.

Event Hubs head-of-line effect

With Functions runtime retries, the Event Hubs checkpoint is not written until the retry policy for the current execution finishes. Progress on that partition pauses behind the failing batch. Keep retry counts bounded and decide explicitly whether poison handling belongs inside the function, in a quarantine store, or in an operational pause/replay process.

17 Saga and compensation

A saga coordinates local transactions across services. If a later step fails, compensation applies domain-specific actions such as cancel reservation, void authorization, or issue refund. Compensation can itself fail, so its progress must also be durable and idempotent.

Use Durable Functions, Logic Apps stateful workflows, or an application orchestrator when central coordination helps. Choreography is viable too, but failure ownership and compensation become more distributed.

18 Ordering, stale messages, and version checks

Idempotency handles duplicates, but it does not automatically solve out-of-order delivery. A stale event can still overwrite newer state.

NeedPattern
Per-key FIFOService Bus sessions with a stable SessionId.
Reject stale updatesVersion / sequence / ETag check before applying.
Event stream replayTrack last processed sequence per consumer/projection.
Concurrent writesOptimistic concurrency rather than broad distributed locking where possible.

19 Replay is a product feature, not an emergency script

A production replay path should preserve original identifiers, record who/what replayed the item, control rate, and support reconciliation. Reprocessing is dangerous if the original side effect may already have happened.

Reconciliation is the final safety net

Idempotency, DLQ handling, retry, and replay reduce error, but they do not prove two independent systems ended in the same state. In pharmacy, claims, and partner integration, run a reconciliation process that compares authoritative business identifiers/counts/statuses across systems and produces an exception list for missing, duplicated, or mismatched outcomes. Reconciliation detects what online processing missed; it should not silently mutate production state without an auditable remediation path.

20 Architect checklist

  • What can fail after the remote side has already committed?
  • Which errors are transient, permanent, poison, or ambiguous?
  • Which layer owns retry? Are retries duplicated across layers?
  • What is the retry time budget and aggregate retry budget? Do downstream timeouts fit inside the caller budget?
  • What is the stable idempotency key for each non-idempotent business action? Which protocol IDs are only correlation/transport IDs?
  • Where is dedupe state stored, and is uniqueness enforced atomically?
  • Does sender-side broker dedupe exist, and what is its window?
  • Can consumer redelivery still occur? Assume yes unless proven otherwise.
  • What happens after max attempts? DLQ, failed workflow, or manual remediation?
  • How are DB state and event publication made consistent?
  • What is the compensation strategy for a partially completed business process?
  • What is the replay process, and how do you prevent replay from duplicating effects?
  • How are ordering and stale updates handled separately from duplicates?
  • Where do bulkheads or queue-based load leveling protect a weak dependency?
  • What reconciliation proves both sides reached the intended business state?
  • What telemetry proves retries, duplicate suppression, DLQ growth, and replay outcomes?
