Reliability & Idempotency Patterns

Feynman way of understanding
A request times out. The caller knows it did not get an answer. But did the other system already do the work?
1. Find ambiguity
2. Predict failure
3. Derive guarantee
4. Break the model
5. Repair it

1 Start with the uncomfortable scenario

If you retry blindly, you might submit twice. If you refuse to retry, you might lose a legitimate request. This is the basic reliability problem.

predict

The partner charged the card, but your process crashed before saving "payment succeeded." Which system is wrong?

Answer: neither is necessarily wrong. You created two independent commits with no shared atomic boundary.

2 Why at-least-once exists

Service Bus PeekLock follows the second model. It removes the message only after you settle it successfully. If your process dies first, the message returns. That is not a bug. That is the reliability contract.

3 So derive idempotency

Suppose the logical command is:

SubmitPrescription RX-4182

The system needs a durable way to recognize that exact logical operation again:

IdempotencyKey = "SubmitPrescription:RX-4182"

Idempotent does not mean "run once." It means "run again and the business state does not change again."

healthcare reality

Sometimes the protocol gives you useful IDs. NCPDP SCRIPT has MessageID and RelatesToMessageID; X12 has ISA13, GS06, and ST02. But ask what each ID means. A transmission/correlation ID is not automatically the logical business-operation key. The question is still: would the same real-world action produce the same durable key when it is retried?

4 The naive dedupe check breaks under concurrency

if (!AlreadyProcessed(key)) {
    ApplyBusinessEffect();
    SaveProcessed(key);
}

Two workers can both check before either saves the key.

The repair is a durable uniqueness constraint or conditional write plus an atomic business update. Let the data store decide which duplicate wins.

5 Why broker duplicate detection is not enough

Duplicate send
Producer is unsure whether Service Bus accepted the send. Same MessageId can be discarded within the configured duplicate-detection window.
Duplicate processing
Consumer applied the side effect, crashed before Complete, and receives the same stored message again. Broker send dedupe cannot prevent this.
break the model

Duplicate detection window is 10 minutes. You replay the same business event two days later using the same MessageId. What happens?

Answer: the broker's old dedupe memory has expired. Consumer-side idempotency still has to protect the business effect.

6 Retries can make outages worse

Retry is not courage. Sometimes the reliable thing is to stop calling the dependency and give it room to recover.

And count carefully: 4 retries means 5 attempts. If another layer then makes 3 attempts, one business request can become 15 downstream calls.

structural fix for HTTP ambiguity

For a long-running POST, stop holding the caller open. Accept a stable Idempotency-Key, return 202 Accepted with a status URL, and let the caller query that same operation. A repeated key returns the existing operation/status instead of creating a second one.

7 Poison is different from transient

Transient: "same input may succeed later."
Poison: "same input will keep failing until something changes."

Retries are useful for the first. Repeating the second only wastes capacity.

8 The dual-write trap

Your service needs to:

  1. save the prescription status, and
  2. publish PrescriptionSubmitted.

If they are separate commits, a crash can occur between them.

The outbox does not create magic exactly-once delivery. It removes the dangerous gap between business state and the intent to publish.

In a SQL-backed integration, that usually means one database transaction writes both the business change and an Outbox row. A separate relay polls or consumes change information and publishes later. The relay itself can repeat, so the consumer still needs idempotency.

9 Compensation is not rollback

Imagine three steps completed in different systems:

Reserve medication stock
Authorize payment
Create shipment

If shipment fails, there is no database rollback spanning those systems. You issue new business commands:

Void payment authorization
Release stock reservation
predict

What if "void payment" times out?

Answer: compensation itself needs retries, durable progress, and idempotency. Recovery logic is production logic.

10 Exactly-once is usually a boundary claim

If documentation says duplicate detection provides "exactly once delivery" within a broker window, read the boundary carefully. That does not prove your external API call, SQL write, email, prescription submission, or shipment happened exactly once.

And there is one more layer: reconciliation. At the end of the day, compare authoritative business outcomes across systems. Reliability controls prevent many errors; reconciliation finds the exceptions that still escaped.

11 Break the model scenarios

scenario 1

A Service Bus Function updates SQL successfully, then crashes before the message is completed. What protects SQL from the redelivery?

Model answer: an idempotent write or dedupe record committed atomically with the SQL change.

scenario 2

Logic Apps HTTP action has the default retry policy. The partner's POST creates a new row every time. What is wrong?

Model answer: retry was enabled at a non-idempotent boundary with no operation key or status lookup.

scenario 3

You enable Service Bus duplicate detection and remove consumer dedupe. Safe?

Model answer: no. Sender duplicates and consumer redelivery are different failure modes.

scenario 4

A poison message keeps cycling from DLQ back to the queue every five minutes. Reliable?

Model answer: no. That is automated repetition of a known failure, not recovery.

scenario 5

Event Hubs replays a batch after a checkpoint gap. Your consumer sends an email per event. What happens?

Model answer: duplicate side effects unless the consumer tracks processed event identity or models the side effect idempotently.

scenario 6

APIM gives up before a slower inner call has actually stopped, and the caller retries. What can happen?

Model answer: two operations can overlap. Timeout is not cancellation. Align nested timeout/retry budgets or redesign the operation as asynchronous request-reply.

12 Final mental model

Reliable systems do not eliminate failure. They turn failure into a bounded, observable, repeatable recovery path.
