Azure App Service - Reference Notes

platform model - app types - config - plans - scaling - networking - deployment - health
Fast model: the plan is the compute, the app is the behaviour. Price, scale, zone redundancy, and shared limits come from the plan. Settings, identity, networking, and deployment are configured per app.

1 Platform model

TermWhat it isArchitect note
App Service planThe set of VMs (instances) you pay for. Sets OS, region, tier, size, and instance count.The unit of cost, scale, and blast radius.
Instance / workerOne VM in the plan. Runs a copy of every app in the plan.Apps on the same plan compete for its CPU and memory.
App (site)A Web App, Function App, or Logic Apps Standard app. Has its own host name, settings, identity, and network config.Configuration is per app. Compute is per plan.
Front endsShared load balancers that terminate TLS and route requests to the right app.Your app receives plain HTTP from the front end. TLS never reaches your code.
Deployment slotA second live copy of an app (staging) on the same plan.Slots consume the same plan resources as production.
SCM / Kudu siteThe <app>.scm.azurewebsites.net endpoint used for deployment and diagnostics.Has its own access restrictions. Lock it down separately.
App Service Environment (ASE v3)A single-tenant App Service deployment inside your VNet. Uses Isolated v2 plans.Dedicated and private by design. Higher base cost.

2 The app types

All three are built on the same host. Each layer adds a runtime and a file.

App typeWhat runsWhat you writeSupported hosting
Web AppYour ASP.NET Core (or other stack) web app, as code or a container.The whole application: startup, routing, middleware.App Service plan (Free to Premium v4), Isolated v2 in an ASE.
Function AppThe Functions host (ASP.NET Core + WebJobs runtime). In .NET isolated, your code runs in a separate worker process, called by the host over gRPC.Handlers with triggers and bindings.Flex Consumption, Consumption, Elastic Premium, Dedicated (App Service plan), Container Apps. See the Functions reference.
Logic Apps StandardThe Functions host plus the workflow extension. Workflows run inside the host process.Workflow definitions (workflow.json), optional custom code.Workflow Standard (WS1-WS3) or an ASE v3 Windows plan. Not an ordinary App Service plan.
WebJobsA background program that runs alongside a Web App on the same instances.A console program or script.Same plan as its Web App.
hosting boundary

A Function App and a Web App can share one Dedicated plan. A Logic Apps Standard app cannot join them on an ordinary App Service plan. It always gets its own Workflow Standard plan, unless you run an ASE v3.

4 Plans and tiers

The tier decides which features exist. Features then get switched on per app.

TierUse it forWhat it adds
Free / SharedExperiments only.Shared compute, no SLA, no VNet features, no custom scale.
BasicDev/test and small internal apps.Dedicated instances, Always On, VNet integration and private endpoints. Manual scale only, no slots.
StandardSmall production.Autoscale rules, deployment slots.
Premium v3 / v4Production default.More slots and instances, zone redundancy, automatic scaling, larger and memory-optimized sizes. v4 is the newest generation, in select regions.
Isolated v2 (ASE v3)Single-tenant, network-isolated, high scale.Runs inside your VNet. Dedicated front ends and workers.
Plan familyBilling modelWho uses it
App Service plan (Dedicated)Per instance, per second, whether busy or idle.Web Apps, Function Apps on Dedicated.
Elastic Premium (EP1-EP3)Per instance, with always-ready and prewarmed instances.Function Apps.
Flex Consumption / ConsumptionPer execution and memory time. Scales to zero (Flex can keep always-ready instances).Function Apps.
Workflow Standard (WS1-WS3)Per instance, reserved capacity. Managed connector calls and storage transactions billed on top.Logic Apps Standard.
cost rule

The app type does not set the price. The plan does. A Function App and a Web App on the same Dedicated plan cost the same. The difference is which plans each is allowed to use.

5 Scaling

MechanismHow it decidesWhereNote
Scale upYou pick a bigger size or tier.All tiersMoves the whole plan. May restart apps.
Manual scale outYou set the instance count.Basic and upFixed capacity.
Autoscale (Azure Monitor)Your rules: CPU, memory, HTTP queue length, schedules, or a metric from another resource such as Service Bus message count.Standard and upQueue-based scaling is possible, but only if you write the rule. Coarse and slow compared with the Functions scale controller.
Automatic scalingThe platform watches HTTP traffic. No rules. Maximum burst up to 30 instances, per-app limits, prewarmed instances.Premium v2 to v4HTTP only. Not a signal for queue backlogs. Not supported for slot traffic.
Functions scale controllerWatches trigger sources directly (queue depth, event lag).Flex, Consumption, Elastic PremiumThe event-driven option. Not available on a Dedicated plan.
shared plan

Scaling is per plan. A noisy app pulls every neighbour up with it, and a starved plan slows every app on it. Use per-app scaling limits, or give workloads with different load curves their own plans.

  • Always On (Basic and up): keeps the app loaded. Without it, an idle app unloads after about 20 minutes and timer or queue triggers on a Dedicated plan stop firing.
  • Zone redundancy: Premium v2 to v4 and Isolated v2. The platform enforces a minimum of two instances and spreads them across zones. No extra meter, but you pay for the minimum instances.

6 Networking

DirectionFeatureWhat it doesArchitect note
InboundAccess restrictionsAllow or deny by IP, service tag, or service endpoint subnet. Can match headers such as X-Azure-FDID for Front Door.Keeps a public endpoint but filters it. Set rules for the SCM site too.
InboundPrivate endpointGives the app a private IP in your VNet. Basic tier and up.Needs the privatelink.azurewebsites.net private DNS zone. Disable public access to make it truly private.
OutboundVNet integration (regional)Routes the app's outbound calls through a delegated subnet in the same region. Basic tier and up.Outbound only. It does not make the app private. Size the subnet for scale-out: every instance takes addresses.
OutboundRoute all trafficSends all outbound traffic, not just private (RFC1918) ranges, into the VNet.Needed for firewall inspection or NAT gateway on internet-bound calls. NSGs and UDRs on the subnet then apply.
OutboundNAT gatewayAttached to the integration subnet. Gives a static outbound IP and a much larger SNAT pool.The fix for partner IP allow-lists and SNAT exhaustion.
OutboundHybrid ConnectionsReaches a single host:port on-premises through a relay agent.Narrow and simple. Not a network.
BothASE v3The whole environment lives in your subnet.No private endpoint or VNet integration needed. Already inside.
SNAT

Outbound connections to public endpoints use SNAT ports, about 128 preallocated per instance, shared by every app on that instance. A new HttpClient per call exhausts them fast, and the neighbour apps fail too. Fix it with connection reuse, private endpoints to Azure services, or a NAT gateway.

7 Identity and security

FeatureWhat it doesArchitect note
Managed identitySystem-assigned (tied to the app's life) or user-assigned (shared, survives the app).Per app, not per plan. The default way to reach Key Vault, Service Bus, Storage, and SQL.
App Service Authentication (Easy Auth)Validates tokens at the platform before requests reach your code.A second check behind APIM, so a leaked URL alone is not enough.
TLS settingsHTTPS only, minimum TLS version, optional client certificates.TLS terminates at the front end. Client certificates arrive as a header.
Basic auth / FTPLegacy publishing credentials.Disable both. Deploy with Entra ID and the pipeline's identity.

8 Deployment and slots

TopicReference
Package deployZip deploy, preferably run-from-package (WEBSITE_RUN_FROM_PACKAGE), so the site runs from an immutable package.
SlotsStandard tier and up. More slots on Premium. Each slot is a full app on the same plan.
Swap sequenceTarget slot settings are applied to the source, instances restart and warm up, then routing flips. A failed warm-up cancels the swap.
Warm-upUse a warm-up path (applicationInitialization on Windows) or Health check so the swap waits for a ready app.
Swap with previewPause after settings are applied. Test, then complete or cancel.
RollbackSwap back. The previous version is still sitting in the staging slot.
slot rule

Anything environment-specific (endpoints, feature flags, queue names) must be a sticky slot setting. Anything the code needs to change with the release travels with the swap.

9 Reliability and health

Feature or limitBehaviourArchitect note
Health checkPings a path on every instance. After 10 failed pings (non 2xx), the instance leaves the load balancer. If it stays unhealthy for one hour, it is replaced.A single-instance app is never pulled from rotation. Run two or more instances.
Request timeoutThe front end returns a timeout if the app sends nothing for about 230 seconds (240 on Linux). Not configurable.Long work goes async: return 202, process from a queue, expose status.
Zone redundancyPremium v2 to v4, Isolated v2. Minimum two instances, spread across zones.Protects against a zone outage, not a region outage.
Auto-healRecycles the process on rules: slow requests, memory, status codes.A safety net, not a fix. Find the leak.
ARR affinitySticky sessions via cookie. On by default.Turn it off for stateless APIs so load spreads evenly.
Platform upgradesInstances restart periodically for patching.Design for restarts: at least two instances, idempotent handlers, graceful shutdown.

11 Choosing a service

NeedStart withWhy
One coherent application: shared code, shared state, one releaseWeb App (or AKS)You own the request handling and lifecycle.
Independent reactions: "when X arrives, do Y"Function AppThe runtime owns triggers, scaling, and retries.
Long waits, callbacks, many partner endpoints, run history for supportLogic Apps StandardThe workflow is the product. Push dense parsing behind it.
Many services, sidecars, mesh, full network control, a platform teamAKSA hosting and operations choice. The same ASP.NET Core code runs on either.
Choose the workload shape first. Then choose the plan by load.

12 Failure checklist

SymptomCheck first
Intermittent outbound failures under load, neighbour apps also failingSNAT exhaustion. Look for per-call HttpClient. Add connection reuse, private endpoints, or a NAT gateway.
Private endpoint set up, app still resolves to a public IPPrivate DNS zone privatelink.azurewebsites.net not linked to the caller's VNet, or custom DNS not forwarding.
App cannot reach a private resourceVNet integration missing, route-all off, NSG or UDR on the integration subnet, or DNS for the target.
New instances fail after scale-outIntegration subnet out of addresses.
Timer or queue work stops overnight on a Dedicated planAlways On is off.
Requests fail at about 4 minutesThe 230-second front-end timeout. Make the operation async.
Production uses staging values after a swapSetting was not marked as a sticky slot setting.
Key Vault reference shows an errorManaged identity lacks access, or the vault is private and the app has no network path to it.
Queue backlog grows, plan does not scaleDedicated plans scale on rules. Add a Service Bus metric rule, or move the consumer to Elastic Premium or Flex.
One app slows every other appShared plan. Split the plan or set per-app limits.
