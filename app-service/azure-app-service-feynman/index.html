App Service, from the problem up

You want to run code that answers the world, and you don't want to own a server. Everything in this page follows from that one wish.

1. The box you rent

Somebody has to run a VM, patch it, put a web server on it, and terminate HTTPS. App Service is Microsoft doing that part. You drop your code in.

That's the whole product. A pool of Windows or Linux VMs, a front end running IIS or Nginx, and a worker process that hosts your app. Everything else is a flavour of that box.

Web App: you write the whole app. Function App: Microsoft wrote the shell, you write the handler. Logic Apps Standard: the handlers are workflows instead of code.

2. Two doors in

A Web App has one way in. HTTP arrives on 443, your code answers.

A Function App wants more. It wants to run your code when a message lands on a queue, a blob shows up, or the clock hits 2 AM. None of that is HTTP. So Microsoft loaded a library into the host, the WebJobs runtime, and gave it a second door.

So what is the WebJobs runtime?

It's a .NET library, the WebJobs SDK, loaded into the Functions host process at startup. The name comes from WebJobs, an older App Service feature for running background jobs next to a web app. Functions grew out of it.

It does four jobs. It finds your functions and reads their triggers. It sets up whatever each trigger needs, usually a background task. When a trigger fires, it invokes your handler. And it handles the plumbing around that call: connections, retries, poison messages, and bindings that hand you the message already deserialized.

The listeners are just background tasks inside the host. Your code is a different story. In the .NET isolated worker model, which is what you build today, your functions run in a separate worker process. The host receives the trigger, then calls your code over gRPC.

At startup the host scans your functions (or, in Logic Apps, your workflow.json files) and reads each trigger. A trigger tells the runtime when to start a run, and each kind does it differently. An HTTP trigger is just a route on the web host. A timer follows a schedule. A Service Bus trigger holds a connection open and receives messages. Some triggers, like many Logic Apps connectors, poll on an interval.

Then what about the Service Bus send in the middle of a workflow? That creates no listener at all. It's an outbound call. The first time the action runs, it looks up the connection in settings, opens a Service Bus client, and sends.

What goes on the wire depends on the connector. The built-in Service Bus connector uses the Service Bus SDK, which speaks AMQP over TCP (port 5671, or AMQP over WebSockets on 443). The managed connector goes out as an HTTPS call to the connector service, which talks to Service Bus for you. A Blob or partner API call is plain HTTPS. Either way the client or connection is cached and reused for the next run.

Triggers start runs. Actions call out. Settings are the phone book; the trigger is what makes the call.

One naming catch. The settings file is appsettings.json in a Web App. In Function Apps and Logic Apps it's local.settings.json, and that file is for local development only. In Azure, all three read their settings from App Settings, which arrive as environment variables.

The platform itself gives all three the same knobs: app settings as environment variables, deployment slots, managed identity, VNet integration, custom domains and certs, Always On, and health checks.

4. The plan sets the price, not the app type

A Function App on the same plan as a Web App costs exactly the same. You're paying for the VM either way. The difference is which plans each type is allowed on.

App typePlans it can use
Web AppApp Service Plan only (Basic, Standard, Premium v3, Isolated)
Function AppConsumption, Flex Consumption, Premium, or Dedicated (an App Service Plan)
Logic Apps StdWorkflow Standard (WS1-WS3), or an App Service Environment v3. Not an ordinary App Service Plan

Consumption bills per execution and scales to zero. Great for spiky or quiet work. At sustained high volume it gets expensive and reserved compute wins. Utilisation is the crossover.

Plan names matter for networking too. The original Consumption plan can't do VNet integration. Flex Consumption can.

5. Three traps that come from sharing

The plan is shared

Every app in one plan runs on every instance of that plan. Same CPU, same memory. Scale the plan and everything scales together. A Function App and a Web App can share one Dedicated plan, and then they rise and fall together. A Logic Apps Standard app can't join them. It always gets its own Workflow Standard plan (or an ASE v3), so it scales on its own curve.

Autoscale can't see your queue

On an App Service Plan, autoscale reacts to CPU and memory. A growing Service Bus backlog does nothing. Functions Premium and Consumption use a scale controller that watches queue depth directly. Also: without Always On, a Dedicated app unloads after about 20 idle minutes and timer triggers stop firing.

Outbound ports are shared

VNet integration and private endpoints are configured per app. But outbound connections to the internet share each instance's SNAT ports, roughly 128 preallocated per instance.

Eligibility runs as a Function on the same Dedicated plan as the TruePriceRx pricing Web App. The Function creates a new HttpClient per payer call. Each call grabs a port, and closed ports stay reserved for minutes. At 100 checks a second the pool is gone in seconds. Now the pricing app's outbound calls fail with SNAT exhaustion, and nothing is wrong with its own code. Fix: reuse clients, use private endpoints, or add a NAT gateway.

6. Follow one request through

You now have all the pieces. Watch them work together on a single NewRx, from the EHR to Surescripts.

In

The EHR calls APIM. APIM validates the token and forwards to your Web App, HTTP Function, or Logic App HTTP trigger. Here's the catch: APIM checking the token doesn't lock down your app. Your app's own inbound access, a private endpoint or access restrictions plus its own auth, is a separate decision. Skip it and anyone who finds the app's URL walks around APIM.

Compute

The plan supplies the workers, how many there are, how they scale, and the limits they share. Your app or workflow supplies the behaviour. When something is slow, ask which of the two is the problem.

Out

Your app sends to Service Bus, writes to Storage, calls the partner. VNet integration decides the route out. It's a different setting from the private endpoint, and people mix them up constantly.

Failure

Now pull the plug on the worker mid-request. What happens? It depends on the trigger, not on App Service.

An HTTP call just fails, and the caller has to retry. A Service Bus message comes back when its lock expires, and dead-letters after too many attempts. A stateful workflow resumes from its last saved step. A stateless one starts over, or doesn't.

"Where does it run?" is the first question. "Will the business process survive a failure?" is the architect's question.

7. Choosing, as an architect

Ask these in order. Answering the last one first is the classic mistake.

  1. One application or a set of reactions? Shared code, shared state, one deployment lifecycle means an application: Web App, or AKS if you need the control. "When X arrives, do Y" means Functions.
  2. Is orchestration the hard part? Long waits, many inconsistent partner endpoints, run history support teams need to read. If yes, Logic Apps, with the dense parsing pushed behind it.
  3. What's the load shape? Spiky or low: Consumption. Steady and high: reserved compute. Volume picks the plan, not the service.
The coupling test: if the pieces version together, they should deploy together.

And where does AKS fit? A microservice is usually a web API, and the same ASP.NET Core code runs on App Service or in a pod. So AKS isn't a different kind of app. It gives you density, sidecars, a mesh, and full network control. App Service gives you nothing to patch. The service count is only a hint. What really decides it is your networking, scaling, and deployment needs, and whether you have a team to run a cluster.

So should the Prescriptions hot path go through Logic Apps? Maybe not, but look at what you'd be buying. Service Bus durably holds and delivers each message. A stateful workflow does something different: it saves the progress of each run and keeps run history. On ten million messages a day, that progress tracking costs storage transactions and latency. It's worth it only if your support team really needs per-message run history. Stateless workflows skip it. Measure before you decide.

The whole page in six lines

App Service provides managed hosting. Web Apps host applications, Functions run triggered code, and Logic Apps Standard runs workflows on the Functions runtime. Each has its own supported plans and scaling.

A Function App is a web host plus background listeners. In .NET isolated, your code runs in a worker process beside it. Triggers start runs, actions call out.

The plan sets price, scaling, and shared limits like CPU and SNAT ports. Separate plans, separate curves.

Follow a request in, through the plan, and out. Then ask what survives a failure.

Choose by shape: one application, a set of reactions, or an orchestration. Then pick the plan by load.

AKS versus App Service is about who runs the orchestrator, not what your code looks like.
