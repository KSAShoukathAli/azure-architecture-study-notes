Azure Logic Apps - Reference Notes

reference notes - hosting, workflows, connectors, B2B/EDI, identity, networking, durability, concurrency, transforms, observability and deployment
The one-line model: a trigger wakes the workflow, the Logic Apps runtime orchestrates steps, actions/connectors talk to external systems, and state/retry/error policies decide what survives failure. In Standard, also ask where the connector runs, because that determines whether VNet integration applies.
  1. Trigger answers: what event starts the workflow?
  2. Workflow runtime answers: what sequence, branch, condition or retry should happen?
  3. Actions/connectors answer: what external system or protocol does each step call?
  4. State + error policy answer: what survives failure and what happens next?

2 Trigger vs action

A trigger is the event source that creates a workflow run: an HTTP request, timer, Service Bus message, file arrival, webhook, and so on. An action is a step that runs after the trigger: call an API, transform data, send to Service Bus, evaluate a condition, wait, compose JSON, or invoke another workflow.

Think event → run: a trigger does not "call every action." It creates a workflow execution; the runtime then evaluates the workflow graph.

3 Stateful vs stateless (Standard)

Stateful workflows persist operation state and run history, can survive interruption, and support longer-running/asynchronous patterns. Stateless workflows optimize for short, low-latency execution and do not store run history by default.

important boundary

Choose stateful vs stateless at workflow creation. Treat it as an architectural decision, not a runtime toggle. Stateless also does not follow the stateful HTTP asynchronous-operation pattern: a downstream 202 Accepted does not cause the runtime to keep polling the Location URI.

4 Built-in vs shared/managed connectors

This distinction matters most in Standard. Built-in / in-app connectors run natively with the Logic Apps runtime. Many service-provider connectors such as Service Bus, Event Hubs, Blob, SFTP and SQL have built-in versions in Standard. Shared/managed connectors run in Microsoft-managed shared connector infrastructure.

networking consequence

If a Standard Logic App is VNet-integrated, the built-in connector can use that private network path. A shared managed connector does not automatically inherit the Logic App's VNet integration because the connector call originates from the shared connector service, not from your app's runtime process.

5 Inbound authentication vs outbound identity

Do not collapse these into one "authentication" question.

DirectionQuestionTypical mechanisms
InboundWho is allowed to trigger this workflow?Request-trigger SAS callback URL, App Service Easy Auth for Standard Request triggers, APIM in front, IP/network restrictions
OutboundWho is the Logic App when it calls Azure resources?System-assigned or user-assigned Managed Identity, connector-supported Entra auth, connection credentials where needed
preferred pattern

For Azure resources such as Service Bus, Key Vault, Storage, Event Hubs and many others, use Managed Identity where the connector supports it. Grant only the RBAC role the workflow actually needs.

6 Standard networking: inbound vs outbound

For Standard Logic Apps, Private Endpoint is the inbound private-access mechanism. VNet Integration is the outbound mechanism that lets the Logic App runtime reach private addresses/routes in a VNet.

connector trap

VNet Integration helps the Logic Apps runtime and built-in connectors. It does not magically move shared managed connectors into your VNet. When a backend is private, connector type becomes part of the network design.

7 Standard storage is part of the runtime

A Standard Logic App needs a storage provider for runtime artifacts/state. Azure Storage is the normal/default provider. Microsoft also supports SQL-based runtime storage for specific Standard scenarios, but Azure Storage is still part of Azure-region hosting requirements.

why this matters

If you lock the Standard app's backing storage behind private networking, the Logic Apps host itself must still resolve and reach the required storage endpoints. A storage firewall/DNS mistake can look like a Logic Apps deployment or runtime problem.

8 Retries, idempotency and error handling

Most connector operations that support retry policies use a default exponential policy, usually up to 4 retries. You can choose exponential, fixed or no retry where supported.

architect's rule

Retry is not correctness. If the first request succeeded but the response was lost, a retry can perform the business operation twice. Design the target operation to be idempotent, or use an idempotency/correlation key.

Run after and scopes

Use Configure run after to decide whether an action runs after success, failure, timeout or skip. Use Scopes to group operations and implement try/catch/finally-style workflow structure.

Try

Main operations in a Scope.

Do not memorize limit numbers that change by plan/runtime. Know the categories, then verify the current limit for the exact workflow type and connector before design sign-off.

10 Concurrency, debatching and ordering

connect it to networking

Standard built-in X12, EDIFACT, AS2 v2, Flat File, XML and Liquid operations run with or as part of the Logic Apps runtime. That makes the earlier question - where does this operation execute? - directly relevant to B2B throughput and private-network reachability.

do not memorize one linking rule

Integration Account behavior varies by connector generation and operation. Standard also lets some maps/schemas live directly in the Logic App resource. AS2 v2 has specific linking requirements, while X12/EDIFACT operations can differ between built-in and managed forms. Check the exact connector you are using rather than applying one universal rule.

Artifact / capabilityWhat it represents
Trading partnerThe external or host organization and its business identity.
AgreementProtocol-specific send/receive rules between partners.
SchemaThe expected message structure used for validation/encoding/decoding.
MapTransformation rules between source and target message shapes.
CertificateSigning/encryption identity material used by B2B protocols.
  1. Partner + agreement define who is exchanging messages and under what B2B rules.
  2. Schema defines the message structure; map converts one structure to another.
  3. Certificates support signing/encryption scenarios such as AS2.
  4. For healthcare X12, the same model applies to HIPAA transaction sets such as claims (837), with HIPAA-specific schema/agreement considerations.

Logic Apps can be the orchestration layer for partner-facing B2B flows, not only JSON APIs. The key idea is to separate the business workflow from the trading-partner contract: protocol, identities, agreement rules, schemas, maps and certificates.

11 Schemas and transformations

boundary

Concurrency and splitOn interact: enabling trigger concurrency lowers the maximum debatch size. Also remember that connector throttling and backend capacity can become the real bottleneck even when the Logic App itself can run more work in parallel.

MechanismUse it when...Ordering implication
splitOnAn array should become separate workflow runs.Each item becomes independent; do not assume batch order is preserved.
Trigger concurrencyYou need to cap how many workflow instances run at once.Set to 1 when workflow-run sequencing is required.
For each parallelItems can be processed independently for throughput.Completion order can differ from input order.
For each sequentialEach item must wait for the prior item.Preserves loop sequence at the cost of throughput.

Throughput and ordering are architecture decisions. Ask whether one incoming event should remain one run, become many independent runs, or stay one run that processes many items.

12 Long-running and callback patterns

BizTalk bridge

If you already think in schemas, maps, envelopes and pipelines, the Logic Apps model is familiar: validate the incoming contract, normalize the data, then orchestrate. The product names changed; the integration problem did not.

Integration rarely fails because two systems cannot send bytes. It fails because they disagree on the shape and meaning of those bytes. Logic Apps provides different transformation tools for different data shapes.

13 Monitoring and observability

Design question: if the partner can call you back, prefer an event/callback pattern over aggressive polling. Stateful workflows are the natural fit when durable waiting and long-lived orchestration matter.
PatternUse it when...
DelayWait a known relative amount of time.
Delay untilWait until a known timestamp.
UntilRepeat work until a condition becomes true, with explicit limits.
HTTP WebhookThe external system supports subscribe/callback/unsubscribe and should notify you when work finishes.

Not every integration finishes in one HTTP round-trip. Logic Apps can wait, delay, loop, or use a callback pattern when the external process completes later.

14 Cost and limits as architecture constraints

  1. Use a business correlation ID that survives across APIM, Logic Apps, queues and downstream APIs.
  2. Use tracked properties / custom tracking ID to make business identifiers queryable.
  3. For Standard, enhanced Application Insights telemetry can expose trigger/action events, retries, connector usage, exceptions and dependencies.
  4. Alert on business-relevant failures, not only host CPU or generic platform health.

Run history answers "what happened in this workflow run?" Observability should answer the larger question: what happened to business transaction X across the integration path?

15 Standard project and deployment model

Standard is much closer to an application project than a single Azure resource definition. Each workflow has its own workflow.json; the project also contains shared files such as connections.json and host.json. Environment-specific values belong in app settings/parameters rather than being hard-coded into workflow definitions.

important files

workflow.json = workflow graph. connections.json = connector/connection metadata. host.json = runtime-wide settings shared by workflows in the app. local.settings.json = local-development settings; do not treat it as a production secret store.

17 Troubleshoot in this order

#QuestionWhat to inspect
1Did the trigger fire?Trigger history / request response / polling trigger status.
2Which action failed?Run history, inputs, outputs, status code.
3Where does that connector run?Built-in/in-app vs shared/managed.
4Can it reach the backend?DNS, VNet integration, routes, NSGs/firewalls, private endpoint.
5Can it authenticate?Managed Identity/RBAC, API connection, token audience/permissions.
6Did retry change behavior?Retry policy, 429/5xx/timeouts, duplicate side effects.
7Is the host healthy?Standard storage reachability, app settings, Application Insights/logs.
8Is this a scale/order problem?Trigger concurrency, splitOn, For each parallelism, connector throttling, waiting runs.
9Can I correlate the transaction?Business correlation ID, tracked properties, Application Insights Requests/Traces/Dependencies.
Good debugging question: "Is this a workflow-definition problem, connector-hosting problem, network problem, identity problem, or downstream-system problem?"
