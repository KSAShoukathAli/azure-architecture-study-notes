Azure Logic Apps - Feynman Way of Understanding

rebuild the platform from first principles instead of memorizing Azure terminology
Feynman goal: don't memorize "Logic Apps has triggers, connectors and retries." Rebuild the platform from the integration problem: something happens, several systems must coordinate, failures happen, and some state must survive.

1 Start with the problem, not the product

Imagine Azure Logic Apps does not exist. You have an EHR request, a queue, a partner API and a database. You need to coordinate them without writing a custom orchestration service from scratch.

what must exist?

Something must notice the event. Something must remember the workflow's place. Something must call the next system. Something must decide what to do when that call fails.

  1. Wake? - derive the trigger.
  2. Survive? - derive stateful vs stateless.
  3. Where? - derive connector hosting and network path.
  4. Fail? - derive retry, run-after, scopes and idempotency.
  5. Then ask about contract, concurrency, message shape, duration and observability.

2 Rebuild the trigger

A workflow sitting idle cannot magically know when to run. Therefore something has to convert an external event into a new execution.

Derivation:
message arrives → somebody must observe it → observation creates a run → that observer is the trigger.

HTTP Request, Recurrence and Service Bus are not three unrelated Azure features. They are three different answers to the same question: what event should wake this workflow?

3 Rebuild stateful vs stateless

Do not start with "stateful stores history." Start with the failure question: if this process disappears halfway through, do I need to reconstruct where it was?

Stateful

The answer is yes. Persist enough information to resume/reconstruct the run.

Stateless

The answer is no. Optimize for a short request-like execution and avoid persistence overhead.

boundary

A downstream 202 Accepted exposes the difference. Stateful HTTP actions can follow the asynchronous-operation pattern. Stateless workflows do not keep polling the Location URI as a stateful workflow does.

4 Rebuild connectors from "where does the code run?"

This is the most important Standard-specific question. Two actions can both say "Service Bus" but have different hosting/network implications depending on whether you choose the built-in/in-app connector or the shared managed connector.

Prediction: if the backend is private and reachable only through the app's VNet Integration, an in-app connector has a natural path. A shared connector may not, because its network call originates from shared connector infrastructure.

5 Rebuild identity: two trust boundaries

Ask two separate questions:

If you mix these questions together, auth designs become confusing very quickly.

6 Rebuild networking: direction first

Before naming a networking feature, ask which direction needs private connectivity.

Caller → Logic App needs private inbound? → Private Endpoint.
Logic App → private backend needs private outbound? → VNet Integration.
Connector call needs the VNet? → ask whether that connector actually runs inside the Logic Apps runtime.
why this compounds

This is the same networking model you already learned: Name → Address → Route → Allow. Logic Apps adds one more question before that model: where is the caller actually running?

7 Rebuild retries from uncertainty

A timeout does not prove the backend failed. It only proves the caller did not receive a usable response in time. Therefore retrying can repeat an operation that already succeeded.

derive idempotency

If "try again" can happen, the business operation needs a way to recognize "I already processed order 123." That's why correlation IDs, idempotency keys, message IDs and deduplication are integration concepts-not Logic Apps trivia.

8 Rebuild error handling

If a workflow has several steps, failure cannot mean "stop thinking." The runtime needs rules for what may execute after success, failure, timeout or skip. That gives you run-after conditions. Once groups of steps need common failure behavior, you need a grouping boundary: Scope.

Try Scope

Business path.

Catch Scope

Runs after failed/timed-out Try.

Finally Scope

Logging/cleanup after either path.

Feynman test: increase the batch size or concurrency by 10×. Predict which limit or downstream dependency becomes the bottleneck first.

Limits are not trivia to memorize. They are boundaries to test against your workload: message size, concurrency, run duration, loop/debatch size, connector throttling and chunking support.

Consumption

More executions and connector calls generally mean more metered activity. Loops and debatching multiply operations.

Standard

You provision host capacity for the runtime. Built-in operations are part of that host model, while shared managed connectors can still be metered separately.

10 Rebuild concurrency from "how many at once?"

your BizTalk bridge

This is the same architectural problem you already know from EDI/BizTalk: receive a partner contract, validate the envelope and schema, transform to an internal shape, then run the business process.

derive the product

If the workflow needs reusable trading-partner identities, agreements, schemas, maps and certificates, some artifact store has to exist. In Azure Logic Apps that role is played by the Integration Account and, for Standard, by artifacts that can also live directly with the Logic App resource depending on the operation.

Two organizations can both send messages and still be unable to do business together. Why? Because transport alone is not enough. They must agree on who they are, which protocol they use, what the envelope means, which schema is valid, and how security works.

11 Rebuild transforms from "same fact, different shape"

Feynman test: if you turn parallelism up, predict which system fails first - the Logic App, the connector, the API, the database, or the business ordering rule.

Suppose ten messages arrive together. Nothing in the word "workflow" tells you whether they should run one-by-one or all at once. You have to decide based on ordering, downstream capacity and throughput.

12 Rebuild long-running work from "must I keep polling?"

Once you see transformation as "preserve meaning while changing representation," choosing Liquid vs XSLT vs Flat File becomes a data-shape decision instead of product memorization.

An X12 claim, an XML document and a JSON API request can represent the same business fact in different shapes. Therefore an integration platform needs a place to validate structure and a mechanism to map one representation into another.

13 Rebuild observability from "prove what happened"

boundary

Callback architecture requires the partner/service to support a subscribe + callback contract. If it cannot, polling with an Until loop and sensible delay/backoff may be the only practical option.

14 Rebuild cost and limits from "where does work run?"

test

Can you start with one business ID and find the trigger event, retries, connector calls, exception and downstream dependency? If not, observability is incomplete even if every component emits logs.

Imagine someone asks: "What happened to prescription/order RX-12345?" A platform is not observable if the answer is "I can see that some workflow failed yesterday." You need a business identifier that crosses technical boundaries.

15 Rebuild Standard as an application host

Why does Standard have host.json, app settings, a storage account and multiple workflow folders? Because Standard is not merely "one workflow resource." It is an application host running the Logic Apps runtime.

Reasoning:
one host → many workflows → shared runtime settings → shared network identity → shared storage dependency → shared app configuration.

That is also why deployment looks like an application package rather than only an ARM JSON workflow definition.

18 Interview-length explanations

Consumption vs Standard

Consumption is the multitenant, pay-per-execution model where each logic app resource represents one workflow. Standard runs the single-tenant Logic Apps runtime, can host multiple workflows, supports stateful and stateless execution, local development, VNet integration and private endpoints.

built-in vs managed

In Standard, built-in connectors run with the Logic Apps runtime, so they can benefit from the app's VNet integration. Shared managed connectors run in Microsoft's shared connector infrastructure, so they don't automatically inherit the app's private network path.

stateful vs stateless

Stateful persists execution state and run history for durability and long-running workflows. Stateless minimizes persistence for low-latency, short-running scenarios and has different asynchronous-operation behavior.

identity

Inbound and outbound identity are separate. SAS/Easy Auth/APIM protect who can trigger a workflow; Managed Identity lets the Logic App authenticate to downstream Entra-protected resources without storing secrets.

observability

Run history explains one workflow execution; production observability should correlate a business ID across the workflow and downstream dependencies. Standard enhanced Application Insights telemetry can expose trigger/action events, retries, connector usage, exceptions and dependencies.

concurrency and ordering

Use splitOn when an array should become separate workflow runs; use trigger and For each concurrency to control parallelism. Higher concurrency improves throughput but can break ordering or overload downstream systems, so concurrency is a business and capacity decision, not just a performance knob.

B2B / EDI

Logic Apps supports enterprise B2B workflows through Integration Account artifacts such as partners, agreements, schemas, maps and certificates, plus X12, EDIFACT and AS2 operations. In Standard, built-in B2B operations run with the Logic Apps runtime, which matters for throughput and networking.
