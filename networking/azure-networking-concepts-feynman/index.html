— START WITHOUT AZURE —

1 Two machines want to communicate

the problem

Application A needs to send data to Service B. Forget Azure. What must be true before a packet can arrive?

Fact 1
The caller needs to know where B is.
Fact 2
Networks move packets using addresses, not application names.
Fact 3
A path must exist from source to destination.
Fact 4
Something may still block the traffic.

From those four facts, we can derive almost the entire networking stack:

Name → Address → Route → Allow. DNS → IP/CIDR → routing → NSG/firewall.
Feynman test

If you can explain a networking failure using these four words before mentioning Azure products, you are reasoning from the mechanism rather than recognition.

2 Why do VNet, CIDR and subnet have to exist?

start with the problem

I have many workloads. I need private addresses, I need to group them, and I need different rules for different groups. One giant undifferentiated address pool would be hard to secure and route.

So we invent a private address boundary. In Azure, that becomes the VNet. We need a compact way to say "these addresses belong to this network" — that becomes CIDR. We need smaller policy/routing zones inside it — those become subnets.

remove the vocabulary

"I have a private range 10.20.x.x. I split it into smaller ranges so web, app and private-endpoint resources can have different routing and security behavior." Only after that explanation do you reattach the labels: VNet, CIDR, subnet.

Break it

  • What if two subnets overlap? Azure won't allow overlapping subnet ranges inside the VNet.
  • What if future VNet/on-prem networks overlap? Connections such as peering become difficult or impossible without redesign/NAT patterns.
  • What if I make every subnet tiny? Scaling consumes addresses quickly; Azure also reserves five addresses per subnet.

3 Why does routing have to exist?

the problem

Knowing the destination IP still does not answer the question: which next hop should receive this packet?

A routing table is just a set of predictions: "If the destination looks like this prefix, send it there." Azure gives subnets system routes; you add UDRs when you need a different decision.

derive longest prefix match

If one rule says "all of 10.0.x.x goes left" and another says "10.0.1.x goes right," the second rule is more specific. That is why longest-prefix-match is a natural routing rule rather than an arbitrary Azure trick.

Prediction exercise

If you add 0.0.0.0/0 → Azure Firewall, predict what changes before testing: destinations with more-specific routes stay on those routes; everything else can be forced through the firewall.

4 Why does NSG have to be separate from routing?

the problem

A route can tell traffic how to reach a destination, but "reachable" is not the same as "allowed." We need a gate.

Route
Which path?
NSG
May it pass?

That distinction explains many confusing incidents: an NSG rule can be perfectly correct while the connection still fails because DNS or routing is wrong. And the reverse is true: the route can be correct while the NSG drops the packet.

boundary

An NSG is not an application authorization system. Allowing TCP 443 says the packet may reach the service; it does not say the caller may read Key Vault secret X or modify prescription Y.

— NOW ADD PAAS —

5 The PaaS problem

the new problem

My VM naturally has a NIC and private IP in my subnet. But Azure SQL, Key Vault or App Service is a managed service. I don't manage its underlying VM/NIC. How can my private network reach it as though it were private?

Now we can reason toward a solution without knowing the product name:

"Give my network a private IP that represents that managed service, and let Azure connect that private representation to the service behind the scenes."

That architecture has to look something like a Private Endpoint backed by Private Link.

three questions

Inbound? Private Endpoint. Outbound from App Service? VNet Integration. Need the service actually deployed into your network? Dedicated/injected deployment where supported.

6 Derive Service Endpoint vs Private Endpoint

same goal, two mechanisms

I want a subnet to reach Azure PaaS without treating it like an unrestricted internet destination. Do I need the service to acquire a private address in my VNet, or is it enough for the PaaS firewall to recognize which subnet I came from?

Derivation: Service Endpoint changes who the service trusts while keeping the public service address. Private Endpoint changes the address you connect to by adding a private IP in your VNet.

7 Rebuild Private Endpoint from first principles

facts we already know

The application calls a hostname. DNS turns that name into an IP. Routing acts on the IP. Therefore, if we want the application to use the new private path, the normal hostname eventually needs to lead to the Private Endpoint's private IP.

  1. Caller asks DNS for the service's normal hostname.
  2. Private DNS resolves the private-link name to the Private Endpoint IP.
  3. The packet is sent to that private IP in the VNet.
  4. Private Link carries the connection to the PaaS service.

Now remove one component at a time

ChangePrediction
Private Endpoint exists, but Private DNS isn't linkedThe hostname may resolve publicly or fail to resolve to the PE IP; the private path isn't selected.
Private DNS resolves correctly, but route/firewall blocks the IPName resolution looks perfect; connection still times out/fails.
Private path works, but public access remains enabledPrivate connectivity exists, but public exposure may still exist too.
Public access is disabled, but on-prem DNS can't resolve private linkHybrid caller has network connectivity but cannot discover the private endpoint correctly.
the sentence to own

Private Endpoint solves connectivity. DNS makes the hostname resolve to that private connectivity.

make it concrete

Common zones you will actually see: privatelink.blob.core.windows.net, privatelink.vaultcore.azure.net, privatelink.servicebus.windows.net, privatelink.database.windows.net, and privatelink.azurewebsites.net. Don't memorize the whole Azure list — learn to recognize the privatelink.* pattern and look up the exact service zone.

8 Why doesn't my 0/0 firewall route catch the Private Endpoint?

predict first

I have 0.0.0.0/0 → Azure Firewall. My Private Endpoint is 10.20.3.5. Will traffic to 10.20.3.5 automatically go through the firewall?

Terraform memory trap

Do not memorize one Terraform property forever. Older AzureRM 3.x used private_endpoint_network_policies_enabled; current AzureRM uses private_endpoint_network_policies and defaults it to Disabled. Provider version is part of the problem statement.

9 Rebuild APIM networking from traffic direction

Don't start with APIM tier names. Start with the traffic requirement.

The useful question: “Which direction must become private?” Once you answer that, APIM's VNet Integration, Private Endpoint and Injection options become much easier to place.

10 Derive hybrid DNS — why a resolver has to exist

problem

On-prem can route to 10.20.3.5, but when it asks for myvault.vault.azure.net, how does its DNS server learn that this name should become that private IP?

The reverse problem also exists: an Azure workload may need to resolve an on-prem name. That is why the managed resolver has both inbound endpoints and outbound endpoints + forwarding rulesets.

11 What does "public endpoint" really mean?

the confusion

If an Azure service has a public endpoint, does my packet literally leave Azure, cross the open internet, and then come back into Azure?

The mistake is mixing endpoint exposure/addressing with physical path. A publicly reachable endpoint can still be served over Microsoft's networking infrastructure. The security concern is that the endpoint is publicly addressable/reachable under its access controls, not that every byte necessarily leaves Microsoft's network.

Boundary

Private Link gives you a private-IP path. It does not automatically answer application identity, authorization, TLS design, data classification or every egress requirement. Networking solves networking problems; don't ask it to do identity's job.

12 VNet Integration vs Private Endpoint — derive the direction

scenario A

A VM in my VNet must call my App Service privately. Where does the private IP need to appear? On the caller's network side. That points to a Private Endpoint.

scenario B

My App Service must call a private SQL server or Private Endpoint in the VNet. Which side needs network access? The App Service outbound path. That points to VNet Integration.

Memory: Private Endpoint = "come privately to me." VNet Integration = "let me send privately from me into the VNet."

16 Interview-length explanations

Private Endpoint

"A Private Endpoint is a network interface with a private IP in my VNet that represents a supported Azure PaaS resource. My application still uses the normal service hostname; private DNS resolves that name to the endpoint's private IP, and Azure Private Link carries the traffic to the service. If I need private-only exposure, I also disable or restrict the service's public access."

VNet Integration

"App Service VNet Integration is an outbound feature. It lets the app send traffic into or through a VNet so it can reach private resources. It doesn't make the app itself privately reachable; for inbound private access I would use a Private Endpoint."

DNS

"A Private Endpoint gives me the private path, but DNS is what makes the existing service hostname select that path. If DNS still returns a public address, the Private Endpoint can exist and my application can still miss it completely."

Service Endpoint vs Private Endpoint

"A Service Endpoint keeps the PaaS service on its public address but lets the service firewall identify and trust traffic from my subnet. A Private Endpoint gives a specific resource a private IP inside my VNet, so DNS must resolve the service name to that private address. I use Private Endpoint when I need true private-IP access, granular resource isolation, or hybrid private access."

APIM networking

"I choose APIM networking from traffic direction. VNet Integration on Standard v2/Premium v2 is outbound to private backends. An inbound Private Endpoint makes the gateway privately reachable. VNet injection places supported APIM tiers into the VNet when I need stronger inbound/outbound isolation."
