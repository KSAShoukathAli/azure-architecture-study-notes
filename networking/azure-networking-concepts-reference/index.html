Azure Networking Concepts

reference notes — VNet, CIDR, routing, NSG, Private Endpoint, Private DNS and PaaS connectivity
The one-line model: DNS tells a workload where to send traffic, IP/CIDR defines the address space, routing decides which path to take, and NSGs/firewalls decide whether that traffic is allowed. A Private Endpoint gives a PaaS service a private representation inside your VNet; Private DNS makes the normal service name resolve to it.
Quick map: VNet / CIDR / subnet · routing · NSG · PaaS patterns · service vs private endpoint · Private Endpoint + DNS · PE routing gotchas · APIM · hybrid DNS · public vs private · troubleshooting

1 VNet, CIDR and subnet

A Virtual Network (VNet) is Azure's private network boundary for an address space in one region. You assign one or more CIDR ranges to it, then carve those ranges into subnets. A subnet is not just an IP bucket: it is where you attach routing and security policy and where many Azure services connect to the network.

ConceptWhat to rememberExample
VNetRegional private network/address boundary.10.20.0.0/16
CIDRIP range + prefix length. Smaller prefix number = larger network./16 is much larger than /24.
SubnetSmaller non-overlapping range inside the VNet. Policy and routes commonly attach here.10.20.2.0/24
Planning ruleLeave room for growth and avoid overlap with other VNets/on-prem ranges you may connect later.Peering can't be created for overlapping VNet address spaces.
Azure reservation

Azure reserves five IPv4 addresses in every subnet: the first four and the last. A /24 therefore has 256 total addresses but 251 usable addresses. Don't size a subnet by raw CIDR count alone.

2 Routing: where does the packet go?

After a destination IP is known, Azure must select a next hop. Every subnet already has system routes. You add a route table with user-defined routes (UDRs) when you need to override or extend that behavior — for example, to send outbound traffic through Azure Firewall or another network virtual appliance.

Longest prefix match: if both 10.0.0.0/16 and 10.0.0.0/24 match the destination, Azure selects the /24 route because it is more specific.
Next hop ideaTypical meaning
Virtual networkDestination is reachable inside the VNet.
VNet peeringDestination lives in a connected VNet.
Virtual applianceSend traffic through a firewall/NVA.
InternetUse Azure's internet path where outbound access is available.
NoneDrop the traffic.

3 NSG: route first, then allow or deny

A Network Security Group is a stateful packet filter. Its rules allow or deny inbound and outbound traffic by source, destination, port and protocol. NSGs can be associated with subnets and supported network interfaces.

Routing asks
"Where should this packet go?"
NSG asks
"May this packet pass?"
common mistake

An NSG does not create connectivity. You can allow TCP 443 all day, but if DNS points to the wrong IP or no route reaches that IP, the connection still fails.

4 Three PaaS network patterns

Azure PaaS complicates the picture because the service often doesn't begin life as a NIC inside your VNet. Start with the direction of the problem — inbound, outbound, or dedicated placement — and the feature name becomes easier to remember.

NeedPatternMental sentence
Private callers must reach PaaSPrivate Endpoint"Give my VNet a private IP that represents the service."
App Service/Function/Logic App Standard must call into VNetVNet Integration"Let my app send traffic into the VNet."
Service must be placed in/dedicated to the VNetDedicated VNet deployment / injection"Put the service in my network." Exact Azure terminology varies by service.
direction matters

For App Service specifically, a Private Endpoint is inbound only. App outbound traffic uses VNet Integration. Those are separate features and generally use separate subnets.

5 Service Endpoint vs Private Endpoint

Both features can restrict Azure PaaS access from a virtual network, but they solve it differently. A Service Endpoint keeps the service on its public endpoint and extends the subnet's identity to that service. A Private Endpoint creates a private IP in your VNet that represents one specific resource instance.

QuestionService EndpointPrivate Endpoint
Destination addressService's public IPPrivate IP in your VNet
DNS changeNoYes, normally Private DNS
ScopeService access from a subnet/VNet identitySpecific resource instance
On-premisesNot the private-access mechanism for on-premCan be reached over VPN/ExpressRoute when routing and DNS are configured
Current design preferenceUseful when supported/appropriate and simpler requirements fitPreferred for new private PaaS designs requiring private IP and stronger isolation
Memory: Service Endpoint = keep the public service address, extend my subnet identity to it. Private Endpoint = give my VNet a private IP for this resource.

6 Private Endpoint + Private DNS

A Private Endpoint is a network interface with a private IP from your VNet that represents a specific Private Link resource. The endpoint solves the connectivity problem. DNS solves the discovery problem.

  1. Caller asks DNS for the service's normal hostname.
  2. Private DNS resolves the private-link name to the Private Endpoint IP.
  3. The packet is sent to that private IP in the VNet.
  4. Private Link carries the connection to the PaaS service.
memory line

Private Endpoint solves connectivity. DNS makes the hostname resolve to that private connectivity.

You normally keep using the service's regular FQDN. Azure's public DNS introduces a privatelink CNAME, while the linked Private DNS zone supplies the private A record for clients that should connect privately. The application usually does not need a different connection string just because you added a Private Endpoint.

what if DNS is wrong?

The Private Endpoint can exist and be perfectly healthy while the application still connects to a public IP — or fails entirely — because the hostname didn't resolve to the private endpoint IP. That is why connectivity testing should start with name resolution.

7 Private Endpoint routing and subnet-policy gotchas

A Private Endpoint adds a very specific route for its private IP. That interacts with two ideas you already know: longest-prefix match and subnet network policies.

why 0/0 is not enough

A default route such as 0.0.0.0/0 → Firewall is broader than the Private Endpoint route, so it does not override the endpoint's more-specific path. If you intentionally want inspection through a firewall/NVA, enable the relevant Private Endpoint network policies on the subnet and design a UDR that is specific enough for the VNet/PE address space.

Terraform provider-version gotcha

Older AzureRM 3.x examples use private_endpoint_network_policies_enabled and defaulted that boolean to true. Current AzureRM uses private_endpoint_network_policies with values such as Disabled, Enabled, NetworkSecurityGroupEnabled and RouteTableEnabled, and the current resource default is Disabled. Check the provider version before copying old subnet code.

9 Hybrid DNS: Azure DNS Private Resolver

Hybrid Private Endpoint designs need two independent things: network reachability and name-resolution reachability. Azure DNS Private Resolver provides a managed way to forward DNS in both directions without running your own DNS VMs.

Hybrid rule: VPN/ExpressRoute can make the private IP reachable, but DNS still needs a forwarding path that returns that private IP. Routing without DNS is not enough.

10 Public endpoint does not mean "the packet left Azure"

A public endpoint is an endpoint exposed through publicly routable addressing/front-door infrastructure. That is a property of exposure and addressing. It does not by itself prove that the physical packet path left Microsoft's network and re-entered Azure. Keep these two questions separate: Is the endpoint public? and What network path did Azure use?

isolation boundary

Creating a Private Endpoint does not universally disable the service's public endpoint. When the design requires private-only access, disable or restrict public network access using the target service's controls.

11 Peering, on-prem and DNS reachability

VNet peering connects two VNets over Azure's network. Their address spaces must not overlap. Peering is not transitive by default: A↔B and B↔C does not automatically mean A↔C.

For on-premises networks, VPN or ExpressRoute can provide network reachability into Azure. But Private Endpoint designs also need a DNS path: on-prem clients must be able to resolve the private-link name to the private endpoint IP, often through DNS forwarding or Azure DNS Private Resolver.

Hybrid networking rule: network reachability and DNS reachability are two separate dependencies. You usually need both.

12 Troubleshoot in this order

#QuestionTypical check
1What name am I calling?Exact FQDN / URL.
2What IP does it resolve to?nslookup / dig.
3Is that IP the one I expected?Private vs public address.
4What route is selected?Effective routes / UDR / peering / firewall.
5Is traffic allowed?NSG, firewall, service access control.
6Is the service listening/authenticating?TCP/TLS/HTTP response, then identity/auth.
architect's habit

Don't begin troubleshooting with "Azure networking is broken." Reduce the problem to Name → Address → Route → Allow → Application. Find the first step where reality differs from your prediction.
