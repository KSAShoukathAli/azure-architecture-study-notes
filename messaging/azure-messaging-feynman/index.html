Azure Messaging - Feynman Way of Understanding

problem -> contract -> failure -> prediction -> boundary
Goal: do not memorize three Azure products. First decide what guarantee the communication itself requires.

1 Start with the asynchronous problem

System A creates work faster than System B can process it. Or System B is offline. Or five different systems may care about the same business event. A direct synchronous call couples their availability and speed.

A broker introduces time between producer and consumer. That changes the problem from can B answer now? to what must the broker remember until B is ready?

SURVIVE?
OWNER?
ORDER?
REPEAT?
REPLAY?

2 Classify the thing being sent

Command: the sender expects work to happen. Event: the publisher announces a fact and does not own every reaction. Stream event: one sample in an ongoing time-ordered flow that consumers may reread.

prediction

If a message means "charge this account exactly as part of this workflow," would you begin with Event Grid? Probably not. That is high-value work ownership, which points toward Service Bus.

3 Derive the Azure service

If you need...Think...
A durable unit of enterprise work with settlement, DLQ, sessions, transactions, or duplicate detectionService Bus
A discrete fact routed to interested handlers with filtering and retryEvent Grid
A high-volume retained stream, independent readers, partitions, offsets, replayEvent Hubs

4 Why does a queue exist?

Because work ownership and timing must be separated. A queue says: this work exists until one consumer finishes it.

derive it

If ten workers listen to one queue, you usually want them to compete for work, not all perform the same work. That is why a queue models a competing-consumer pattern.

A topic changes one assumption: more than one independent business capability needs its own durable copy. That produces topic subscriptions.

5 At-least-once falls out of distributed uncertainty

The consumer can update a database, then lose the network before telling the broker Complete. The broker sees an uncompleted lock and eventually redelivers. The broker is behaving correctly.

This is why "exactly once" cannot be treated as a magic broker switch for end-to-end business effects.

The clock is part of correctness

Peek-Lock defaults to 1 minute and can be configured up to 5 minutes. If work lasts longer, renew the lock. Otherwise the broker is free to redeliver.

Prefetch changes the clock

A prefetched message is already locked while it waits in the client buffer. More prefetch is not automatically more throughput if processing time can consume the lock before the handler starts.

6 There are two duplicate problems

Duplicate detection handles sender uncertainty by recognizing repeated MessageId values within a window. Idempotency handles consumer uncertainty by making the business operation safe to perform again.

break it

You enabled duplicate detection, but the consumer updates the database and crashes before completing the message. Can the business action still happen twice? Yes. Duplicate detection does not solve receive-side redelivery.

7 Ordering has a cost

The most scalable answer is often not "preserve all order." Ask which messages must be ordered relative to which other messages.

Service Bus sessions let you create ordered lanes by SessionId. Messages for Patient A can remain ordered while Patient B is processed in parallel.

8 A poison message needs quarantine, not infinite retry

If the same message fails repeatedly because its data is invalid or a deterministic code path is broken, retries only create heat. The DLQ separates failed work from the healthy flow while preserving evidence for repair.

Transient failure

Dependency unavailable, throttling, timeout. Retry with an appropriate backoff while the lock/host policy allows it.

Deterministic poison

Invalid schema or impossible business data. Repeating the same work does not heal it; dead-letter deliberately and preserve the reason.

large payload

If the payload itself is the problem, do not turn the broker into object storage. Store the large body externally and send a claim-check reference through the message.

9 Event Grid: the publisher should not own the reactions

Suppose a prescription changes state to Submitted. Billing, audit, notification, and analytics may care. The prescription service should not call every one of them.

It publishes a fact. Event Grid routes that fact to interested subscribers. Push delivery is natural when handlers can receive callbacks; namespace pull is useful when the consumer needs receive control, cannot expose an endpoint, or requires private-link receive semantics.

boundary

Event Grid does not promise ordered delivery. If your business correctness depends on per-key FIFO, that requirement points away from ordinary Event Grid event delivery and toward a broker/stream design that explicitly models ordering.

10 Event Hubs: stop thinking "message removed"

Event Hubs behaves like a retained partitioned log. Consumer A reading an event does not prevent Consumer B from reading the same event. Each consumer group tracks its own position.

Partitions give scalable ordered lanes. Checkpoints save consumer progress. Replay means moving the read position back within retention.

break it

Event 103 always fails, but events 104 and 105 are valid. If your consumer refuses to checkpoint past 103, the partition can suffer head-of-line blocking. If it checkpoints past 103, you need another place to preserve/retry that failed work. That tension is why a stream is not automatically a work queue.

11 A good architecture can use all three

example

Service Bus: durable prescription processing command.
Event Grid: announce that prescription processing completed.
Event Hubs: stream high-volume operational telemetry and analytics events; Capture/export to durable storage when long-term audit retention is required.

The services are not competitors when the semantics differ.

12 Async systems need a trace thread

The HTTP request disappears quickly, but the business transaction can live for minutes or hours. Carry a stable business correlation ID through every hop and log message identifiers, session/correlation properties, retries, settlement failures, and DLQ reason.

This becomes the foundation for the separate end-to-end observability topic later.

13 Blank-page explanation

say this without notes

Service Bus: durable enterprise work broker. Messages are settled; redelivery can happen; sessions provide per-key FIFO; DLQ isolates poison work.
Event Grid: routes discrete facts to interested subscribers using push or pull delivery; ordering is not guaranteed.
Event Hubs: retained partitioned stream. Consumers track offsets independently and can replay within retention.
Reliability: at-least-once means consumers must be idempotent.
Decision: durable work, state-change notification, or replayable stream.

transaction boundary

A Service Bus transaction does not make your SQL database update and broker send one distributed ACID transaction. If the business requirement is "update database and publish atomically," the later reliability page should derive the transactional outbox pattern.

14 Break the model

exercises
  1. A consumer updates SQL, then loses its Service Bus lock before completing. Predict what happens next.
  2. You need one copy for billing and one for audit. Queue or topic?
  3. Messages for one patient must stay ordered, but different patients can process in parallel. What key do you model?
  4. You enabled duplicate detection. Why is consumer idempotency still required?
  5. Five analytics applications need to reread the same telemetry independently. Service Bus topic or Event Hubs?
  6. You need Azure resource change notifications and do not care about ordering. Which service is the natural first candidate?
  7. Your Event Hubs consumer restarts. What lets it resume near the last successfully processed position?
  8. The DLQ keeps growing. What do you inspect before resubmitting?
  9. A Service Bus handler normally takes 7 minutes. The queue lock is configured for 5 minutes. What must the client do, and what happens if renewal fails?
  10. A FHIR bundle plus attachment is larger than the message size you want to tolerate. How would claim-check change the design?
  11. Event Hubs can retain events for weeks. Why is that still not your primary database or compliance archive?
  12. One Event Hubs event repeatedly fails while later events are valid. What happens to checkpoint progress, and when would a work queue be the better abstraction?
