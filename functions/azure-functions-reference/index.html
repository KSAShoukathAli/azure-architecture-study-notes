1 What Azure Functions solves

Functions removes the need to keep an application server running just to wait for work. An event arrives, Azure invokes code, the code performs a bounded task, and the hosting platform supplies instances according to the selected plan.

architecture boundary

A Function can call many services, but that does not make it durable orchestration. If workflow progress must survive restarts, waits, and multi-step failures, use a persisted workflow mechanism such as Durable Functions or Logic Apps.

2026 direction

For a new serverless Function app, Microsoft recommends Flex Consumption. Do not collapse the old Consumption lifecycle into one OS statement: Windows Consumption is still available but documented as legacy; Linux Consumption retires September 30, 2028 and no longer receives new features or language versions.

Flex design constraints

Flex is Linux code-only, supports one function app per plan, does not support deployment slots or the C# in-process model, and its Blob trigger uses the Event Grid source rather than the polling source. These constraints can rule it out for a specific workload even when its scaling model is attractive.

4 Scale and concurrency are different controls

  • Concurrency = how many executions one instance processes at the same time.
  • Scale-out = how many instances the platform runs.
  • Fixed concurrency is the default model for most triggers. Dynamic concurrency is opt-in and currently supported by Blob Storage, Queue Storage, and Service Bus triggers with supported extensions.
  • In Flex Consumption, HTTP, Blob Event Grid, and Durable triggers each scale as groups; most other trigger types scale independently per function.
  • Flex supports 512 MB, 2,048 MB, and 4,096 MB instances. For HTTP triggers, the default concurrency is 4, 16, and 32 respectively; Python defaults to 1 at every size.
  • Flex can scale to as many as 1,000 on-demand instances per scaling group. The default regional subscription quota is 250 cores across all Flex apps in that region, and always-ready instances count against that quota. Quota can therefore cap practical scale before the 1,000-instance service ceiling.
  • For Service Bus single-message processing, settings such as maxConcurrentCalls and maxConcurrentSessions shape per-instance parallelism unless dynamic concurrency takes over.
  • Batch Service Bus trigger gotcha: one invocation owns a batch, so batch-trigger concurrency is always 1 per function instance and dynamic concurrency does not apply to that batch execution model.
architect question

If a database can tolerate only 80 concurrent writes, should a Function app be allowed to scale to hundreds of instances with high per-instance concurrency? Scaling the consumer is easy; protecting the dependency is the design problem.

5 Service Bus trigger: settlement, locks, and redelivery

With automatic completion enabled, a successful invocation completes the message. If the invocation fails, the runtime abandons it; if the lock is lost or expires before settlement, the broker can make it available again. Delivery count rises, and after the entity's configured MaxDeliveryCount the broker moves the message to the DLQ.

at-least-once delivery + side effects = idempotency required

Do not equate Function success with business exactly-once processing. A crash can occur after an external side effect but before message settlement. The same message can then be delivered again.

The four Service Bus knobs to connect mentally

Setting / behaviorWhy it matters
autoCompleteMessagesDefault is true. The host completes on successful invocation and abandons on failure. Set false when your code deliberately owns settlement.
maxAutoLockRenewalDurationFor single-message processing, the host renews the message lock while the function runs, up to this configured duration. Current extension default is 5 minutes.
prefetchCountPrefetched messages are already locked. Oversized prefetch can spend lock time in the local buffer before processing starts and contribute to MessageLockLost.
maxConcurrentCalls / sessionsControls how much Service Bus work one scaled instance accepts. Higher values increase throughput but also pressure CPU, downstream systems, and lock timing.
lock gotcha

Automatic lock renewal is not an excuse for unbounded handlers. Processing that exceeds the configured renewal window, oversized prefetch, network/link failures, or CPU starvation can still produce MessageLockLost and redelivery. Batch-trigger lock behavior is different; do not assume single-message auto-renew semantics apply to batches.

identity + scale gotcha

The Service Bus extension can use administration APIs to obtain accurate queue/subscription counts for scale decisions. With identity-based connections, receiving messages and obtaining accurate scale metrics are different permission needs; Microsoft documents Azure Service Bus Data Owner or an equivalent custom read permission for the administration call. Without it, the extension can fall back to peek-based estimation.

failure mode

Retries can multiply side effects. Any action that creates, charges, sends, signs, or updates should have an idempotency strategy based on a stable business key or message identifier.

7 Managed identity and configuration

Prefer identity over secrets

Give the Function app a system-assigned or user-assigned managed identity, grant RBAC on Service Bus, Storage, Key Vault, SQL, or other Entra-protected resources, and use identity-based connections where the binding supports them.

Keep secrets out of code

Use application settings for configuration and Key Vault references for secrets. Key Vault references use the app identity by default, and a user-assigned identity can be configured when needed.

Key Vault networking

If the vault is network-restricted, the Function app must also have a working network path and DNS resolution to the vault. Managed identity proves who the app is; it does not create network connectivity.

8 Private Endpoint vs VNet integration

Private Endpoint gives clients a private inbound path to the Function app. VNet integration gives the Function app an outbound path into a VNet so it can reach private endpoints and network-restricted dependencies. These solve opposite directions and are often used together.

Current Functions networking support: Flex Consumption, Premium, and Dedicated support inbound Private Endpoint and outbound VNet integration. Consumption does not support those two capabilities for the function app. Functions hosted on Container Apps use Container Apps ingress/networking instead.

The storage account is part of the Function runtime

  • Every Function app depends on host storage through AzureWebJobsStorage. If that storage account becomes unreachable, the app or its triggers can fail even when your business dependency networking is correct.
  • When storage public access is restricted, the Function app needs outbound VNet connectivity plus DNS that resolves required storage service names to the appropriate private endpoint IPs.
  • The exact storage subresources depend on the hosting/content model and workload. Azure Files can be required for content on some plans; Durable Functions using the Azure Storage provider also needs Queue access. Flex stores its deployment package in a Blob container, by default in the same storage account unless you configure separate deployment storage.
  • Think in pairs: Private Endpoint creates private connectivity; DNS makes the normal storage hostname resolve to that connectivity.
common failure

"We disabled public access on Storage and the Function stopped starting" is usually not an application-code problem. Check VNet integration, the required storage private endpoints, private DNS links/forwarding, and the app's host/deployment storage settings.

9 Application Insights and runtime telemetry

  • Functions integrates directly with Application Insights and Azure Monitor.
  • Use APPLICATIONINSIGHTS_CONNECTION_STRING; the instrumentation-key setting is legacy.
  • Sampling protects cost and volume, but aggressive sampling can hide traces needed for diagnosis. Exclude critical telemetry types where appropriate.
  • Track dependencies so you can distinguish function execution time from downstream latency.
  • For scale issues, Functions can emit scale controller logs; for concurrency, look at Host.Concurrency traces when dynamic concurrency is enabled.
  • Carry a business correlation ID from APIM/Logic Apps/Service Bus into logs so one transaction can be followed end to end.

10 Deployment model and slots

  • Package-based deployment is the standard code deployment path. Flex Consumption runs from its managed deployment package by default.
  • For Premium/Dedicated, ZIP deployment plus run-from-package is recommended.
  • Changing app settings restarts the Function app.
  • Deployment itself can restart the app and terminate currently running functions. Durable or idempotent design matters for long processing.
  • Flex Consumption does not currently support deployment slots. Its RollingUpdate site update strategy drains and replaces instances to support zero-downtime updates. Microsoft's dedicated site-update documentation says it is generally available in selected regions with broader rollout in progress; other how-to content can lag this rollout. Treat regional availability as a deployment prerequisite rather than assuming it everywhere. The default Recreate strategy can terminate active instances during an update.

what unbounded really means

-1 removes the Functions execution timeout, not infrastructure lifecycle. On Flex/Premium, a scale-in event allows up to 60 minutes for an execution to finish, while a platform update gives 10 minutes. Long-running code still needs restart-safe design; do not interpret "unbounded" as "this process is guaranteed to stay alive indefinitely."

important

Even when function execution can run longer, an HTTP-triggered response still has a platform limit of about 230 seconds because of the Azure Load Balancer idle timeout. For long work, return quickly and continue asynchronously, or use the Durable async HTTP pattern.

12 Durable Functions roles

  • Durable client: starts orchestrations, raises external events, gets status, terminates/purges when authorized.
  • Orchestrator: deterministic control flow. It decides what should happen next; it should not perform ordinary nondeterministic I/O directly.
  • Activity: the normal place for database calls, HTTP calls, messaging, file work, CPU work, and other side effects.
  • Entity: message-driven, addressable state with explicit operations. Useful for small distributed state; not required for every workflow.
.NET 2026 gotcha

Use the isolated worker model for new .NET Functions. Flex Consumption does not support the C# in-process model, and in-process support ends November 10, 2026. Also check the target .NET runtime itself: .NET 8 and .NET 9 reach end of support on November 10, 2026, while .NET 10 isolated is supported through November 14, 2028. For a new late-2026 app, .NET 10 isolated provides the longer support runway when your dependencies are compatible.

13 Checkpoints, history, and replay

The orchestrator is not one thread sitting alive for hours. At durable wait points, the runtime can unload it. When something happens later, the runtime loads history and re-executes the orchestrator from the top. Calls already recorded in history return their historical result instead of repeating the external work.

determinism

Replay works only if the orchestrator makes the same decisions for the same history. Do not use ordinary wall-clock time, random values, arbitrary network calls, thread sleeps, or other nondeterministic APIs inside orchestration logic. Use Durable-provided time, GUID, timer, activity, and event APIs.

Long-lived orchestrations outlive your deployment

Changing orchestrator code can be a breaking data-format change because old instances replay against persisted history. Adding, removing, renaming, or reordering durable calls can make the new code disagree with old history and produce nondeterminism failures.

Built-in orchestration versioning

Microsoft now documents runtime orchestration versioning as the recommended strategy for most breaking changes. Each instance keeps a version, newer workers can continue older versions, and orchestrator code can branch on that version. It is backend-agnostic.

Side-by-side isolation

When built-in versioning does not fit, deploy old and new workflows side by side with separate task hubs/storage boundaries so old instances finish on compatible code. Stopping all in-flight instances is only reasonable when losing them is acceptable.

deployment test

Before changing an orchestrator, ask: did I change the name/input/output of a durable function, or add/remove/reorder an activity, sub-orchestration, timer, entity call, or external-event wait? If yes, treat the deployment as potentially breaking for in-flight instances.

Failure and retry behavior

Activity or sub-orchestration fails

The framework marshals the failure back to the orchestrator, where normal language-level error handling can decide whether to compensate, continue, or fail.

Retry at the call boundary

Activity and sub-orchestration calls can be scheduled with Durable retry policies. Retries create new attempts; they do not make an external side effect exactly-once.

  • An unhandled orchestrator exception completes that orchestration instance with Failed status.
  • A retry policy can add delay and repeat an activity or sub-orchestration call up to the configured limit.
  • Because an activity may fail after an external system accepted the side effect, side-effecting activities still need idempotency or a business deduplication key.
  • Compensation is a business decision, not an automatic rollback. The orchestrator must explicitly schedule compensating activities when that is the desired behavior.

15 Durable state storage / backends

  • Durable Task Scheduler is Microsoft's recommended managed backend in 2026 and works with Functions hosting SKUs.
  • Azure Storage provider stores orchestration data across queues, tables, and blobs and remains broadly used.
  • MSSQL provider is available as a bring-your-own backend for supported Durable Functions scenarios.
  • Netherite reaches end of support March 31, 2028; plan migration rather than choosing it for a new workload.
  • On Flex Consumption, Microsoft currently supports Durable Task Scheduler and Azure Storage as Durable storage providers.
  • Storage-provider migration is not an in-place state migration. Microsoft does not support moving existing task-hub data between providers; switching providers starts against a fresh, empty task hub. Plan how in-flight orchestrations will drain or remain on the old backend.
Durable beyond Functions

Do not confuse Durable Functions with the broader Durable Task programming model. The portable Durable Task SDKs can run workers on Azure Container Apps, AKS, App Service, VMs, or other compute while using Durable Task Scheduler as the managed orchestration backend. Durable Functions adds the Functions host, triggers/bindings, and its supported storage-provider choices.

18 Failure checklist for architects

  • Can the same event/message arrive twice?
  • If the function crashes after the side effect but before settlement, what happens?
  • What is the per-instance concurrency, and can the downstream service tolerate it?
  • Which component owns retries: Functions runtime, binding extension, Event Grid, or Service Bus?
  • What moves a poison item out of the hot path?
  • Do private DNS and outbound VNet integration allow the app to reach every network-restricted dependency, including AzureWebJobsStorage and deployment/content storage?
  • Will a deployment restart terminate in-flight work?
  • For Durable: is orchestration code deterministic, and is the deployment safe for in-flight orchestration versions?
  • Can orchestration history grow without bound? Should the design use sub-orchestrations, continue-as-new, or retention/purge controls?
  • Is each side-effecting activity itself idempotent or protected by a business idempotency key?
