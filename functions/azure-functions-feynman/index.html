1 Start with one small function

This is the cleanest Function mental model. Something happens. Azure gives your code a turn. Your code does one bounded piece of work. It finishes.

You do not need Durable Functions yet. There is no long-lived coordination problem.

predict

If the same HTTP request or message arrives twice, what should happen? If your answer is "two identical database inserts," you already found your first architecture problem.

2 Now connect it to Service Bus

Service Bus solves a very specific memory problem: it remembers that work still exists even when the Function is not running.

That is powerful, but notice the boundary. The queue remembers the message. It does not automatically remember that your five-step business process finished steps 1 and 2, is waiting for a doctor approval, and must resume at step 3 tomorrow.

3 Find the failure gap

This is why "Service Bus + Function" does not magically mean exactly once.

The safe question is not "Will Azure ever send this twice?" The safe question is "If this runs twice, can I detect that I already applied the business effect?"

redelivery is normal - duplicate side effects are the bug

4 Why a long workflow breaks the simple model

Imagine prescription enrollment:

1. validate request
2. call payer
3. call pharmacy
4. wait for clinician approval - maybe 2 days
5. if approved, submit
6. if rejected, cancel earlier reservations

A plain Function can execute code, but what should it do at step 4?

Bad idea: keep the process alive

Hold a thread or worker for two days waiting for approval. Expensive, fragile, and still lost if the process restarts.

Manual state machine

Write progress to a database, publish wake-up messages, correlate callbacks, reload state, manage timers, retry transitions, and make each transition safe.

The second design is legitimate. But once you build it carefully, you have started building an orchestration engine.

5 Derive Durable Functions from first principles

We need progress to survive. So persist the workflow's history. We need to continue later. So replay code against that history to rebuild local variables and control flow. We need side effects not to repeat during replay. So put side effects in activities and let replay return recorded results.

That is the core of Durable Functions.

6 Replay: the strange part

Suppose the orchestrator says:

result1 = call activity A
result2 = call activity B(result1)
wait for approval
result3 = call activity C(result2)

After activity A finishes, the runtime records that result. After activity B finishes, it records that too. Then the workflow waits for approval and the orchestrator can disappear from memory.

Tomorrow an approval event arrives. The runtime starts the orchestrator code again from the top.

This is why orchestrator logs can appear multiple times unless you use replay-safe logging. The code really can execute again. But history tells the runtime which durable operations are old and which one is new.

7 Why determinism is required

Replay assumes the same history leads the orchestrator down the same path. Break that assumption and the runtime cannot safely match today's code execution to yesterday's recorded decisions.

Inside orchestratorWhy
Use Durable context time APIsReplay must see the same logical time.
Use Durable GUID APIs when supportedA random GUID would change the path during replay.
Call external systems through activitiesNetwork calls are nondeterministic and have side effects.
Use durable timers, not thread sleepA timer is persisted; a sleeping thread is not.
Be careful with code changes for in-flight instancesNew orchestration logic may not match old persisted history.
predict

The orchestrator calls DateTime.Now and says "if hour > 17, send to night workflow." It runs at 4 PM, waits, then replays at 8 PM. Which branch should replay take? That ambiguity is exactly why ordinary wall-clock time is not allowed.

Now break it with a deployment

An orchestration may live longer than the code version that started it. Six months later, you add an activity before an old activity. Replay now sees history that says "A happened first" while the new code says "X should happen first." That is a versioning problem, not a random runtime bug.

repair the model

Use Durable's built-in orchestration versioning for breaking changes when it fits: an instance keeps its version, and newer workers can keep executing older-version instances with compatible branching. For stronger isolation, run old and new workflows side by side with separate task hubs until old instances drain. The key rule is simple: long-lived state needs long-lived code compatibility.

8 Waiting without holding a thread

A durable timer is a promise to resume later, stored outside the current worker. The worker is free to disappear. This is what makes day-long waits reasonable.

9 Fan-out / fan-in

Parallel work is not the interesting part. The interesting part is remembering which branches finished, surviving worker changes, then resuming exactly when the required set is complete.

break it

What if one branch succeeds, one fails permanently, and one is still running? Decide the business rule: fail fast, retry one branch, accept partial results, or compensate successful branches. Parallelism does not choose the policy for you.

10 External event + human interaction

This is one of the strongest Durable mental models. The workflow can race a durable timer against an external event. Nothing needs to poll every second. Nothing needs to hold a thread.

11 Monitor pattern

Sometimes you really do need to check an external condition repeatedly: "Has the lab result arrived?"

check condition
if done -> finish
if not done -> create durable timer for 10 minutes
wake later
check again

The key is the durable timer. The orchestration sleeps as persisted state, not as an occupied worker thread.

12 Saga / compensation

A distributed workflow cannot usually wrap three SaaS systems in one database transaction. So record completed business steps. If a later step fails, run compensating actions. Durable Functions helps remember the sequence, retries, and state. You still define what "undo" means.

13 Three tools, three abstractions

If the requirement is "when a Service Bus message arrives, validate JSON and call one API," plain Functions is natural. If the requirement is "fan out 200 tasks, wait for all, then pause for approval and compensate on failure," Durable is natural. If the requirement is dominated by connectors, B2B artifacts, visual run history, and integration operations, Logic Apps may be the cleaner abstraction.

14 If you know BizTalk, use the analogy carefully

BizTalk taught the same hard lesson years ago: long-running business processes cannot live only in RAM. BizTalk dehydrated orchestrations and rehydrated them later. Durable Functions solves the same class of problem, but with a different mechanism.

Useful analogy

BizTalk orchestration = persisted business control flow. Durable orchestrator = persisted business control flow.

Important difference

Durable reconstructs local state through deterministic replay against history. Do not imagine an XLANG/s instance being serialized and restored byte for byte.

External events feel similar to correlation: a later message must find the correct long-running instance. But in Durable, instance IDs and event names are explicit design choices.

15 Break the model

scenario 1

An activity charges a credit card, then the worker crashes before the activity completion is safely recorded. Could the activity run again? What business idempotency key protects the charge?

scenario 2

Your Service Bus trigger uses high concurrency and Flex scales rapidly. The database starts throttling. Which knob should change first: app instance ceiling, per-instance concurrency, database capacity, or the workload shape?

scenario 3

A Durable orchestration waits six months and your team deploys code that changes the branch logic. Old history can disagree with the new durable-call sequence and cause nondeterminism. Protect it with built-in orchestration versioning or side-by-side compatible deployments/task hubs.

scenario 4

You put a Private Endpoint on the Function app. The Function still cannot reach a private SQL endpoint. Why? Because inbound private access does not create the outbound VNet path.

scenario 5

You set a Premium Function timeout to unbounded, then call it over HTTP and wait ten minutes. Why can the client still lose the connection around 230 seconds? Execution timeout and HTTP response-path timeout are different boundaries.

scenario 6

You disable public access on the Function app's storage account. Your SQL private endpoint is perfect, but the Function host stops starting. What did you forget? The host itself depends on storage: it needs an outbound VNet path plus private DNS/private endpoints for the storage subresources it uses.

16 Rebuild from a blank page

  1. An event arrives.
  2. A Function is a small execution unit triggered by that event.
  3. The hosting plan decides how instances exist and scale.
  4. Concurrency decides how much work each instance accepts.
  5. Messaging retries can produce redelivery, so idempotency matters.
  6. If the process has many steps and long waits, local memory is not enough.
  7. Persist workflow history outside the worker.
  8. Replay deterministic orchestration code against that history to rebuild state.
  9. Put side effects in activities.
  10. Represent waiting as durable timers or external events, not sleeping threads.
  11. Keep long-lived orchestration code compatible with in-flight history; use versioning when durable-call structure changes.
  12. Remember that the Function host itself depends on storage and networking/DNS to that storage.
  13. Use compensation when a distributed business step must be undone.
  14. Choose plain Functions, Durable Functions, or Logic Apps from the abstraction the problem actually needs.
EVENT → FUNCTION → small work
ORCHESTRATOR → remembers progress → schedules activities → waits durably → replays history
