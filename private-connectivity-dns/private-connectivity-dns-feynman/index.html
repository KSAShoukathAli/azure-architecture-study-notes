Private Connectivity and DNS

Feynman page - derive it from the problem, not the product names. Details and failure modes: Reference notes.

The whole idea in one breath: most PaaS services are public by default. Your VNet is a private zone. Private connectivity is just the handful of ways to pull a service into that zone. DNS is what makes the calls actually go there.

1. Start with the problem: PaaS is public

Service Bus, SQL Database, Key Vault, Storage, your Logic App. Each one ships with a public hostname like mynamespace.servicebus.windows.net. Anyone on the internet can reach the front door.

So what stops them? Mostly identity - a key, a token, a connection string - plus any IP firewall rules you add. That's one wall. And credentials leak - into Git repos, logs, laptops. When that happens, a public endpoint is an open door.

You don't strictly need a VNet. Everything works over public endpoints. You add one for a second wall:

Identity decides who can use a service. The network decides where they can reach it from. With both, a stolen key alone is useless from the internet. In healthcare, organizations often make this a hard requirement.

2. The VNet: your private zone

A VNet is your own isolated network in Azure. You pick a private range (say 10.0.0.0/16), cut it into subnets, and control traffic with NSGs and routes. Think of your old datacenter network, rebuilt in software.

Here's the catch. PaaS services live outside it. So the real question is: how do you pull them in? The answer depends on one thing you might not expect - whether the service is shared or dedicated.

3. The spine: shared or dedicated?

This one question explains almost everything - the networking pattern, the cost, even how long provisioning takes.

Shared
Microsoft's machines serve many customers at once. They can't be moved into your subnet. So you connect with a private endpoint and VNet integration. Service Bus, SQL Database, Key Vault, Storage, Logic Apps on WS plans, APIM v2. Fast to create. Cheap to start.
Dedicated
The machines are yours alone. So Microsoft can place them inside your subnet. That's VNet injection. Classic APIM (Developer, Premium), ASE v3, SQL Managed Instance, Databricks. Slow to create. Higher starting cost.

Notice "PaaS" never came up. PaaS only tells you who patches the servers. It says nothing about the network.

The spine tells you why. The tier's docs tell you what is actually supported - confirm there before you design.

Dedicated is the easy case. It's injected - and in internal mode, private both ways (external mode still keeps a public gateway). Shared services take more work, because they stay outside and need a way in. That's next.

4. For shared services, direction decides

Ask one thing: who calls whom?

The receiver needs a private endpoint.
It gets a private IP in your subnet. Callers inside the VNet reach it there. Turn off public access and it disappears from the internet.
The caller needs VNet integration.
Its outbound traffic leaves through your subnet, so it can reach private IPs. Outbound only.

Service Bus is a mailbox. It never calls anyone - so it only ever needs a private endpoint (same for Key Vault, Storage, SQL Database, Cosmos DB, Event Hubs). Your Logic App gets called by APIM and calls Service Bus. So it needs both.

One exception: Event Grid is a caller, but it has no VNet integration for delivery. It can't deliver into your VNet. (Publishing to Event Grid can use a private endpoint - that's the inbound side.) One supported design: it delivers to services like Service Bus using managed identity, through their trusted Microsoft services exception - over the public endpoint, not the private one (that endpoint stays closed to everyone else - the firewall lets Event Grid through only because it's a trusted Microsoft service and proves itself with a managed identity).

Trap: VNet integration alone does not make an app private. The app keeps its public endpoint. You opened a door out and left the front door facing the internet. To close it, add a private endpoint and disable public network access - a separate, inbound step.

5. DNS: the part that actually breaks

Your Logic App calls a name, not an IP. By default that name resolves to the public IP. Public access is off, so the call fails - even though the private endpoint is sitting right there.

The fix is a Private DNS Zone linked to the VNet, so the same name returns the private IP from inside:

ServicePrivate DNS zone
Service Busprivatelink.servicebus.windows.net
SQL Databaseprivatelink.database.windows.net
Key Vaultprivatelink.vaultcore.azure.net
Logic App / App Serviceprivatelink.azurewebsites.net
Storage (blob)privatelink.blob.core.windows.net

When something can't connect, check DNS first. It's usually DNS.

6. Walk your pipeline

1-2 APIM lives in your subnet, so it calls the Logic App's private endpoint directly. privatelink.azurewebsites.net resolves the Logic App's name to 10.0.2.4. 3-4 The Logic App's outbound call enters the VNet through the integration subnet. DNS returns 10.0.2.5, so 5 it lands on Service Bus through its private endpoint.

Easy to miss: the Logic App's own storage account holds workflow state, across four endpoints: blob, file, queue, and table. Lock it down without private endpoints and DNS for it, and the Logic App won't even start. Also: Service Bus private endpoints need the Premium tier.

7. Three questions for any service

1. Shared or dedicated? Injection, or private endpoint + integration. Also tells you rough cost and deploy time.
2. Who calls whom? Receiver gets a private endpoint. Caller gets integration. Both directions, both.
3. How does the name resolve? No private DNS zone, no private traffic.

The network gets you to the door. Identity decides whether it opens - APIM still needs permission to call the Logic App, and the Logic App still needs a role to send to Service Bus.

9. Test yourself

Service Bus and Logic App are both PaaS. Why does one need integration and the other doesn't?

Direction. Logic App calls out, so it needs integration. Service Bus only receives, so a private endpoint is enough.

Logic Apps Standard is "single-tenant." So why can't a WS plan be injected?

Single-tenant means your own runtime and workers. But they sit on a shared App Service stamp whose front ends and network Microsoft owns. ASE v3 gives you the whole stamp, so it can be injected.

Why did your classic APIM take so long to create?

It's dedicated. Microsoft built VMs, a load balancer, and networking just for you, inside your subnet. Shared services just carve out a slice.

Private endpoint exists, public access is off, call still fails. First check?

DNS. The name is probably still resolving to the public IP.
