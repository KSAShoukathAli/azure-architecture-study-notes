Private Connectivity and DNS

Reference notes - for lookup when you design or troubleshoot. The Feynman page builds the model; this page holds the details, tier limits, and failure modes.

The model in one line: pick the connection option the service and tier support, make sure the name resolves to the private IP from wherever the caller sits, then check the caller has permission. Placement, direction, DNS, identity - in that order.

1. The connection options at a glance

OptionDirectionWhat it gives youPublic endpoint after?Typical services
Private endpoint (Private Link)Inbound to the serviceA NIC with a private IP in your subnet, mapped to one service instanceStill on until you disable public accessStorage, Key Vault, SQL DB, Cosmos DB, Service Bus Premium, App Service family, APIM
VNet integrationOutbound from the appThe app's calls leave through a delegated subnet, so it can reach private IPsUnchanged - integration never touches inboundApp Service, Functions, Logic Apps Standard, APIM Standard v2 / Premium v2
VNet injectionBothThe dedicated instance runs inside your subnetDepends on mode (internal vs external)Classic APIM Developer/Premium, APIM Premium v2, ASE v3, SQL MI
Service endpointInbound to the serviceYour subnet reaches the service over the backbone; the service can allow that subnet in its firewallYes - the service keeps its public IPStorage, Key Vault, SQL DB, Cosmos DB, Service Bus Premium
Private endpoint vs service endpoint: a service endpoint keeps the public IP and only works from Azure subnets. It can't be reached from on-prem, and it allows the whole service type from that subnet, not one instance. A private endpoint gives one instance a private IP that on-prem can reach over VPN or ExpressRoute. For new designs, default to private endpoints.

3. Private endpoint anatomy

PieceWhat to know
Network interfaceA NIC in your subnet with a private IP. It's the only thing that lives in your VNet - the service itself doesn't move.
Sub-resource (group ID)A PE targets one sub-resource: blob, queue, vault, sites, namespace, Gateway. Need blob and queue? Two PEs.
Connection approvalAuto-approved if you have rights on the target. Otherwise it sits Pending until the owner approves - common across subscriptions and tenants.
RoutingAzure adds a /32 route for the PE IP to the VNet and peered VNets. It's more specific than a broad UDR, so traffic can bypass your firewall unless you plan for it.
NSG and UDR on the PEOnly applied when private endpoint network policies are enabled on the subnet.
DNS zone groupAttach one to the PE and Azure writes and cleans up the A record in the private DNS zone for you. Without it, you manage records by hand.
Public accessCreating a PE does not close the public endpoint. That's a separate setting on the service.

4. VNet integration (App Service family)

SettingWhat to know
SubnetDedicated and delegated to Microsoft.Web/serverFarms. Size it for scale-out - every instance takes an IP.
What goes through itTraffic to private IPs goes through the VNet. Turn on outbound internet routing ("route all") if internet-bound calls must also pass your firewall or NAT gateway.
DNSThe app uses the VNet's DNS settings, so private zones linked to that VNet (or your resolver) apply.
InboundNot affected. Add a PE and disable public access to make the app private.
Logic Apps Standard storageThe runtime needs its storage account's blob, file, queue, and table endpoints. Lock the account down and each needs a PE and a zone, or the app won't start.
Portal experienceWith public access disabled, the designer and run history need a browser inside the network (VPN, Bastion, jump box).

Rules that keep DNS sane: one zone per name for the whole organization, linked to every VNet that needs it. Attach a DNS zone group to each PE so records stay in sync. Test from where the caller actually runs, not from your laptop.

7. Hub-spoke DNS

In a hub-spoke network, don't create privatelink zones in each spoke. You'd end up with several copies of the same zone, each holding different records, and resolution would depend on which VNet asked.

PieceWhere it lives
Private DNS zonesOnce, centrally (hub or connectivity subscription)
Zone linksTo the hub, and to each spoke - or spokes point their DNS at a central resolver
PE recordsWritten into the central zones by DNS zone groups, often enforced with Azure Policy
Spoke DNS settingAzure default, or the resolver's inbound IP (or firewall DNS proxy) for a single controlled path

168.63.129.16 is Azure's built-in resolver. It only answers from inside Azure, which is why on-prem needs the resolver below.

9. Event Grid: the delivery exception

SidePrivate option
Publishing to Event Grid (inbound)Private endpoint on the topic or domain
Delivery from Event Grid (outbound)No VNet integration, and delivery through private endpoints isn't possible

One supported design for a locked-down destination: Event Grid delivers to Service Bus, Event Hubs, or a Storage queue using a managed identity, through the destination's trusted Microsoft services bypass. The traffic uses the destination's public endpoint. Your private code then pulls from there through its private endpoint.

Setup for Service Bus or Event Hubs: enable a managed identity on the topic or domain (system- or user-assigned), grant it Data Sender on the namespace, turn on "Allow trusted Microsoft services", and set the subscription to deliver with that identity. Service Bus needs Premium for the bypass. Storage queues with a firewall accept only the system-assigned identity. Alternative: Event Grid namespaces with pull delivery, where your consumer pulls over a private endpoint.

11. Commands

Run DNS checks from where the caller runs. Your laptop's answer tells you nothing about the VNet's.

# From a VM or on-prem machine: expect a privatelink CNAME and a 10.x address
Resolve-DnsName sb1.servicebus.windows.net
nslookup sb1.servicebus.windows.net

# Can you reach the port once DNS is right?
Test-NetConnection sb1.servicebus.windows.net -Port 443

# From an App Service, Function, or Logic App: Kudu console (Advanced Tools)
nameresolver sb1.servicebus.windows.net
tcpping sb1.servicebus.windows.net:443

# Is the PE connection approved?
az network private-endpoint-connection list --id <resource-id> -o table

# Which VNets is the zone linked to?
az network private-dns link vnet list -g <rg> -z privatelink.servicebus.windows.net -o table
